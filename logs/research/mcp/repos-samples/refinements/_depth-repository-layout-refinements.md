# Depth Pass Refinements — Sample > Repository layout

Per-role cross-corpus refinement proposals from inspecting every sample's content under this role.

The role's level-2 description focuses on architectural shipping unit (single-package vs monorepo vs cross-language). Cross-corpus inspection surfaces three persistent under-described axes: explicit `src/` vs flat package shape, the role of an `awslabs.*`-style namespace prefix, and "monorepo" really being three distinct shapes (independent servers, namespace-prefixed siblings, multi-published-package coordinated by workspace tooling). A handful of mis-placements stem from the consolidated using one phrase ("Single-package src-layout") for what samples treat as two distinct conventions.

## Description sharpenings

> Format: `<role-chain> > <path>` — what the existing description misses; cross-corpus evidence; sharpened text suggestion

- `Sample > Repository layout > Single-package src-layout` — the description names "src/<package>/" as the shape but ~half of supporting samples actually place the package directly at the repo root (`<package>/`, no `src/`). Examples that do use `src/`: `chroma_mcp` (`src/chroma_mcp/`), `crystaldba--postgres-mcp` (`src/postgres_mcp/`), `qdrant--mcp-server-qdrant` (`src/mcp_server_qdrant/`), `redis--mcp-redis`, `feiskyer`, `mahdin75`, `mukul975`, `shibuiwilliam`, `zilliztech`, `baryhuang`, `ckreiling`, `alexei-led`, `designcomputer`, `jlowin--fastmcp`, `motherduckdb`, `sajal2692`, `thenets`. Examples that do NOT (flat package directory at repo root): `pagerduty_mcp/`, `clickup_mcp/` (DiversioTeam), `alpaca_mcp_server/`, `servicenow_mcp/` (echelon-ai-labs), `cursor_notebook_mcp/`, `earthdata_mcp_server/`, `app/` (the-momentum--fhir, voska--hass), `semantic_scholar/` (zongmin-yu), `ktanaka101`, `tumf--grafana-loki-mcp`, `lanbaoshen`. Both shapes are present under one bucket because authors use "src-layout" loosely to mean "modern Python packaging." The bucket as currently labeled implies an explicit `src/` directory; the supporting evidence shows the actual common factor is "single installable Python package with `pyproject.toml`," with `src/` present in roughly half the samples.

  Sharpened text suggestion: "Modern single-package Python (or TypeScript) layout with one `pyproject.toml` (or `package.json`), `tests/` sibling, optional `examples/`, `dev/`, `docs/`, `agents/`, `.github/`. The package lives at the repo root either as `src/<package>/` (explicit src-layout, prevents accidental imports during testing) or as `<package>/` directly (flat package-at-root). Both shapes share the same packaging ergonomics — one importable distribution, conventional tests directory, modern build backend — and the choice between them is largely an author preference. Same shape across Python, TypeScript, and other runtimes. Appropriate for servers that wrap one upstream service and ship one distributable package."

- `Sample > Repository layout > Single-package source (language-conventional)` — description says "the simplest organization" and lists `cmd/`, `pkg/`, `internal/` for Go and `app/`, `src/` for TypeScript; supporting samples include both Go SDK-shaped projects (`github-mcp-server`, `googleapis--mcp-toolbox`, `geropl--linear-mcp-go`, `korotovsky`) and TS projects with `src/` and `package.json` (`Figma-Context-MCP`, `executeautomation`, `v-3--discordmcp`, `docker--hub-mcp`, `ahmedmustahid`, `paypal`, `exa-labs`, `HenkDz`, `DaInfernalCoder`, `jparkerweb`). The "simplest" framing under-sells: the bucket is really "follow the language ecosystem's default layout" — Go follows `cmd/`/`pkg/`/`internal/`, TS follows `src/`+`package.json`, npm-bin packages follow flat. The unifying factor is conventionality, not simplicity.

  Sharpened text suggestion: "One module/package laid out in the language ecosystem's standard form: Go uses `cmd/` for binaries plus `pkg/`/`internal/` for libraries (`cmd/github-mcp-server`, `geropl--linear-mcp-go`, `googleapis--mcp-toolbox`, `korotovsky/`); TypeScript projects use `src/` with `package.json`, `tsconfig.json`, optional `dist/` (`Figma-Context-MCP`, `docker--hub-mcp`, `executeautomation`, `paypal`, `v-3--discordmcp`); npm-distributed JS often uses a flat layout with a `bin/` entry. The package shape follows ecosystem convention rather than being a deliberate organizational choice. Appropriate when one server is one product."

- `Sample > Repository layout > Single Rust crate` — description is accurate but missing the "minimal Cargo project" baseline that two samples represent. `apollographql` and `rust-mcp-stack--rust-mcp-filesystem` add `/examples` and `/e2e` (or `tests/`) substantively; `conikeec--mcpr` is a library with `/src/` and `/examples/`; `elastic--mcp-server-elasticsearch` is the most elaborate with `tests/`, `docs/`, `scripts/`, `.buildkite/`. The path is accurate but description should acknowledge that supporting samples span "minimal example crate" through "production-shaped crate."

  Sharpened text suggestion: "`Cargo.toml` at repo root with source under `src/`, optionally `tests/`, `docs/`, `examples/`, `e2e/`, plus build/CI artifacts (`Makefile`, `Makefile.toml`, `Dockerfile`, `.buildkite/`). Spans library crates (a published `mcpr`-style SDK) and binary crates shipping an MCP server. Appropriate when Rust is the primary language and only one crate is published from the repo."

- `Sample > Repository layout > Single-package flat layout` — description currently says "server file at repo root with optional `src/<helpers>/`. Common for hackable community servers." Supporting samples are split: `AlwaysSany--deepl-fastmcp-python-server` and `duolingo--slack-mcp` have `main.py` at root (clean flat); `marlonluo2018--pandas-mcp-server` has scripts at root with `/core` subdir for support; `shreyaskarnik--huggingface-mcp-server` has the server file at root plus `src/huggingface/` for helpers — explicitly the hybrid case. The shape is consistent. Description is accurate; minor sharpening to acknowledge the hybrid sub-pattern.

  Sharpened text suggestion: "Server entry-point file (`main.py`, `<name>_mcp_server.py`) at repo root, with `pyproject.toml`/`requirements.txt` and `Dockerfile` as siblings. Helpers may live in a sibling subdirectory (`/core`, `src/<helper>/`) when the entry-point file would otherwise grow too large. Common for hackable community servers where the entire surface fits in one or two files. Appropriate for small, single-author projects where src-layout overhead would be ceremony."

- `Sample > Repository layout > Single-file script / monolith` — description says "one .py file, sometimes very large (~112 KB), with requirements.txt or no manifest." Supporting samples: `hannesrudolph` (single file + requirements/docs), `labeveryday--mcp_pdf_reader.py`, `misbahsy--video-audio-mcp` (`server.py`), `normaltusker--kotlin-mcp-server.py` (the 112 KB outlier with 32 tools), `twolven--mcp-server-puppeteer-py`. One useful disambiguation vs `Single-package flat layout`: the monolith doesn't have helper modules (or has a single `vscode_bridge.py` companion); the flat layout has helpers in a subdir. The line between the two is whether helper files exist. Worth surfacing.

  Sharpened text suggestion: "The entire server is one source file at repo root — no helper modules, optionally a `requirements.txt` or `pyproject.toml` next to it, sometimes no manifest at all. Sizes range from a few hundred lines to ~112 KB monoliths with dozens of tools (`normaltusker--kotlin-mcp-server.py`). Distinguished from *Single-package flat layout* by the absence of helper modules — a monolith is the script alone; the flat layout has the script plus a `/core/` or `src/<helper>/` companion. Appropriate when the surface is small enough that splitting adds no value, for prototypes and demonstrations, and for projects optimizing for 'one file to read'."

- `Sample > Repository layout > Monorepo of namespace-prefixed packages` — description says "many sub-packages under `src/<name>/` each with their own `pyproject.toml`, all sharing a namespace prefix." All four supporting samples are awslabs (`awslabs--mcp` parent, `aws-api-mcp-server`, `aws-documentation-mcp-server`, `bedrock-kb-retrieval-mcp-server`). The pattern is genuine but the corpus evidence is one organization deep. Worth flagging that this is "the awslabs pattern" — a Python namespace-package model where `awslabs.<server>` is the import path.

  Sharpened text suggestion: "Many sub-packages under `src/<server-name>/` each with their own `pyproject.toml`, all sharing a Python namespace prefix (e.g., `awslabs.aws_api_mcp_server`). Central dev tooling at root (ruff, pre-commit, secrets baseline). Each sub-package independently published to PyPI and installable via `uvx`. The awslabs/mcp monorepo is the canonical example with 40+ servers; the pattern requires the namespace package to be set up in each sub-package's `pyproject.toml`. Appropriate when one organization ships many related servers and wants consistent tooling, identity (the namespace prefix is a brand mark), and per-server release independence without combining them into one package."

- `Sample > Repository layout > Monorepo of independent servers` — description says "Many subdirectories, each a standalone MCP server with its own Dockerfile, scripts, and tests. A `Dockerfile.template` at root acts as scaffolding..." Strong match for `FuzzingLabs--mcp-security-hub` (38 tool subdirs each with Dockerfile + script + tests, `Dockerfile.template` at root). The other supporting sample, `microsoft--playwright-mcp`, is described in the sample only as "Monorepo with `/packages` directory" — which is closer to a Turbo+pnpm monorepo than to "many independent servers each with own Dockerfile." Possibly mis-placed; see *Mis-placed samples* below.

- `Sample > Repository layout > Hosted-service layout (Next.js app + mcp-src + lib)` — description's parenthetical names Next.js + mcp-src + lib, matching `neondatabase--mcp-server-neon` exactly. The other supporting sample (`idosal--git-mcp`) uses React Router + Cloudflare Workers + Wrangler, NOT Next.js. The unifying axis is "the deliverable is a hosted service rather than a published package," not the specific framework. The bucket name should generalize.

  Sharpened text suggestion (also implies a heading rename — flag for reconciler): rename heading to "Hosted-service layout" without parenthetical narrowing. "Repo is shaped as a deployable web service rather than a publishable package: a frontend or framework app at root (Next.js `landing/`, React Router `app/`, Cloudflare Worker entry), an `mcp-src/` or equivalent for tool/handler logic, a `lib/` for shared OAuth/config helpers, stratified `tests/`, optional `.claude/skills/` co-located. Examples: `neondatabase--mcp-server-neon` (Next.js + mcp-src + lib), `idosal--git-mcp` (React Router + Wrangler + Cloudflare Workers). Appropriate when the deliverable is a hosted service rather than a published package, and the team wants client/landing UI and MCP transport in one repo."

- `Sample > Repository layout > Single-package with dual-ecosystem wrapper` — description says "Python package as canonical implementation with thin npm wrapper that invokes the Python entry point." Strong match: `rohitg00--kubectl-mcp-server` (Python core + npm publisher wrapper invoking Python). Strong match: `stripe--agent-toolkit` (Python and TS published in parallel from same repo). Weak match: `sandraschi--email-mcp` — the sample says "Cargo.toml alongside pyproject.toml — Rust-side present (likely for MCPB bundle signing)." That's not a wrapper; the Rust isn't invoking Python. Mis-placement candidate; see *Mis-placed samples*.

- `Sample > Repository layout > Multi-directory single-repo (ancillary services)` — single sample (`sandraschi--email-mcp`), but content matches description well: `src/email_mcp/` core, `mcp-server/` packaging, `webapp/` monitoring dashboard with Vite+Uvicorn, `monitoring/` health/metrics. Description is accurate.

- `Sample > Repository layout > Umbrella consolidation` — single sample (`Azure--azure-mcp`); description captures it well, including the multi-month gap between code-freeze and formal archival. No sharpening needed.

- `Sample > Repository layout > Domain-per-module decomposition` — single sample (`severity1--terraform-cloud-mcp`); description matches the sample's "one module per upstream-API object class" enumeration. Description accurate.

## Sub-axis observations

> Format: `<role-chain> > <path>` — sub-pattern observed; supporting sample count; whether to fold into description or propose split

- `Sample > Repository layout > Single-package src-layout` — sub-axis: explicit `src/` directory vs flat package-at-root. Supporting samples split roughly half-and-half (~17 explicit `src/<package>/`, ~16 flat `<package>/` at root, given the 35 supporting samples). The two shapes are interchangeable for consumers but they're a real authoring choice and a common confusion. Recommendation: **fold into the description** rather than split — the role's purpose is "single Python/TS package as one shipping unit," and both shapes deliver that. Splitting would create two paths that consumers can't distinguish without looking inside the repo.

- `Sample > Repository layout > Single-package source (language-conventional)` — sub-axis: Go (`cmd/`/`pkg/`/`internal/`) vs TypeScript (`src/`+`package.json`+`tsconfig.json`) vs npm flat (`package.json`+`bin/`). Supporting sample distribution: ~6 Go, ~9 TS, ~1 mixed. The shapes are language-determined; splitting would create per-language buckets that contradict the methodology's goal of role-not-tool. Recommendation: **fold into the description** with explicit naming of the language conventions, not split.

- `Sample > Repository layout > Single-package src-layout` — secondary sub-axis: `app/` as package name vs `<project_name>/`. Two samples (`the-momentum--fhir-mcp-server` with `module-name = "app"`, `voska--hass-mcp` with `app/` module) chose the `app/` convention. Three samples (zongmin-yu, alpacahq, …) chose project-named flat packages. Both small clusters; no split warranted, but the description should not assume the package directory is project-named.

- `Sample > Repository layout > Monorepo of namespace-prefixed packages` and `Sample > Repository layout > Monorepo sub-package` — both describe the awslabs pattern from different angles. `Monorepo of namespace-prefixed packages` describes the parent monorepo; `Monorepo sub-package` describes one sub-package within. They are not alternatives — they're the same pattern at different granularities. Three samples chose "namespace-prefixed packages" (parent or whole) and one (`awslabs--openapi-mcp-server`) chose "sub-package" — but they're the same physical layout; see *Mis-placed samples* and *Proposed bucket merges*.

## Proposed bucket merges

> Format: `<path-A> + <path-B>` — why same; supporting samples; canonical name suggestion

- `Sample > Repository layout > Monorepo sub-package` + `Sample > Repository layout > Monorepo of namespace-prefixed packages` — both describe sub-packages within a multi-server Python monorepo with shared central tooling and per-package PyPI release. The only difference is whether the sample focuses on the parent (whole monorepo) or one child (sub-package). All four supporting samples (`awslabs--mcp`, `awslabs--aws-api-mcp-server`, `awslabs--aws-documentation-mcp-server`, `awslabs--bedrock-kb-retrieval-mcp-server`) are awslabs siblings; `awslabs--openapi-mcp-server` is also awslabs but currently sits under `Monorepo sub-package`. Same pattern, two labels — merge candidate. Canonical name suggestion: keep `Monorepo of namespace-prefixed packages` and treat each sub-package as part of that monorepo. Move `awslabs--openapi-mcp-server` accordingly.

  Caveat for reconciler: the bucket merge is unambiguous for awslabs, but `pathintegral-institute--mcp.science` (currently under `Monorepo with per-server subdirectories and one PyPI package`) is a related-but-distinct shape — single PyPI package routing to multiple servers via CLI subcommand, no namespace prefix per server. That stays separate.

## Proposed bucket splits

- None proposed. The corpus contains genuine variation but the splits the variation suggests (explicit `src/` vs flat, Go-vs-TS conventional, framework-specific hosted-service flavors) are sub-patterns within their existing buckets, not distinct paths consumers would choose between. The methodology's "refine descriptions; don't restructure" guidance applies. ## Cross-corpus observations

> Patterns visible only with full role visibility — surface even if not actionable now

- **The "src/" prefix is a Python-flavor signal more than a layout signal.** Half the Python supporting samples under `Single-package src-layout` use `src/<package>/` (the explicit src-layout that prevents accidental imports during testing); the other half use the package directly at the repo root. Authors call both "src-layout" colloquially because they ship one importable package via pyproject.toml. The bucket's name promises an explicit `src/` directory it doesn't deliver in half the cases. This is the single largest description-vs-evidence gap in the role.

- **Monorepo branches collapse into three real shapes.** The corpus has 9 buckets containing the word "Monorepo": `independent servers`, `namespace-prefixed packages`, `sub-package`, `with multiple published packages`, `with per-server subdirectories and one PyPI package`, `Turbo + pnpm`, `Gradle multi-module / Maven multi-artifact`, `Cross-language monorepo`, `Polylith components (Clojure)`. Cross-corpus inspection shows three real shapes underneath: (a) namespace-prefixed Python siblings each independently published — awslabs and one umbrella variant; (b) JS/TS workspace-orchestrated monorepos publishing multiple packages — Stripe, Supabase, Upstash, Cloudflare, Sentry, Microsoft Playwright; (c) cross-language reference sets — modelcontextprotocol/servers and Kotlin SDK. The current 9-bucket fragmentation reflects authoring vocabulary (Turbo vs Gradle vs Polylith), not three distinct consumer-facing decisions. No split or merge proposed at this pass — the language-tooling differences are real for contributors — but flagging for the reconciler that the role's vocabulary is overloaded.

- **The "Hosted-service" path is one decision, two stacks.** Both supporting samples (`neondatabase`, `idosal`) ship a hosted MCP service with frontend + transport + lib + tests, but one uses Next.js and the other uses React Router + Cloudflare. The bucket name's parenthetical (`Next.js app + mcp-src + lib`) is one sample's specific shape promoted to the canonical name. Generalize the heading and let the description list both stacks.

- **`.codex-plugin/` and `.claude-plugin/` and `skills/` are appearing in repos as siblings to source.** Five supporting samples explicitly mention these (blazickjp, openags, exa-labs, getsentry, slackapi, stripe). The host-integration sibling pattern is becoming a marker of "this server is being shipped to multiple AI hosts, not just MCP-compatible clients." Relevant to *Single-package plus sibling host integrations* and *Configs-only*; the pattern overlaps both. Not actionable in this pass but worth noting for the role's evolution.

- **A handful of samples carry `.claude/`, `.claude-plugin/`, or `CLAUDE.md` at repo root.** Across the supporting samples, these appear in: `apollographql--apollo-mcp-server` (`.claude` + `CLAUDE.md`), `bhauman--clojure-mcp` (`.claude/`), `exa-labs--exa-mcp-server` (`.claude-plugin/`), `getsentry--sentry-mcp` (`.claude-plugin/` + `.mcp.json`), `hugoduncan--mcp-clj` (`.claude/`), `makenotion--notion-mcp-server` (`CLAUDE.md`), `slackapi--slack-mcp-plugin` (`.claude-plugin/`). Cross-cuts repository-layout buckets — present in src-layout, language-conventional, monorepo, Polylith, configs-only, hosted-service. Not a layout dimension itself but worth noting that ~7% of the corpus surface this signal in the layout content.

- **Single-sample paths cluster into "long tail of unique-shape repos."** Of 30 paths in the role, 17 have exactly one supporting sample, and 8 have two. Only 5 paths have >2 samples. The role's tail is heavy because repository layout is a high-degree-of-freedom decision; small organizational variations (`changeset/`, embedded test substrate, ancillary monitoring dashboard) get their own paths because no two repos solve them the same way. The methodology's "convergence" signal applies less cleanly here than for narrower roles like Transport — long-tail singletons are a feature of the role, not a divergence to drive out.
