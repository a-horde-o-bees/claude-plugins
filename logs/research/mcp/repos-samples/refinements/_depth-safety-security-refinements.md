# Depth Pass Refinements — Sample > Safety and security posture

Per-role cross-corpus refinement proposals from inspecting every sample's content under this role.

Inspected 25 paths total — 19 with supporting samples, 3 with zero samples (Path/repo allowlist as access control, MCP Roots-driven scope, Migration prepare/commit pattern), 3 paths defined but supported only via cross-role linking. Total 31 samples exhibit the role; mongodb-js alone carries 5 paths, and the long tail is single-sample paths from one project apiece. ~6 KB sample evidence pulled across paths.

## Description sharpenings

> Format: `<role-chain> > <path>` — what the existing description misses; cross-corpus evidence; sharpened text suggestion

- `Sample > Safety and security posture > Read-only by default with explicit write flag` — current description lists launch-flag and env-var examples but doesn't name the sub-mechanisms the corpus actually uses. Across 11 samples the read-only posture is implemented through five distinct mechanisms (each visible in a different sample): tool-set suppression at launch (PagerDuty, geropl, github, mongodb-js, terraform-cloud, rust-mcp-stack, motherduck, hf), URL query parameter (supabase), DB engine native flag (ktanaka101's DuckDB `--readonly`), SQL parser-based rejection (crystaldba's pglast), and tool-set authoring discipline (hf ships no write tools at all). The description should acknowledge that the user-facing posture is the same but the *enforcement layer* varies — and that crystaldba's path also surfaces under "In-process safety enforcement via parsing" because the same project deliberately documents both the user-facing flag and the underlying parsing technique. Sharpened text: append "Enforcement layer varies — tool-set suppression at launch, URL parameter gating, DB-engine-native readonly mode, SQL parser-based rejection of mutating statements, or simply not shipping write tools. Authors who rely on parser-based enforcement may surface the technique separately under *In-process safety enforcement via parsing*."

- `Sample > Safety and security posture > Lockdown / content-filter mode` — current description focuses on filtering untrusted upstream content before returning it to the agent. Of the two supporting samples, one (github `--lockdown-mode`) matches this; the other (supabase) is *prompt-injection mitigation* — wrapping SQL results with anti-injection instructions so LLMs resist following commands embedded in returned data. Both filter what reaches the model but the techniques are distinct: upstream-content filter vs result-wrapping with anti-injection prompts. Sharpened text: clarify that the path covers two related techniques — pre-return filtering of untrusted upstream payloads (github lockdown-mode) and prompt-injection mitigation via output-wrapping (supabase wraps SQL results with anti-injection instructions). Both operate on data flowing back to the model regardless of which tools are enabled.

- `Sample > Safety and security posture > Explicit non-security stance` — current description matches Playwright's posture (README disclaimer + escape-hatch flag) but the second supporting sample (v-3/discordmcp) is doing something different: it's an operator-guidance disclaimer urging human approval before sending messages. There's no enforcement either way, but Playwright explicitly opts *out* of being a security boundary, whereas discordmcp is asking operators to *be careful*. Sharpened text: split the framing — the path covers two stances: "this server is not a security boundary, here is the escape-hatch for risky modes" (Playwright) and "operator should require human approval for sensitive operations" (discordmcp). Both are documentation-only postures with no runtime enforcement. (See also Mis-placed samples below — discordmcp may belong under Anti-multi-tenancy disclaimer or a renamed "Documentation-only safety stance" path.)

- `Sample > Safety and security posture > None / not surfaced` — current one-liner ("Many projects ship full capabilities unconditionally") understates what the supporting samples reveal. Of three samples, bhauman has a sandbox-example file but no server-layer enforcement (gestures at sandbox, doesn't enforce it), redis has transport-layer SSL but no application gating, and sandraschi markets quality but enforces nothing. The corpus visibility shows "None / not surfaced" actually has texture: the absence is sometimes tacit (no mention), sometimes acknowledged (sandbox example without enforcement), and sometimes hidden behind transport-level guarantees masquerading as security. Sharpened text: "Server ships full capabilities unconditionally with no application-level safety gates documented. Variants surface in the corpus: tacit absence (no mention), acknowledged absence (sandbox example demonstrating the pattern but not enforcing it), or transport-only gates (TLS/SSL knobs that do not address application-level safety). Appropriate when the upstream is read-only or the tool surface is genuinely safe; problematic when the project's marketing claims quality discipline that the implementation does not back."

- `Sample > Safety and security posture > Workspace path enforcement (canonicalization)` — current description names canonicalization (`os.path.realpath`) as the mechanism. The three supporting samples reveal the canonicalization is actually the *narrowest* of the three: jbeno does explicit realpath checks, samuelgursky validates paths stay in expected directories (mechanism unnamed), and normaltusker uses `WORKSPACE_PATH` env var paired with audit logging tied to compliance modes (GDPR/HIPAA). The compliance-audit pairing is distinctive enough to mention. Sharpened text: append "Some implementations pair workspace enforcement with audit logging tied to compliance regimes (GDPR/HIPAA), where the path-restriction is one half of a dual safety+compliance posture."

- `Sample > Safety and security posture > Hardened-by-default container posture` — current description focuses on Dockerfile baseline (non-root, capability-drop, read-only mounts, resource limits) which matches FuzzingLabs. The second supporting sample (rust-mcp-stack) emphasizes a *different* hardening — multi-stage build producing a static binary atop alpine, primarily for attack-surface minimization rather than the FuzzingLabs-style cap-drop discipline. Sharpened text: acknowledge that hardening surfaces in two flavors — capability-restriction discipline (non-root + dropped caps + read-only mounts + resource limits) and attack-surface minimization (multi-stage build, static binary, minimal alpine final image). The two often co-occur but the corpus shows projects emphasizing one or the other.

## Sub-axis observations

> Format: `<role-chain> > <path>` — sub-pattern observed; supporting sample count; whether to fold into description or propose split

- `Sample > Safety and security posture > Read-only by default with explicit write flag` — five enforcement-layer sub-mechanisms across 11 samples. Probably fold into description (sharpened text above) rather than split into 5 paths — the user-facing posture is what the operator chooses; the enforcement layer is implementation detail of how the posture is realized. Splitting would obscure that they all share the same operator-facing semantics.

- `Sample > Safety and security posture > Workspace path enforcement (canonicalization)` — pairs with compliance-audit logging in 1 of 3 samples (normaltusker). Too thin to split; fold into description.

- Role-level — across all 25 paths, mechanisms cluster into five disciplines: **static gating** (read-only, destructive-action, capability-scoped, sandbox-mode default), **runtime input/output gating** (tool-layer query validation, AST validation, blacklist-filtered, in-process parsing, defusedxml, index-scan rejection, mode parameter), **workflow gating** (destructive-tool elicitation, migration prepare/commit, mode plan-vs-execute, per-tool auto-approve), **boundary/scope clamping** (workspace path enforcement, path/repo allowlist, MCP Roots-driven, temporary-user TTL), and **stance/documentation only** (explicit non-security stance, anti-multi-tenancy disclaimer, MseeP.ai badge, none/not surfaced). Hardened-by-default container posture sits orthogonally — it's deployment hardening, not application gating. The role-level description currently says "what the server constrains and defends against" without naming these disciplines. Consider adding to the role-level prose a one-paragraph map of the five disciplines so readers can navigate the 25 paths by intent rather than scanning every leaf. Not a structural change; an orientation aid for the role's prose.

## Cross-corpus observations

> Patterns visible only with full role visibility — surface even if not actionable now

- **Power-law distribution.** mongodb-js alone carries 5 of the 25 paths (read-only, destructive elicitation, dry-run config dump, index-scan rejection, temporary-user TTL). The long tail of 12 single-sample paths means most "safety mechanisms" in the consolidated are exemplars from one project apiece. The 11 read-only-by-default samples are the only meaningfully-multi-sample path; everything else is 1-3 samples. This shapes how the consolidated should be read: it documents the *space* of options, not a mainstream of conventions.

- **Stance vs mechanism separation.** Across the role, four paths (`Anti-multi-tenancy disclaimer`, `Explicit non-security stance`, `MseeP.ai security badge`, `None / not surfaced`) are *not safety mechanisms* — they're documentation/stance/absence. They form a natural cluster the consolidated could either group prose-wise (in the role description) or factor as a sub-region. The current arrangement intermingles them with mechanism paths in the alphabetized leaf order, making the role harder to navigate.

- **Two paths borrow each other's evidence.** crystaldba--postgres-mcp appears under both `Read-only by default with explicit write flag` and `In-process safety enforcement via parsing` — same project documenting the user-facing posture and the enforcement technique as separate paths. This is the only such double-listing in the corpus and reflects an authoring choice (postgres-mcp deliberately exposes both views). Worth leaving as-is — the duplication is meaningful, not accidental.

- **The "in-process execution" cluster is fragile by design.** Three paths (`AST validation with import allowlist`, `Blacklist-filtered code execution`, `In-process safety enforcement via parsing`) all gate user-supplied code or queries via parser/validator logic in-process. Two acknowledge their fragility explicitly (blacklist-filtered says "known-fragile"; AST allowlist says "trust depends entirely on the allowlist's tightness"). Process isolation as an alternative is conspicuously absent from the corpus — no sample exhibits a sandbox-process / restricted-exec posture for code execution. Worth flagging in the role description as an absence the corpus exposes.

- **Container hardening sits at the role boundary.** `Hardened-by-default container posture` is the only path in this role that addresses deployment-layer (not application-layer) safety. The path is also cross-linked from *Container artifacts*. This is correct cross-role placement, but the role's description prose treats deployment hardening as if it were one mechanism among many, when it's actually a different layer of defense. The role description could note that one path operates at deployment layer; the rest at application layer.
