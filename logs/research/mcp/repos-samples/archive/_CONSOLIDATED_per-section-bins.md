# Sample

Heading-by-heading accumulation of synthesized findings across the 104 MCP server repos under `repos-samples/`. Empty sections are unsynthesized; populated sections carry the canonical synthesis for that section.

## Identification

Stable repo-metadata across the 104 MCP server samples. Per-sample identity facts (URL, owner/repo, one-line purpose) don't aggregate as adoption signals — they're properties of each repo. License, default-branch, star-count and lifecycle distributions, however, surface useful cross-cutting patterns about what kind of code populates the MCP ecosystem.

### url

All 104 samples are GitHub-hosted (`https://github.com/<owner>/<repo>` form). No GitLab, Bitbucket, Codeberg, or self-hosted repos surfaced — the corpus is GitHub-skewed by construction (sourced from picker queries against GitHub-indexed search).

Owner concentration is light: of 104 samples, only `awslabs` (6 sub-server entries within the umbrella monorepo) and three two-entry owners (`modelcontextprotocol`, `cyanheads`, `datalayer`) repeat — the remaining 96 samples come from 96 distinct owners. The picker enforces deduplication well; no owner dominates.

## Language and runtime

The base technology stack for each MCP server. The corpus is dominated by two language ecosystems — Python and TypeScript/Node — which together account for ~85/104 samples. Go, Rust, Clojure, Kotlin, C#, and C++ form the long tail. Within Python the SDK choice splits roughly evenly between FastMCP (a decorator-based wrapper) and the raw `mcp` SDK; within TypeScript the canonical `@modelcontextprotocol/sdk` is near-universal. Version constraints are documented unevenly — some samples cite explicit `requires-python` or `engines.node`, others infer floors from `.python-version` files or fall back to `not extracted within budget`.

**Python SDK choice as a divide.** FastMCP and raw `mcp` are nearly evenly split among Python samples — ~24 vs ~25 of the 63 Python repos — with a small overlap (~5 samples carry both, typically as migration shim or to keep the `mcp` CLI tooling alongside the FastMCP server). FastMCP positions itself as a higher-level decorator API; raw `mcp` is the lower-level protocol surface. The corpus does not show a clear migration direction — both grow.

**TS-SDK monoculture.** Of ~24 TypeScript samples, ~22 use `@modelcontextprotocol/sdk` directly. The exceptions (`cloudflare/mcp-server-cloudflare`'s internal `@repo/mcp-common` abstraction and `neondatabase/mcp-server-neon`'s `mcp-src/` subdivision under Next.js) layer atop the canonical SDK rather than replace it. No TS counterpart to the FastMCP-vs-raw-`mcp` split exists.

**Go SDK fragmentation.** Three Go SDK options coexist: `mark3labs/mcp-go` (canonical), `metoro-io/mcp-golang` (alternate), and custom-from-spec (4 samples). The split is meaningful — Go samples don't show convergence on a single SDK the way TS does.

**Custom-from-spec as a meaningful minority.** ~10 samples implement MCP without depending on a published SDK — including `awslabs/mcp-lambda-handler` ("protocol implementation without official SDK"; flagged in Unanticipated axes), `FuzzingLabs/mcp-security-hub`, `teaguesterling/duckdb_mcp`, the two Clojure servers, and the four custom-Go servers. Custom-from-spec is most common in Go and in language ecosystems where an SDK doesn't yet exist (Clojure, C++/DuckDB). Reveals MCP's spec-first nature: the protocol is implementable without an SDK when the ecosystem requires.

## Transport

How each MCP server speaks to its host. The corpus is overwhelmingly stdio-default — stdio is the only universally-attested transport, present in 93/104 samples either as the sole supported mode or as the documented default. Streamable HTTP (and its predecessor SSE) is the second-tier transport; ~45/104 ship it alongside stdio as a network-mode alternative. WebSocket and in-memory transports surface only in language-SDKs and reference implementations. The MCP spec prescribes stdio for local-host pairing and Streamable HTTP for network deployments — the corpus aligns strongly with this prescription, with SSE persisting as a legacy mode that several repos explicitly call deprecated. How transport is selected splits across five mechanisms: default-only (no selector), CLI flag, env var, separate console-script or subcommand, URL path on a shared server, and programmatic API for SDKs.

**Multi-transport adoption.** ~45/104 samples ship more than one transport; ~55/104 are stdio-only. The corpus's most-multi-transport repos:

- `modelcontextprotocol/kotlin-sdk` — five transports (stdio, Streamable HTTP, SSE, WebSocket, ChannelTransport) in one SDK; the broadest transport surface in the corpus
- `viant/mcp` — four (HTTP/SSE, Streamable HTTP, stdio, plus experimental HTTPS-with-custom-auth)
- `mark3labs/mcp-go`, `metoro-io/mcp-golang`, `feiskyer/mcp-kubernetes-server`, `opensearch-project/opensearch-mcp-server-py`, `rohitg00/kubectl-mcp-server`, `lanbaoshen/mcp-jenkins`, `hugoduncan/mcp-clj`, `AlwaysSany/deepl-fastmcp-python-server`, `qdrant/mcp-server-qdrant`, `korotovsky/slack-mcp-server`, `utensils/mcp-nixos`, `mahdin75/gis-mcp` — three-transport (stdio + HTTP + SSE) is the typical "rich transport" shape

**Transport posture clusters:**

- **Stdio-only by deliberate framing** — `awslabs/mcp` (sample notes: "SSE removed 2025-05-26; Streamable HTTP planned"), `paypal/paypal-mcp-server`, `severity1/terraform-cloud-mcp`, `geropl/linear-mcp-go`, `samuelgursky/davinci-resolve-mcp`, `mukul975/cve-mcp-server`. Several explicitly state "no network transport documented" or "outbound-HTTPS only (no inbound listener ports)" — stdio-only is a deliberate posture, not just an omission.
- **HTTP-only / network-only** — `awslabs/mcp-lambda-handler` ("there is no stdio path — this is inherently HTTP"), `slackapi/slack-mcp-plugin` (HTTP remote endpoint), `supabase-community/supabase-mcp` (HTTP canonical), `googleapis/mcp-toolbox` (HTTP-first), `cloudflare/mcp-server-cloudflare` (Streamable HTTP via `/mcp` Worker endpoint), `duolingo/slack-mcp` (HTTP-only on port 8001), `idosal/git-mcp` (HTTPS cloud endpoint). All hosted/cloud-deployed servers; opposite extreme of stdio-only local-host servers.
- **Stdio + HTTP/Streamable HTTP dual** — the typical "ship both" shape; ~30/104 follow this pattern. Stdio for local Claude Desktop pairing, HTTP for shared deployments. Adoption signals investment in both deployment models.
- **stdio + SSE (legacy network)** — repos that haven't migrated SSE→Streamable HTTP yet — `crystaldba/postgres-mcp` (`--transport=sse`), `tumf/grafana-loki-mcp` (stdio + SSE), `zilliztech/mcp-server-milvus` (stdio + SSE), `sooperset/mcp-atlassian` (SSE primary — unusual). Cross-references the legacy-transport observation.
- **stdio emulation via client-side shim** — `mcp-remote` (npm package, published outside the server's repo) is the host-side stdio↔HTTP bridge used by `cloudflare/mcp-server-cloudflare`, `idosal/git-mcp`, and other remote-only servers. The server speaks HTTP, the host wants stdio, and `mcp-remote` translates. Captured in detail in the Entry-point/launch wrapper analysis; flagged here as a transport-architectural pattern.

**Authoritative-doc alignment.** The MCP spec prescribes stdio (local) and Streamable HTTP (network), with SSE marked as the predecessor of Streamable HTTP (deprecated). Corpus practice aligns:

- stdio adoption (93/104) matches the prescription's "default for local hosts"
- Streamable HTTP adoption (38/104) is the dominant network-transport choice; explicitly named as the "primary" or "current" mode in 11+ repos
- SSE is universally treated as the deprecated mode it is — 7+ repos call out the deprecation explicitly; many that ship it pair it with Streamable HTTP and note the migration path
- WebSocket is spec-permitted but corpus-rare (2/104) — only `modelcontextprotocol/kotlin-sdk` actually ships it

The one tension: SSE persists as the *primary* network transport in `sooperset/mcp-atlassian` (5k stars, community-canonical for Jira/Confluence). The sample notes don't explain why SSE-primary over Streamable HTTP — re-examination would help establish whether this is migration lag, host-compatibility constraint, or deliberate.

The MCP spec doesn't prescribe a selection mechanism — it defines transport semantics, not the launcher contract. Corpus practice picks whichever mechanism fits the launch wrapper: CLI flags dominate for native-binary servers, env vars dominate for Docker-launched servers, programmatic APIs dominate for SDKs/frameworks, URL-path/config dominate for hosted services. The five mechanisms are largely substrate-aligned rather than competing alternatives.

**Outliers worth re-examining:**

- **Subcommand-as-mode vs flag-as-mode** as distinct architectural choices — `echelon-ai-labs/servicenow-mcp` ships *two console scripts* (one stdio, one SSE) instead of one binary with a flag. The two-binary approach simplifies per-transport configuration but loses runtime selection. `ahmedmustahid/postgres-mcp-server`'s positional subcommand (`stdio` keyword vs bare command for HTTP) is a middle path. Flag-as-mode is dominant; subcommand-as-mode is the minority architectural posture.
- **`zilliztech/mcp-server-milvus` env-vs-CLI precedence inversion** — sample notes flag this server as one where env vars *override* CLI flags rather than the other way around. Inverts the precedence convention assumed by most CLI-aware hosts. Already noted in Unanticipated axes.
- **`teaguesterling/duckdb_mcp`'s SQL-PRAGMA selection** — uniquely transport-via-SQL: users configure transport with `PRAGMA mcp_server_start(...)` from inside DuckDB. No corpus parallel. Sample-grade outlier; reveals MCP can run as a database extension where SQL becomes the launcher.

**Pitfalls observed:**

- **SSE deprecation timing varies by repo** — `awslabs/mcp` documents the SSE removal date (2025-05-26) explicitly; `cloudflare/mcp-server-cloudflare` and `neondatabase/mcp-server-neon` ship `/sse` alongside `/mcp` without committing to a removal; `sooperset/mcp-atlassian` documents SSE as primary without deprecation framing. Consumers depending on SSE should track per-repo deprecation timelines, not assume corpus-wide SSE removal.
- **"stdio implicit" vs "stdio documented"** — many samples report stdio without README confirmation, inferring from `npx`/`uvx` invocation patterns or "Claude Desktop integration only" framing. Sample notes flag this for `spences10/mcp-turso-cloud`, `rust-mcp-stack/rust-mcp-filesystem`, `riza-io/riza-mcp`, `pathintegral-institute/mcp.science`, `DaInfernalCoder/perplexity-mcp`. Inferred-stdio is data, but not equivalent to README-documented support.
- **Transport flag semantics drift** — `microsoft/playwright-mcp`'s `--port <n>` *flips* the transport from stdio to SSE/HTTP based on port presence, while `executeautomation/mcp-playwright`'s `--port` does the same — but `feiskyer/mcp-kubernetes-server`'s `--port` is meaningless without `--transport`. Hosts and downstream agents can't infer transport-from-flag-shape uniformly across the corpus.

## Distribution

How each MCP server reaches end users. The corpus splits roughly into three packaging traditions — Python (PyPI + uvx), JavaScript (npm + npx), and Container (Docker / GHCR) — with most repos publishing through one tradition and many backstopping with a second channel. Outside those three, registry mechanisms (Smithery, mcp-get) and ecosystem-native channels (Cargo, Maven Central, Homebrew, `go install`, Nix) appear in smaller counts. A meaningful long tail ships source-only (clone-and-run / editable installs / `make`-based) without any registry presence, and a small but distinct cluster runs as remote / hosted endpoints where users register a URL rather than install a binary.

> The README one-liner doubles as MCP-host config: hosts paste the command (or its `command` + `args` decomposition) into `claude_desktop_config.json` / `mcp.json` and the result is a working server. This drives the heavy preference for single-line invocations — `uvx <pkg>` and `npx -y <pkg>` dominate because they collapse "install + run" into one string the host can substitute verbatim.

**Pitfalls observed:**

- README install commands often elide the host-registration step. `uvx <pkg>` runs the server, but the user must also encode that command in their MCP host config (`claude_desktop_config.json` / `mcp.json`); samples that show only the `uvx` invocation can mislead first-time users.
- A repo with no PyPI/npm publication but a "discovered package name" in this synthesis can be misleading — `cyanheads/perplexity-mcp-server` is "not on npm registry" but the repo name suggests publication; consumers should verify against the registry, not the repo. Sample notes for ~7 repos explicitly flag "not confirmed on PyPI" or "presumably not published."
- Smithery is sometimes written as if it were a primary channel ("install via Smithery") when in practice it's a `npx -y @smithery/cli install` wrapper around an underlying PyPI/npm publication — agents should treat Smithery as installer-orchestrator, not as the source of truth for what's published.

## Entry point / launch

The exact command an MCP host invokes to start the server. The shape mirrors the chosen distribution channel — `uvx <pkg>` and `npx -y <pkg>` collapse install + launch into one string for hosts to substitute verbatim, while console scripts (`<name>` directly), Docker `docker run`, ecosystem-native invocations (`go run`, `clojure -Tmcp`, Cargo binaries), and bare `python <file>.py` cover the long tail. A small but distinct cluster has *no* user-runnable command — frameworks/SDKs (`jlowin/fastmcp`, `awslabs/mcp-lambda-handler`, `mark3labs/mcp-go`) hand the entry-point decision to consumers, and remote-only servers (`slackapi/slack-mcp-plugin`) skip the local-launch surface entirely.

## Configuration surface

How configuration reaches each server. Environment variables dominate the corpus by a wide margin — ~80/104 samples document env-var configuration, with the host's `mcpServers.<name>.env` block as the typical delivery channel. CLI flags are the second-most-common channel (~45/104) and frequently mirror env vars one-to-one. Beyond env-and-CLI, the long tail surfaces a much wider variety of mechanisms than the template's common-values list anticipates: `.env` files, in-tree YAML/JSON config files for tool definitions, URL query parameters for hosted services, HTTP request headers for per-request multi-tenancy, programmatic functional-options APIs for SDKs, runtime tool-call reconfiguration, OS-native config directories via `platformdirs`, and (one outlier) SQL PRAGMA calls. Precedence between channels is rarely documented; when it is, the conventional "CLI overrides env" order is the default — but `zilliztech/mcp-server-milvus`'s explicitly-inverted `.env > CLI` ordering and `qdrant/mcp-server-qdrant`'s env-only-with-CLI-deprecated stance show that the assumed precedence isn't safe to take for granted.

**Configuration-surface size distribution:**

The volume of configuration each server exposes varies by orders of magnitude:

- **Minimal-config servers** (<5 env/flag knobs) — `JackKuo666/PubMed-MCP-Server` (host-config only), `voska/hass-mcp` (`HA_URL`, `HA_TOKEN`), `shreyaskarnik/huggingface-mcp-server` (`HF_TOKEN` optional), `sajal2692/mcp-weaviate` (small env set), `ckreiling/mcp-server-docker` (`DOCKER_HOST` only), `samuelgursky/davinci-resolve-mcp` (mode flag only via wizard). Servers with single-credential or zero-config requirements.
- **Medium-config servers** (5–15 knobs) — typical for API-bridge servers (`alpacahq/alpaca-mcp-server` 3 keys, `crystaldba/postgres-mcp` URI + access-mode + transport, `sooperset/mcp-atlassian` per-Atlassian-instance creds, `redis/mcp-redis` SSL flags + URL forms). Modal cluster.
- **Large-config servers** (20+ knobs) — `microsoft/playwright-mcp` (50+ CLI flags, every flag mirrored as `PLAYWRIGHT_MCP_*` env var — corpus's largest config surface), `cyanheads/git-mcp-server` (Zod-validated transport + session + format + identity + signing + auth + logging), `mongodb-js/mongodb-mcp-server` (`MDB_MCP_*` env namespace + camelCase CLI + JSON config combined), `mukul975/cve-mcp-server` (10+ per-source API keys plus retry/timeout knobs), `github/github-mcp-server` (parallel env + flag surfaces with toolset selection), `korotovsky/slack-mcp-server` (4 token types + transport + per-tool flags), `awslabs/aws-api-mcp-server` (AWS profile + region + transport + OAuth endpoints + experimental flags). Vendor and security-focused servers anchor this bucket.

The "every CLI flag has a `PLAYWRIGHT_MCP_*` env equivalent" pattern in `microsoft/playwright-mcp` is the most-disciplined config-surface-symmetry in the corpus — most repos with both env and CLI surfaces have partial coverage, not full mirroring.

**Precedence patterns:**

Documented precedence is rare. When stated:

| Pattern | Examples |
|---|---|
| CLI overrides env (conventional) | `chroma-core/chroma-mcp` (CLI primary, env secondary, `.env` via flag), default assumed elsewhere |
| Env overrides CLI (inverted) | `zilliztech/mcp-server-milvus` (`.env` explicitly takes priority over CLI) — sample notes flag this as "inverse of the more common CLI overrides env" |
| Env-only (CLI deprecated) | `qdrant/mcp-server-qdrant` (CLI args deprecated; env-only the supported channel) |
| Multi-channel without documented precedence | most other repos with both surfaces — consumers must test or read source |

The assumed default is "CLI overrides env"; `zilliztech` and `qdrant` are the explicit deviations. Cross-cutting concern: hosts setting both env and CLI based on the assumed precedence will silently misbehave on `zilliztech` (env wins) and break on `qdrant` (CLI ignored). Worth flagging as an integration pitfall.

**Outliers and unanticipated patterns:**

- **Runtime reconfiguration** (`sandraschi/email-mcp`) — `configure_service()` is the only sample's-grade example of MCP-tool-driven reconfiguration. Most servers require a restart to pick up config changes; this server's tool-call channel sidesteps that. Already noted in Capabilities exposed; surfaces here as a config channel.
- **Persistent OS-native state** (`DiversioTeam/clickup-mcp`) — uses `platformdirs` to write API key into the user's OS-native config directory. Most other servers expect every credential to come from env/CLI/JSON each launch; this one persists between launches. The `set-api-key` subcommand provides the interactive setup flow.
- **`mongodb-js/mongodb-mcp-server`'s three-source surface** — env + CLI + JSON config file *all parallel*, with `MDB_MCP_CONFIG` env var pointing at the JSON path. Most multi-channel servers only document two; three-channel surfaces are rare and signal vendor-grade flexibility (and complexity).
- **`apollographql/apollo-mcp-server`'s config-file-driven authoring** — the YAML/TOML config file is the *primary* mechanism, with operations as the tools. Reflects the spec-driven authoring posture (cross-referenced in Notable structural choices) — config file is the unit of authoring, not env or CLI.
- **`googleapis/mcp-toolbox`'s dynamic reload** — `--disable-reload` opts out; the default is hot-reload. Sample notes flag this as a distinctive ergonomic — most servers require restart for config changes; this one watches the `tools.yaml` file. Already cross-referenced; surfaces here as a config-channel-with-runtime-update behavior.
- **`microsoft/playwright-mcp`'s 50-flag surface** — only sample with explicit "every flag has an env-var equivalent." The most-disciplined config-surface-symmetry; provides full env-or-CLI flexibility for downstream agents and host configurators.
- **`exa-labs/exa-mcp-server`'s `EXA_API_KEY` env or URL parameter** — single credential delivered through *either* env or URL. Rare dual-channel auth-key delivery; reflects the dual hosted+local stdio posture.

**Cross-section observations:**

- **System-binary servers report no runtime config surface** — `labeveryday/mcp_pdf_reader` ("environment / system-level Tesseract install; no runtime config surface documented"), `misbahsy/video-audio-mcp` ("env-level ffmpeg binary availability; no documented runtime config"). The "system-binary dependency" axis from Notable structural choices manifests here as config-surface absence — these servers' real configuration is at the OS level, not the MCP layer.
- **Container-native config patterns cluster** — kubeconfig mounts, AWS creds chain, Docker volume mounts appear together. Container-deployed servers tend to ship volume-mount-based config delivery rather than env/CLI exclusively. Cross-references the Container/packaging artifacts cluster.
- **`upstash/context7`'s CLI helper handles config** — `npx ctx7 setup` orchestrates OAuth flow and credential setup, rather than asking the user to wire env vars manually. Cross-references the wizard-pattern under Notable structural choices and the setup-subcommand under Entry point/launch.

### pitfalls observed

- **Precedence assumption is hazardous** — `zilliztech/mcp-server-milvus` inverts the conventional `CLI > env` order. Hosts that set both based on the assumed precedence will get unexpected behavior. Re-document precedence per repo.
- **`stripe/agent-toolkit`'s sample explicitly notes "exact env-var config surface vs CLI flags not extracted"** — env-var equivalents to documented `--api-key` exist but are not enumerated. Repo readers should consult source for the full set.
- **Config-file-as-primary servers** (`apollographql/apollo-mcp-server`, `googleapis/mcp-toolbox`) require a separate manifest authoring step; agents wiring these into a host config can't rely on the env-var-only mental model.
- **`.env`-precedence inversion sample is a singular outlier; `qdrant`'s env-only is similarly singular** — but together they signal that the conventional precedence shouldn't be assumed without verification.

## Authentication

How each server authenticates to the upstream service it bridges (when one exists) and where the credentials originate. The corpus splits on a ~50/25/29 spine: static API key / bearer token / personal-access-token is the dominant flow (~50/104); no-auth / not-applicable is the second-largest cluster (~25/104, covering local-file servers, public-API bridges, and "not a security boundary" reference servers); the remaining ~29/104 deploys richer auth — OAuth/OAuth2/OAuth2.1, AWS credential chain, kubeconfig delegation, multi-mode auth selectors, and one Lambda-Authorizer-offload outlier. Credentials almost universally originate from environment variables (~75/104), with smaller channels for CLI flags, `.env` files, request headers, OAuth callbacks, and OS-native credential files. The MCP spec recommends OAuth 2.1 with PKCE for HTTP-transport servers; the corpus aligns where it matters — every hosted/SaaS server that's not zero-auth ships OAuth — but local-stdio servers continue to ship static-token auth as the dominant pattern, reflecting that the host is trusted with the credential and the server doesn't see external traffic.

**Auth-flow distribution by deployment posture:**

The auth choice strongly correlates with deployment posture rather than service domain:

- **Local-stdio servers ship static API keys / PATs almost universally.** The host is trusted with the credential, and stdio servers never see external clients — auth is "carry the upstream service's credential through the env block." Roughly half the corpus.
- **Hosted/SaaS / remote-HTTP servers ship OAuth 2.0/2.1 almost universally.** The hosted endpoint must distinguish users; OAuth is the only practical flow. Every hosted-endpoint server that's not zero-auth (`getsentry/sentry-mcp`, `neondatabase/mcp-server-neon`, `slackapi/slack-mcp-plugin`, `supabase-community/supabase-mcp`, `upstash/context7`, `stripe/agent-toolkit`, `github/github-mcp-server`, `viant/mcp`) ships OAuth — strongest cross-cutting alignment with the spec's prescription.
- **No-auth servers cluster around three specific situations** — local file access (filesystem, SQLite, DuckDB), public APIs (arXiv, PubMed, AWS docs), and zero-trust browser automation (Playwright, Puppeteer with "not a security boundary" disclaimer). All three are deliberate; "no auth" is data, not omission.
- **Container/cloud-native servers reuse ambient credentials** — AWS chain, kubeconfig, GCP ADC, Docker socket. Cross-references container-mount-based config in Configuration surface.
- **Database-bridge servers reuse DB-native auth** — connection strings carry credentials directly. Cross-references the connection-string config-channel pattern.

**Outliers and unanticipated patterns:**

- **`mukul975/cve-mcp-server`'s 21 optional API keys with graceful degradation** — corpus's most-multi-credential surface. The server enables only the tools whose backing services have keys present. A graceful-degradation discipline distinct from binary auth-required vs. auth-disabled.
- **`korotovsky/slack-mcp-server`'s "stealth mode"** — uses browser cookie token instead of bot OAuth to act as an existing user without admin approval. Sample notes flag this as a privilege-minimized posture distinct from the OAuth bot-app pattern. Cross-references Notable structural choices.
- **`thenets/ghost-mcp`'s 5-min auto-renewing JWT** — server holds a 5-minute JWT and renews it automatically. Caller never sees auth lifecycle. Server-managed credential rotation is rare in the corpus (~5 samples documented something similar).
- **`spences10/mcp-turso-cloud`'s two-tier child-token generation** — the server generates short-lived per-database tokens from an org-level token with configurable permission granularity. Reduces the org-token's blast radius if a child leaks. One-of-a-kind pattern in the corpus.
- **`viant/mcp`'s OAuth2 token acquisition on 401** — client-side automatic acquisition: server returns 401 with metadata, the client discovers the protected resource, acquires a token, and retries. Sample-grade implementation of the OAuth resource metadata flow that the spec recently formalized.
- **`awslabs/mcp-lambda-handler`'s API-Gateway-Authorizer offload** — auth lives architecturally outside the server. The handler "never sees raw tokens." Demonstrates an MCP-on-FaaS pattern where auth is the platform's job, not the server's.
- **`paypal/paypal-mcp-server`'s 3-8 hour token lifecycle** — sample explicitly flags pitfall: "not clear from surface whether server refreshes automatically or expects caller to rotate." Token-rotation responsibility is unclear from README; consumers may need to read source.

**Cross-cutting source patterns:**

- **Env-var dominance is structural** — it matches the host's `mcpServers.<name>.env` block, which is the universal injection point across Claude Desktop / Claude Code / Cursor / VS Code / Cline. Any server that uses CLI flags must be wired through `args` instead, fragmenting the host config. The dominance of env-as-source is downstream of host-config conventions.
- **`.env` files are a Python convention.** Almost all `.env`-using samples are Python-based. JS/TS servers prefer raw env vars (Node has no built-in dotenv loading). The cross-language asymmetry maps to ecosystem norms.
- **Header-based credentials are emerging for multi-tenant deployments.** The two header-based samples (`lanbaoshen/mcp-jenkins`, `upstash/context7`) and `mongodb-js/mongodb-mcp-server`'s `mcp-session-id` header all turn an HTTP server into a multi-tenant surface where each request carries its own credentials. Likely to grow as hosted MCPs proliferate.
- **Browser-based OAuth has no fallback for headless agents** — every OAuth-bearing sample assumes the host can launch a browser. Headless deployment of an OAuth-flow server requires manual token capture, which several samples (`upstash/context7`, `cloudflare/mcp-server-cloudflare`'s `mcp-remote` shim) work around with setup wizards or shim tools.

### pitfalls observed

- **Token lifecycle responsibility is often unclear** — `paypal/paypal-mcp-server`'s sample explicitly flags "not clear whether server refreshes automatically or expects caller to rotate." Consumers should test refresh behavior under expiration before depending on it.
- **`zilliztech/mcp-server-milvus` `.env > CLI` precedence inversion affects credential delivery** — already flagged in Configuration surface; a host setting both will hand the env-defined credential to the server even if CLI was meant to override.
- **"No auth" is sometimes "no MCP-layer auth" but still requires upstream credentials** — `bhauman/clojure-mcp` ("no built-in authentication; optional API keys for external LLM providers"), `mahdin75/gis-mcp` ("none at MCP layer; downstream API keys via dataset-specific config"), `pathintegral-institute/mcp.science` ("server-specific API keys for specialized integrations"). The auth surface and the credential surface aren't always the same — consumers reading "no auth" should verify whether downstream APIs need keys.
- **Reference servers' "filesystem allowlist as access control" framing** is not a true auth equivalent — `modelcontextprotocol/servers`' filesystem reference uses directory allowlist as access boundary; samples flag this as an access-control mechanism, not authentication. Consumers shouldn't treat "no auth + allowlist" as substitution for credential-based authentication.
- **Multi-mode auth selectors require the user to know which mode** — `echelon-ai-labs/servicenow-mcp`'s `SERVICENOW_AUTH_TYPE`, `cyanheads/git-mcp-server`'s mode env var, `korotovsky/slack-mcp-server`'s 4-token-type matrix all require the user to pick correctly. README clarity on "when to pick which" varies; the matrix-style auth surfaces have the highest configuration-error-rate risk.

**Distinct patterns surfaced:**

- **Tenancy-as-tool-argument** (`sajal2692/mcp-weaviate`) sidesteps server-side tenancy entirely — every tool call carries a tenant ID as an argument. - **AWS-tag-driven scoping** noted in `awslabs/bedrock-kb-retrieval-mcp-server` (only KBs tagged `mcp-multirag-kb=true` are visible) — categorized under `single-user` here because it's not per-request, but it's worth flagging as a distinct boundary mechanism for future template revisions.
- **Externally-managed sessions** (`mongodb-js/mongodb-mcp-server` — `EXTERNALLY_MANAGED_SESSIONS=true` + `mcp-session-id` header) ships a hook for host-driven session management without committing to per-tenant tenancy. - **Dual shapes** are common: stdio single-user + hosted per-user OAuth (Sentry, GitHub, Stripe). The same codebase ships two tenancy postures depending on transport.

**Pitfalls observed:**

- Counts in this section are sensitive to whether you treat per-client HTTP connection multiplexing as "per-request tenancy" (the same auth and config across all clients, just multiple sockets) or as a single-user pattern. The synthesis above uses the repo's own framing; readers should re-read primary sources before depending on a specific count.
- Several "single-user" repos document per-request features (session IDs, multi-provider config selection) without claiming multi-tenancy — these are easy to over-count.

**Cross-cutting observability themes:**

- **The "not documented" plurality is a finding, not a gap.** The picker's research budget didn't always extract observability details, but the rate (~55/104) is so high that it points to README authors omitting observability rather than research-budget shortfall. Most stdio servers default to stderr per SDK convention; many README authors apparently consider that obvious enough to skip. Consumers adopting these servers should expect to read source for observability surface.
- **Compliance-driven servers ship audit logging.** `mukul975/cve-mcp-server` (security domain), `normaltusker/kotlin-mcp-server` (GDPR/HIPAA modes), `the-momentum/fhir-mcp-server` (HIPAA framing), `awslabs/mcp` (CloudTrail) — domains with regulatory pressure ship structured audit logs explicitly. Consumer domains without compliance pressure (most of the corpus) ship neither structured logs nor audit trails.
- **JSON-RPC stdout-pristine constraint is under-documented.** Only ~3 samples (`sandraschi/email-mcp`, `executeautomation/mcp-playwright`, `hannesrudolph/sqlite-explorer-fastmcp-mcp-server`) explicitly call out the "no print to stdout" discipline. Many other stdio servers logged to stderr by default, which works correctly, but the constraint isn't surfaced — agents implementing new MCP servers can break JSON-RPC framing by adding `print()` debugging. Worth elevating in template revisions or in a separate observability-patterns doc.
- **OpenTelemetry adoption is so low (~4/104) that integration-level observability across MCP servers is essentially unsolved.** `datalayer/jupyter-mcp-server`'s "OTel as core dep" is the corpus exception — most servers don't ship telemetry primitives at all, leaving consumers without distributed-tracing context for tool calls.
- **Pluggable-logger systems are rare** — `mongodb-js/mongodb-mcp-server`'s `LOGGERS` env (disk/mcp/stderr) is the only cleanly-pluggable example. Most servers hard-code their destination. Architecturally, MCP-Logging-primitive support (sending logs back to the client via the `mcp` logger) is a spec-compliant cross-cutting capability that few servers implement.
- **Hosted servers cede observability to the vendor.** `cloudflare/mcp-server-cloudflare`, `slackapi/slack-mcp-plugin`, `idosal/git-mcp`, `getsentry/sentry-mcp`'s hosted endpoint — none ship a self-hostable observability layer for their hosted variants. Consumers debugging these must use the vendor's dashboard. Cross-references hosted-vs-local axis.
- **Test/eval harnesses sometimes substitute for observability** — `getsentry/sentry-mcp` notes `pnpm test` and `pnpm eval` instead of explicit observability; `jparkerweb/mcp-sqlite` flags MCP Inspector script via `npm test`. When formal observability is absent, testing scaffolding fills the verification need.

**Outliers worth flagging:**

- **`sandraschi/email-mcp`** — separate `monitoring/` directory + web dashboard + zero-tolerance print policy. Most-comprehensive observability + monitoring surface in the corpus, with a discipline (`no print to stdout`) others don't enforce.
- **`mukul975/cve-mcp-server`'s audit log discipline** — rotating JSON file with explicit redaction of API keys and payloads. Sample-grade compliance-friendly audit trail in a corpus that mostly ships none.
- **`datalayer/jupyter-mcp-server`'s OTel-as-core-dep** — `>=1.24.0` is a *core* dependency, not optional. Sample explicitly flags this as unusual; "every installation ships observability." Cross-cutting design choice (instrument-by-default) that's rare in the corpus.
- **`mark3labs/mcp-go`'s recovery middleware** — captures tool-execution panics and surfaces them through the SDK. Operational observability built into the SDK rather than left to consumers. Cross-references the SDK-as-observability axis.
- **`microsoft/playwright-mcp`'s `--init-script` for instrumentation injection** — users can inject their own instrumentation into the browser context. Distinct from server-side logging; allows browser-level observability hooks. Tracing/video are *capability toggles*, not observability per se (sample explicitly distinguishes).

### pitfalls observed

- **Sample-budget-limited visibility is the dominant pitfall** — same pattern as Tests and CI synthesis: ~55/104 samples report "not extracted." Absence in the synthesis means absence in the README sample, not absence in the repo. A targeted research wave opening source files would resurface a richer observability picture for many repos.
- **"Standard logging" without specifics is a research-output stub, not a finding** — many samples report "Python `logging`" or "Go stderr default" as the entire observability section. These are non-statements; they tell consumers what the SDK defaults are, not what the repo configures.
- **README claims of "comprehensive logging" don't always match the surface** — `designcomputer/mysql_mcp_server` ("comprehensive logging" claim, specifics not surfaced), `twolven/mcp-server-puppeteer-py` ("Detailed error handling and logging" claimed, destination not specified). When marketing language doesn't match documented surface, consumers should verify in source.
- **Stdout-cleanliness pitfall is real but under-documented** — adding `print()` debug statements to a stdio MCP server breaks JSON-RPC framing. Three samples surface this discipline; the other 90 stdio-bearing samples likely encode the constraint in code without surfacing it. New-MCP-server authors may break stdio without warning.
- **Tracing/metrics absence is corpus-wide** — only ~4/104 samples ship anything beyond logs. Distributed-tracing context across multi-server tool chains is structurally absent from the corpus. Cross-cutting concern for consumers building tool pipelines.

**Notable testing patterns (beyond framework choice):**

- **Cassette-recording for HTTP determinism** — `geropl/linear-mcp-go` ships go-vcr with cassettes checked into `testdata/`; live test workspace `linear.app/linear-mcp-go-test` for re-recording; separate flags for re-record (`-record=true`) and write-op recording (`-recordWrites=true`). The most disciplined HTTP-stub pattern in the corpus — explicit cassette regeneration workflow rather than mocking. Already cited as exemplar in Notable structural choices and Unanticipated axes (CI/release/supply-chain hardening axis).
- **Evaluation harnesses as peer of unit tests** — `getsentry/sentry-mcp` ships `pnpm eval` (evaluations / scenario tests) alongside `pnpm test` (unit). Eval discipline as a first-class testing artifact, not buried in scripts. Also called out in Unanticipated axes.
- **Multi-phase live test plans** — `samuelgursky/davinci-resolve-mcp` ships a 5-phase suite: read-only / destructive / media / AI-ML / advanced; 319/324 methods live-tested (98.5%); 319/319 pass rate claimed. Sample-grade test discipline against a host-bound product (DaVinci Resolve) where conventional CI can't reach. The phase model — read-only first, destructive last — is itself a recurring pattern when the system-under-test is destructive.
- **AI-generated adversarial workloads** — `crystaldba/postgres-mcp`'s README notes use of "AI-generated adversarial workloads" — an LLM-generated test corpus pushing edge cases beyond hand-authored tests. One sample, but worth flagging as an emerging discipline in this corpus.
- **Pyramid testing layered explicitly** — `neondatabase/mcp-server-neon` documents a four-layer test pyramid: unit (pure logic) / integration (tool contracts) / E2E (MCP protocol with real clients) / web E2E (Playwright + ephemeral DB). The MCP-protocol-with-real-clients layer is the rare middle layer most repos skip — testing that real client behavior matches the server's MCP contract.
- **Live integration gating via flag** — `awslabs/aws-documentation-mcp-server`'s pytest config gates live-AWS tests behind `--run-live`. The off-by-default-but-callable pattern lets fast unit tests gate CI while the expensive live tests run on demand. Pattern parallels the `--run-agent` discipline this project's own test suite uses for agent-spawning tests; both surface "expensive integration is opt-in, not always-on."
- **Conformance test as published artifact** — `apollographql/apollo-mcp-server`'s `e2e/mcp-server-tester` is an end-to-end MCP-protocol conformance harness intended to be reused. `modelcontextprotocol/kotlin-sdk` ships `kotlin-sdk-testing` as a purpose-built test module with integration + conformance tests + Knit properties for code-snippet testing. Both project conformance to MCP as a testable property, not just unit-test coverage.
- **Test-runtime dep mis-declaration** — `misbahsy/video-audio-mcp` declares `pytest` as a *runtime* dep (not dev) — sample explicitly flags as unusual. Not a corpus-wide pattern, but a flag for downstream consumers.
- **Per-server vs monorepo test infrastructure** — `modelcontextprotocol/servers` sample notes "each server is small enough that test infrastructure is minimal/per-package"; `awslabs/mcp` ships per-server tests with codecov badge for cross-server coverage. Monorepos handle test infrastructure at one of two scopes — per-server (when servers are small enough), or central (when shared scaffolding is meaningful). Neither is dominant.

**Adjacent quality-tooling for tests:**

- **Coverage tooling** — `pytest-cov` is the dominant Python coverage tool (~10 explicit mentions); `--cov --cov-branch` for branch coverage in `awslabs/aws-documentation-mcp-server`; `npm run test:coverage` (`makenotion`); codecov integration in `apollographql/apollo-mcp-server`, `awslabs/mcp`, `lanbaoshen/mcp-jenkins`, `redis/mcp-redis`.
- **Multi-Python CI matrix** — `sandraschi/email-mcp` explicitly tests 3.10/3.11/3.12. Other Python repos likely do this in CI but the matrix wasn't surfaced for many. Worth flagging as an explicit Python-version test-coverage discipline some repos invest in.
- **Type-check as test** — `cyanheads/perplexity-mcp-server` has `npm test` run TypeScript noEmit type checks (no functional tests, just type-check). Pattern when "test" is repurposed as "static analysis"; not common but worth noting.
- **Test-file location split** — most pytest repos use `tests/` (singular); a few use `/test` (`teaguesterling/duckdb_mcp`); one (`marlonluo2018/pandas-mcp-server`) places `test_*.py` files at repo root rather than under `tests/`. Convention is heavily skewed toward `tests/` directory.

**Pitfalls observed:**

- **Sample-budget-limited visibility** — same caveat as CI: ~39/104 samples report "not extracted within budget" for tests. Absence in this synthesis is sample-coverage absence, not corpus absence.
- **"Test directory present" without framework signal** is the modal sample state — visiting the repo would surface the framework, but research budget didn't go that deep for ~25 samples.
- **MCP Inspector as testing-surrogate** isn't a substitute for unit tests — it's a developer ergonomic for stepping through messages. Repos that flag MCP Inspector as their "test" surface (e.g. `jparkerweb/mcp-sqlite`, `v-3/discordmcp`) typically lack formal test discipline.

**Cross-cutting patterns:**

- **Two-variant Dockerfile** — `mahdin75/gis-mcp` ships `Dockerfile` (prod) and `Dockerfile.local` (dev); `elastic/mcp-server-elasticsearch` ships `Dockerfile` (main) and `Dockerfile-8000` (alternative port). Per-environment Dockerfile splits are uncommon (2/54 Dockerfile-bearing repos) — most ship a single multi-purpose Dockerfile.
- **Per-server Dockerfile in monorepo** — `modelcontextprotocol/servers` ships per-server Dockerfile (`src/filesystem/Dockerfile`, `src/git/Dockerfile`, `src/fetch/Dockerfile`) with images published as `mcp/<server-name>`; `awslabs/mcp` ships per-server Dockerfile across 40+ servers; `FuzzingLabs/mcp-security-hub` ships per-tool Dockerfile + `Dockerfile.template` as scaffold for new tools. Monorepo-of-servers pattern carries dockerfile-per-server, not a shared image.
- **Container-as-primary distribution** — `voska/hass-mcp` (Docker Hub primary, README leads with `docker pull`), `elastic/mcp-server-elasticsearch` (Docker container only — no PyPI/npm), `alexei-led/k8s-mcp-server` (ghcr.io is the canonical distribution), `github/github-mcp-server` (`docker run` is the canonical install path, GHCR primary). When Docker is the primary, samples explicitly flag this — pattern is intentional, not a fallback.
- **Container as test-stack rather than deployment** — `thenets/ghost-mcp`'s docker-compose ships full Ghost 5.x + MySQL 8.0 — for end-to-end local testing, not server deployment. Sample explicitly flags this distinction. `mcp-clickhouse`'s `test-services/` Compose serves the same purpose. Dev-time-only orchestration is a recurring use-case for compose, separate from deployment use.
- **Container-deployment-as-counterproductive** — `samuelgursky/davinci-resolve-mcp` explicitly notes "Docker would be counterproductive since the server must run on the host with Resolve." When the server depends on host-bound resources (GPU, system tools, OS-native APIs), containerization is structurally inappropriate. Recurring pattern with `bhauman/clojure-mcp` (REPL-driven, JVM/Clojure host environment), `labeveryday/mcp_pdf_reader` (Tesseract OCR system binary), `misbahsy/video-audio-mcp` (ffmpeg). The "system-binary dependency" axis from Notable structural choices manifests as container-absence here.
- **Hosted-equivalent-replaces-container** — `slackapi/slack-mcp-plugin` ("not applicable — remote service"), `cloudflare/mcp-server-cloudflare` ("N/A — servers run as Workers, not containers"), `supabase-community/supabase-mcp` ("Managed cloud endpoint reduces need for containerization"), `idosal/git-mcp` ("no Dockerfile; Cloudflare Workers cloud-native deployment"), `neondatabase/mcp-server-neon` ("Vercel-hosted deployment model"). Hosted-service samples uniformly explain *why* there's no Docker artifact — the cloud-native runtime is the deployment unit.
- **Crystaldba's host-network shim** — `crystaldba/postgres-mcp`'s Dockerfile auto-remaps host address (localhost → host.docker.internal on macOS/Windows, 172.17.0.1 on Linux). One-of-a-kind in-container UX detail: rewrites the user's connection string to make `localhost` work across container-host network topologies. Worth flagging as a portability pattern.

- **Single-file scripts persist** — 5–6 samples ship a single `.py` at repo root rather than a packaged module. Most predate FastMCP 2.x. `twolven/mcp-server-puppeteer-py` even pairs `puppeteer.py` with `requirements.txt` (no `pyproject.toml`). Reveals MCP server authoring's low floor: a single script + decorator + transport binding suffices.
- **Polylith adoption is unique to one Clojure server** (`hugoduncan/mcp-clj`) — Polylith is a Clojure-community architectural pattern; no other ecosystem in the corpus uses it. Shows language-ecosystem conventions surface in repo layout.
- **Config-only repository** — `slackapi/slack-mcp-plugin` ships only `.claude-plugin/`, `.cursor-plugin/`, and `commands/skills/` — no server source. The "server" is hosted at `mcp.slack.com/mcp` and the repo is the *configuration* shipped to host plugin systems. A new layout class: "host-config-as-product."
- **Mixed parallel subprojects** — `isaaccorley/planetary-computer-mcp`'s parallel `vscode-extension/` TS subproject under a Python repo and `sandraschi/email-mcp`'s `webapp/` dashboard alongside the server. These read as single-repo monoliths rather than monorepos because there's no workspace mechanism — they share a tree without sharing a build system.

**Cross-language layout convergence.** Despite different ecosystems, the dominant shape (single package + tests + one config file) is consistent. Go's `cmd/` + `pkg/` and Python's `src/<pkg>/` and TS's `src/` are different naming for the same idea — code in a directory, tests alongside, manifest at root. Where layouts diverge meaningfully — Polylith, Gradle multi-module, Cargo workspaces — it's because the language community has its own conventions.

## Notable structural choices

Freeform synthesis across all 104 samples — every sample populated this section, so the denominator is effectively the full corpus. The patterns below cluster the most-cited structural choices that surfaced in three or more samples; one-off curiosities are kept brief at the end. Where a pattern duplicates content already synthesized in a labeled section (Capabilities exposed, Multi-tenancy), this section captures the *cross-cutting structural framing* — what these specific repos chose to highlight as distinctive about themselves — rather than re-reporting the per-axis distributions.

**Recurring structural patterns:**

- **Read-only / safety gating as a first-class flag** (~25 samples) — `geropl/linear-mcp-go` (`--write-access`), `PagerDuty/pagerduty-mcp-server` (`--enable-write-tools`), `severity1/terraform-cloud-mcp` (`READ_ONLY_TOOLS` + `ENABLE_DELETE_TOOLS`), `feiskyer/mcp-kubernetes-server` (four-way `--disable-{kubectl,helm,write,delete}`), `mongodb-js/mongodb-mcp-server` (`--readOnly` + `--indexCheck` + `--dryRun`), `microsoft/playwright-mcp` (`--caps`), `github/github-mcp-server` (`--read-only` + `--lockdown-mode`), `crystaldba/postgres-mcp` (pglast SQL parsing), `ClickHouse/mcp-clickhouse` (`WRITE_ACCESS` + `DROP`), `rust-mcp-stack/rust-mcp-filesystem` (read-only default + tool-disable), `alpacahq/alpaca-mcp-server` (paper-trade default), and ~12 more. The framing varies — single read-only toggle, two-axis read-only-plus-delete, per-verb fan-out, per-tool gating — but the underlying choice (mutating capability is opt-in, not default) is the most-cited cross-cutting design discipline in the corpus.

- **Tool consolidation / capability gating to manage surface size** (~15 samples) — `HenkDz/postgresql-mcp-server` (46 atomic → 17 meta-tools, `tools.json` per-tool enable), `paypal/paypal-mcp-server` (`--tools` opt-in), `microsoft/playwright-mcp` (`--caps=vision/pdf/testing`), `samuelgursky/davinci-resolve-mcp` (compound 27 vs full 342 dual-mode), `github/github-mcp-server` (toolset flags + dynamic toolsets), `opensearch-project/opensearch-mcp-server-py` (category env-var lists), `neondatabase/mcp-server-neon` (URL-param category), `getsentry/sentry-mcp` (skills disable), `supabase-community/supabase-mcp` (`features` query param), `utensils/mcp-nixos` (deliberate two-tool collapse). Surface-size pressure is real: the corpus's largest servers (253, 342, 100+ tools) all ship gating mechanisms in response.

- **Dual / triple-transport in one binary, selected at launch** (~12 samples) — `AlwaysSany/deepl-fastmcp-python-server` (stdio + SSE + Streamable HTTP), `the-momentum/fhir-mcp-server` (stdio + http + https env-var-switched), `ahmedmustahid/postgres-mcp-server` (HTTP streamable + stdio subcommand), `executeautomation/mcp-playwright` (`--port` switches stdio↔HTTP), `docker/hub-mcp` (CLI flag with explicit default), `chroma-core/chroma-mcp` (4 backing-store modes via flags), `hugoduncan/mcp-clj` (stdio + SSE + in-memory), `cyanheads/perplexity-mcp-server` (stdio/HTTP via Hono), `metoro-io/mcp-golang` (stdio + HTTP + Gin). One-binary-many-transports is dominant over `echelon-ai-labs/servicenow-mcp`'s split-console-script approach.

- **Vendor-published "first-party" servers as a recurring category** (~12 samples) — `microsoft/playwright-mcp`, `github/github-mcp-server`, `alpacahq/alpaca-mcp-server`, `paypal/paypal-mcp-server`, `cloudflare/mcp-server-cloudflare`, `getsentry/sentry-mcp`, `stripe/agent-toolkit`, `slackapi/slack-mcp-plugin`, `makenotion/notion-mcp-server`, `supabase-community/supabase-mcp` (community-with-vendor-blessing), `redis/mcp-redis`, `mongodb-js/mongodb-mcp-server`, `elastic/mcp-server-elasticsearch`, `googleapis/mcp-toolbox`. Vendor framing brings credibility but doesn't predict adoption (`paypal/paypal-mcp-server` at 9 stars, `sandraschi/email-mcp` first-party at 1 star vs. unofficial `GLips/Figma-Context-MCP` at 14.4k). The community-canonical-without-first-party pattern (`sooperset/mcp-atlassian` for Atlassian, `samuelgursky/davinci-resolve-mcp` for Resolve, `executeautomation/mcp-playwright` competing with Microsoft's own) recurs in 5+ samples.

- **Hosted/SaaS + local-stdio dual deployment from one codebase** (~8 samples) — `getsentry/sentry-mcp` (`mcp.sentry.dev` + local stdio, `SENTRY_HOST` pivot), `github/github-mcp-server` (hosted endpoint + binary), `stripe/agent-toolkit` (same), `cloudflare/mcp-server-cloudflare` (Workers-only, no local at all — opposite extreme), `idosal/git-mcp` (`gitmcp.io` SaaS), `slackapi/slack-mcp-plugin` (remote-only with config-only repo), `supabase-community/supabase-mcp` (hosted-first), `neondatabase/mcp-server-neon` (remote-first, OAuth primary). The dual posture creates a distribution-strategy axis distinct from local-only servers.

- **Multi-host plugin/skill wrappers shipped in-repo** (~8 samples) — `getsentry/sentry-mcp` (`.claude-plugin/`), `stripe/agent-toolkit` (`.claude-plugin/` + `.cursor-plugin/`), `slackapi/slack-mcp-plugin` (commands/ + skills/), `blazickjp/arxiv-mcp-server` (`skills/` + `.codex-plugin/`), `openags/paper-search-mcp` (`claude-code/` skill files), `neondatabase/mcp-server-neon` (`.claude/skills/`), `exa-labs/exa-mcp-server` (`.claude-plugin/plugin.json` HTTP variant), `motherduckdb/mcp-server-motherduck`, `upstash/context7` (`.claude-plugin/marketplace.json`). See dedicated section for distribution.

- **Docker-first / container-only distribution** (~10 samples) — `FuzzingLabs/mcp-security-hub` (no PyPI, hardened multi-server), `elastic/mcp-server-elasticsearch` (Docker only), `voska/hass-mcp` (Docker primary, README leads with `docker pull`), `alexei-led/k8s-mcp-server` (README steers toward container), `github/github-mcp-server` (GHCR primary), `korotovsky/slack-mcp-server` (compose variants), `cyanheads/perplexity-mcp-server` (multi-stage), `rust-mcp-stack/rust-mcp-filesystem` (multi-stage alpine non-root), `baryhuang/mcp-server-aws-resources-python` (multi-arch incl. arm/v7), `HenkDz/postgresql-mcp-server` (Docker alongside npm), `duolingo/slack-mcp` (containerization-first). Container-as-primary signals operational deployment over local stdio dev workflows.

Declarative-from-spec contrasts with code-defined hand-authored tools as a fundamental authoring axis.

- **Encrypted credential / token-rotation in-server** (~5 samples) — `the-momentum/fhir-mcp-server` (master-key encrypted credential vault, HIPAA framing), `thenets/ghost-mcp` (JWT auto-renewal every 5 min), `spences10/mcp-turso-cloud` (auto-generates short-lived child tokens), `mongodb-js/mongodb-mcp-server` (temporary-user TTL), `viant/mcp` (OAuth2 refresh on 401). - **Bundled prompts / skills / "prompt routines" as a shipped artifact** (~5 samples) — `pragmar/mcp-server-webcrawl` ("prompt routines" as Markdown), `awslabs/mcp` ("agent SOPs" preview-tier aggregated server), `getsentry/sentry-mcp` (skills as togglable abstraction in `.agents/skills/`), `ckreiling/mcp-server-docker` (docker-compose workflow prompts), `shreyaskarnik/huggingface-mcp-server` (`compare-models`, `summarize-paper` prompts). Crosses with Capabilities exposed but framed here as a content-shipping decision.

- **Single-binary management CLI alongside server** (~4 samples) — `DiversioTeam/clickup-mcp` (`set-api-key`, `check-config`, `test-connection` subcommands), `geropl/linear-mcp-go` (`setup` subcommand), `pragmar/mcp-server-webcrawl` (`--interactive` terminal mode), `openags/paper-search-mcp` (dual-binary: server + CLI sharing core lib). The corpus contains SDKs and frameworks in addition to actual servers — these are referenced as "the canonical SDK X" by other samples and are evidence of the de-facto language-ecosystem tooling.

- **In-server LLM / embedded RAG pipeline** (~3 samples) — `getsentry/sentry-mcp` (`EMBEDDED_AGENT_PROVIDER`), `the-momentum/fhir-mcp-server` (llama-index + huggingface + pinecone in-server), `redis/mcp-redis` (in-server doc-search via separate HTTP endpoint). ### Notable Python-specific choices

Idiosyncrasies, dependency-set quirks, and cross-cutting Python-ecosystem postures observed across the 62 Python-carrying repos. Many are already cited in cross-section synthesis (Notable structural choices, Unanticipated axes); this section captures the *Python-stack-specific* framing.

**Python ecosystem patterns observed:**

- **`uv` adoption is near-monocultural** — across the 62 Python repos, ~40 explicitly cite `uv` / `uvx` / `uv sync` / `uv tool install` workflows. The `uv` tool collapses install + run into one host-config-substitutable string and is the Python-ecosystem analogue to `npx -y` in the JS ecosystem. Holdouts (pip-only, pipx-only, plain venv, custom installers) are small in count but deliberate where they exist (`pragmar/mcp-server-webcrawl` "positioned for plain Python users rather than uv-native ecosystem").
- **`hatchling.build` is the dominant build backend** (~25 explicit; corpus-modal). `setuptools.build_meta` (~4) is contrarian; `uv_build` (`redis/mcp-redis`, `the-momentum/fhir-mcp-server`) is leading-edge; `poetry-core` (`PagerDuty/pagerduty-mcp-server`) is one sample.
- **PEP 735 `[dependency-groups]`** — `redis/mcp-redis` is the corpus's lone sample using the modern dependency-groups syntax (separate `dev` and `test` groups). Most repos still use `[project.optional-dependencies]` extras (`[dev]`, `[test]`).
- **`pydantic-settings` for typed-config pattern** — `DiversioTeam/clickup-mcp`, `the-momentum/fhir-mcp-server`, `awslabs/aws-api-mcp-server` use pydantic-settings for env+file config loading. Adoption is low but emergent — most repos still load env vars directly.
- **Dependency-set quirks worth flagging** — already cataloged in Notable structural choices, recapped here:
    - `awslabs/aws-api-mcp-server` pinning `awscli==1.44.81` exact (a CLI tool distributed as a Python dependency)
    - `qdrant/mcp-server-qdrant` Pydantic range `>=2.10.6,<2.12.0` (FastMCP compat narrow)
    - `mahdin75/gis-mcp` `fastmcp == 2.13.1` exact pin
    - `thenets/ghost-mcp` FastMCP 2.12.3 exact pin
    - `awslabs/openapi-mcp-server` 0.9223372036854775807.* sentinel version (int64-max release placeholder)
    - `awslabs/aws-api-mcp-server` and `jbeno/cursor-notebook-mcp` carrying both `mcp` and `fastmcp` (migration shim)
- **`.python-version` (pyenv-style) without uv-native layout** — `JackKuo666/PubMed-MCP-Server`, `chroma-core/chroma-mcp` (likely), `ckreiling/mcp-server-docker`, `isaaccorley/planetary-computer-mcp`, `labeveryday/mcp_pdf_reader`, `sajal2692/mcp-weaviate`, `shreyaskarnik/huggingface-mcp-server`. Common as a bridge between modern Python tooling and older pip workflows.
- **Module-name divergence from package name** — multiple repos ship a module name that doesn't match repo or package name. `the-momentum/fhir-mcp-server`'s `module-name = "app"` (uv_build), `voska/hass-mcp` (module `app`), `duolingo/slack-mcp` (top-level `main` module, no package). Sample notes for all flag this as unusual; consumers searching for the package internals can't infer module path from repo name.

**Distribution-pattern Python-specific choices:**

- **Namespace-prefixed PyPI packages** — `awslabs/mcp` uses `awslabs.<service>-mcp-server` (40+ packages with dotted names enabled by quoted `[project.scripts]` entries). `pathintegral-institute/mcp.science` uses single `mcp-science` package with subcommand dispatch ("Dispatcher-style monorepo where a single PyPI package routes to multiple servers via CLI subcommand — unique in the sample").
- **MCPB bundle distribution** (`.mcpb`) — Python-ecosystem-specific packaging path for Claude Desktop drag-and-drop. `motherduckdb/mcp-server-motherduck` (with `.mcpbignore`), `sandraschi/email-mcp` (MCPB-first; mixed Python + Rust packaging via `Cargo.toml` for MCPB signing). Adoption is low (2/62) but distinctive.
- **Cross-language distribution shims** — `rohitg00/kubectl-mcp-server` publishes Python to *both* PyPI and npm (the npm package wraps the Python install for hosts that prefer `npx`). `googleapis/mcp-toolbox` (Go-primary; out of Python subset) inverts this with an npm wrapper around a Go binary.
- **Source-only distribution** — `JackKuo666/PubMed-MCP-Server`, `cyanheads/perplexity-mcp-server` (TS), `duolingo/slack-mcp`, `echelon-ai-labs/servicenow-mcp`, `hannesrudolph/sqlite-explorer-fastmcp-mcp-server`, `isaaccorley/planetary-computer-mcp`, `labeveryday/mcp_pdf_reader`, `marlonluo2018/pandas-mcp-server`, `misbahsy/video-audio-mcp`, `mukul975/cve-mcp-server`, `normaltusker/kotlin-mcp-server`, `reminia/zendesk-mcp-server`, `samuelgursky/davinci-resolve-mcp`, `shibuiwilliam/mcp-server-scikit-learn`, `the-momentum/fhir-mcp-server`, `twolven/mcp-server-puppeteer-py`. ~12 Python repos in the source-only cluster (cross-references the cross-section "developer-mode-as-release" cluster).

**Optional-extras patterns:**

- **Extra-per-library pattern** — `mahdin75/gis-mcp` exposes opt-in fan-out so users install only the GIS toolchain they need. `jlowin/fastmcp` ships very broad optional-deps surface (`anthropic`, `azure`, `gemini`, `openai`, `apps`, `code-mode`, `tasks` — each opt-in to avoid bloat). `kubectl-mcp-server[ui]` gates the UI extra. `awslabs/openapi-mcp-server[all]` and `[prometheus]` extras.

- **Optional-deps groups taxonomy** — `datalayer/earthdata-mcp-server` ships clean `[test]`, `[lint]` (mdformat + ruff), `[typing]` (mypy) groups. Sample notes "clean PEP 621 optional-deps taxonomy."

**Single-file / no-pyproject anomalies:**

**What the gap distribution reveals about research methodology:**

- Single-fetch README extraction surfaces ~80% of corpus structure but systematically misses repo-state details (last commit, lock file presence, pyproject specifics) that require a second read
- Sample-grade extraction is sufficient for *pattern* analysis (which transports, which SDKs, which distribution channels) but insufficient for *operational* analysis (test coverage breakdown, exact version pins, observability config)
- Future research waves that target gap categories should batch fetches: a single second-pass that reads `pyproject.toml`, `package.json`, `.github/workflows/*.yml`, `LICENSE` per repo would resolve ~60% of the gaps above
- `slackapi/slack-mcp-plugin`'s "config-only repo" reveals one true gap: the actual server is a remote service whose surface isn't visible from the repo. Gaps here are not extraction-budget limits but the repo's intentional opacity
