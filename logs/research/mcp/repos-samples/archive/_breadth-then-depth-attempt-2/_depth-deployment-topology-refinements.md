# Depth Pass Refinements — Sample > Deployment topology

Per-role cross-corpus refinement proposals from inspecting every sample's content under this role.

## Description sharpenings

> Format: `<role-chain> > <path>` — what the existing description misses; cross-corpus evidence; sharpened text suggestion

**Sample > Deployment topology (role-level)** — The role description ("the runtime substrate the server is designed to run inside, and the shape of where the server actually runs in production. Cuts across distribution + transport but is its own concern") is accurate but does not establish a clean boundary against the two adjacent roles flagged by the Container artifacts depth pass: `Container artifacts` (in-tree files that build the artifact) and `Distribution channel` (how end users obtain a runnable artifact). The current text gestures at "cuts across distribution + transport" without naming what stays here. Cross-corpus visibility shows three substrate-replaces-container facts (Cloudflare Workers, Vercel, Lambda zip / Azure deploy artifacts) currently filed under `Container artifacts` that the Container artifacts depth report explicitly proposes moving here — meaning the role's effective scope is wider than its prose suggests once those moves land.

Sharpened framing — *"Where the running server lives in production — the substrate that hosts the running process, regardless of how the artifact got there. Boundary against Container artifacts: that role tracks in-tree files (Dockerfile shape, compose layouts, devcontainer config); this role tracks runtime substrates (host machine, container engine, edge runtime, Lambda + API Gateway, REPL, vendor-operated SaaS). Boundary against Distribution channel: that role tracks the publication form (PyPI, Docker registry, Smithery); this role tracks where the published thing actually runs. The same Docker image fact splits across all three roles: Dockerfile in tree (Container artifacts), `docker pull` from registry (Distribution channel), `docker run` on the host (Deployment topology — Containerized local process)."*

**Sample > Deployment topology > Local stdio process per session** — Description accurate, supporting evidence (4 samples) is uniform: stdio child of the host. None of the supporting samples surface anything beyond the basic shape. The description's qualifier *"Appropriate for single-user, local-data, or per-user-credentialed workloads"* is reasonable but unsupported by any sample's prose — it's an inferred constraint. Adoption count is 4, but the path describes the *default* shape of the entire stdio half of the corpus; most samples that don't have a `Deployment topology` section at all are implicitly here. Worth flagging: the role's coverage is undercount by construction, since most stdio servers don't bother to write a Deployment topology section.

Sharpened text suggestion — keep as-is on substance; add a sentence on the implicit-coverage point: *"This is the default shape implied by every stdio-transport sample even when the sample does not write a Deployment topology section. Adoption count understates the real prevalence — explicit Deployment topology entries cluster on samples that have something non-default to say (a hosted variant, an HTTP variant, a containerized variant)."*

**Sample > Deployment topology > Containerized local process** — Description accurate. Cross-corpus evidence (3 samples — FuzzingLabs, github, googleapis) shows a meaningful sub-axis the description doesn't surface: container-as-default (FuzzingLabs `docker run`, github "canonical local-launch path") vs container-as-alternative (googleapis "Docker variant supports containerized local runs"). Two distinct postures, both legitimate, but they communicate different things to a reader scanning the corpus.

Also, the description's phrasing *"transparent execution wrapper around the same stdio loop"* is true for FuzzingLabs and github but assumes stdio mode — googleapis is HTTP-mode in the same containerized form (`http://localhost:5000`). Containerized local process is not exclusively stdio; the wrapper-of-stdio framing is a stdio-default assumption that doesn't hold across the corpus.

Sharpened text suggestion — *"Host launches `docker run` as the server invocation; the container is an execution wrapper around the server process (typically the same stdio loop, occasionally an HTTP listener bound to localhost). Two postures appear: container-as-default (README leads with `docker run` even where source builds exist) and container-as-alternative (a Docker option alongside language-native install). Appropriate when language runtimes can't be assumed on the host, when bundled native deps make installation painful, or when the project standardizes on container-only distribution."*

**Sample > Deployment topology > Hosted SaaS endpoint** — Description accurate. Cross-corpus evidence (6 samples) sharpens two underplayed facts:

- *Multi-tenant by construction* — every supporting sample either explicitly says multi-tenant (neondatabase "multi-tenant service running on Vercel") or is structurally so (exa-labs, getsentry, github, idosal, supabase all serve all customers from one URL). The description doesn't connect Hosted SaaS endpoint to the multi-tenancy implications it forces. Cross-role: see `Multi-tenancy > Per-user / per-workspace via OAuth` and `Stateless HTTP for shared deployment`.
- *Coexistence with self-host is the dominant posture, not the exception* — the current description hedges *"Often co-exists with a local stdio mode for self-hosted variants."* Cross-corpus, it's not "often" — it's 4 of 6 (getsentry hosts and ships local; github hosts and ships local stdio + Docker; idosal hosts and offers self-host; supabase hosts and offers self-host npm). Only exa-labs and neondatabase are hosted-without-self-host. Pattern is the rule, not the exception.

Sharpened text suggestion — *"The maintainer operates a single (or replicated) deployment users connect to. Multi-tenancy is forced by the substrate — one URL serves all customers, with per-user scoping via OAuth or bearer tokens (cross-role: Multi-tenancy). For most samples this coexists with a self-hosted local variant — same code, two deployment shapes, with the SaaS reducing setup friction and the local variant covering security-sensitive workloads. Pure-hosted-only samples are the minority. Appropriate when the upstream resource is shared (public data, cloud APIs the maintainer brokers) or when zero-install ergonomics matter enough that self-host is an opt-in alternative."*

**Sample > Deployment topology > Self-hosted HTTP server** — Description accurate. Cross-corpus evidence (4 samples — cyanheads/git-mcp-server, duolingo/slack-mcp, googleapis/mcp-toolbox, supabase-community) sharpens one structural fact: 2 of 4 (supabase, cyanheads transport-flexible) are *the same code as the Hosted SaaS variant* — operator runs the SaaS code in their own perimeter. The other 2 (duolingo, googleapis) are *self-host-only* — no hosted SaaS variant exists, the operator self-hosts because that is the only deployment shape. The current description names the same-code-as-SaaS framing only ("Same code as the SaaS variant in some products") and doesn't acknowledge the self-host-only cluster.

Sharpened text suggestion — *"Operators deploy the server as a long-running HTTP service inside their own infrastructure. Two motivations cluster across the corpus: (1) self-host-as-alternative-to-SaaS — same code as a Hosted SaaS variant, deployed inside the operator's perimeter for compliance / data-residency reasons; (2) self-host-only — no SaaS variant exists, HTTP self-host is the project's only deployment shape (forced by transport choice, e.g., when OAuth 2.1 makes stdio impossible). Appropriate when the operator wants a long-running HTTP service inside their own perimeter, or when the transport choice rules out stdio."*

**Sample > Deployment topology > Edge / serverless deployment (Cloudflare Workers, V8 isolate)** — Description accurate. Cross-corpus evidence (2 samples — cloudflare, idosal) shows the path is genuinely about Cloudflare Workers specifically, but the path's parenthetical "(Cloudflare Workers, V8 isolate)" makes it look platform-restricted when in principle other V8-isolate edge runtimes (Vercel Edge Functions, Deno Deploy) could fit. Neither supporting sample uses anything other than Cloudflare Workers. The path naming is honest about the substrate, but reads as if the "edge / serverless" abstraction has more breadth in evidence than it does. Cross-role: Container artifacts > Cloudflare Workers config (3 samples — same domain, one extra: cyanheads has Wrangler config without filing a Deployment topology entry for it).

Sharpened text addition — *"Across the corpus this path is exclusively Cloudflare Workers; the broader 'edge / V8 isolate' framing accurately describes the substrate class but no sample exhibits non-Cloudflare V8-edge deployment."* Also: cyanheads/git-mcp-server's Container artifacts entry says Wrangler is "an additional deploy target alongside the Dockerfile" — this is a deployment-topology fact (where the running server can live) but is filed as a container-artifact fact. See *Mis-placed samples* for the cross-bleeding pattern.

**Sample > Deployment topology > Serverless (Lambda + API Gateway)** — Description accurate; 1 sample (awslabs/mcp-lambda-handler). Description thoroughly captures the substrate's constraints (statelessness, cold-start, externalized session state). Cross-role pointer is missing: this path is the deployment-topology view of the same fact captured at `Distribution channel > Lambda deployment package`, `Container artifacts > No container artifacts (substrate replaces container)`, `Transport > HTTP via API Gateway in front of Lambda`, `Multi-tenancy > Per-request tenancy with externalized session state`, and `Observability > CloudWatch via Lambda`. The Lambda story splits across 6+ roles for a single sample — worth a cross-role linkage callout.

Sharpened text addition — *"Cross-role: this path co-occurs across Distribution channel (Lambda deployment package), Container artifacts (No container artifacts — substrate replaces container), Transport (HTTP via API Gateway in front of Lambda), Multi-tenancy (Per-request tenancy with externalized session state), and Observability (CloudWatch via Lambda). The Lambda story splits across multiple roles by construction; this path is the runtime-substrate view."*

**Sample > Deployment topology > REPL-resident** — Description accurate; 1 sample (bhauman/clojure-mcp). The supporting evidence ("Server code runs inside a long-lived REPL process; the host connects to the REPL. Native Clojure-ecosystem deployment shape.") matches the consolidated almost verbatim. Description's framing *"Appropriate only when the target ecosystem (Clojure / nREPL) already has REPL-driven development as the dominant idiom"* is accurate and well-grounded. Sample count is too small to reveal sub-axes. No sharpening needed.

**Sample > Deployment topology > Per-user local process (artifact = binary)** — Adoption count is 0; the consolidated lists this path with no supporting samples. The description ("artifact is the binary that runs as a subprocess of the host on the user's laptop. No separate deployment story exists; install equals deploy.") describes a coherent posture but no sample's `## Deployment topology` section maps to it. The shape it describes (compiled-binary stdio servers — github/github-mcp-server, googleapis, rust-mcp-stack, geropl, apollographql) is real and present in the corpus, but those samples either filed their deployment topology under `Local stdio process per session` (github did; the binary nature is implicit) or didn't write a Deployment topology section at all. The path is structurally real but is a categorization slot that the sample-side prose never reaches for. See *Cross-corpus observations* for the implication.

**Sample > Deployment topology > Published container image (artifact = image)** — Description accurate; 1 sample (elastic). Cross-corpus evidence makes clear this path's distinction from `Containerized local process` and from `Hosted SaaS endpoint` — *the deployable thing is the image, not a running endpoint*. Elastic's framing ("EC2, ECS, EKS deployment targets called out in README; the unit of deployment is the published container image at Elastic's vendor registry") names the operator's deployment substrate (their own EC2/ECS/EKS), with the image as the unit. This is structurally distinct from `Self-hosted HTTP server` (which assumes the operator picked a process-supervisor substrate) — Published-container-image leaves substrate choice to the operator and ships only the image.

The current cross-role pointer ("see Distribution channel — Docker image") is correct but underplays the structural overlap: every Published-container-image sample is also under Distribution > Docker / OCI image, and the Container artifacts depth report flagged the same overlap with `Container artifacts > Published Docker image`. The artifact-vs-distribution-vs-deployment trichotomy collapses to one fact at the registry-publication level. The thing that distinguishes `Deployment topology > Published container image (artifact = image)` from `Distribution channel > Docker / OCI image` is *the operator-runs-it claim* — the README treats the image as the unit of production deployment, not just the unit of distribution. Worth surfacing in the description.

Sharpened text suggestion — *"Pre-built image at a known registry, with the README explicitly framing operator-side deployment targets (EC2, ECS, EKS, AWS Marketplace) — the unit of production deployment is the image. Distinct from `Containerized local process` (image runs on user's machine), from `Hosted SaaS endpoint` (maintainer operates the runtime), and from `Distribution channel > Docker image` (registry-publication fact). What this path uniquely captures: the README presents the project as deployable infrastructure rather than per-user installs. Cross-role: Distribution channel > Docker / OCI image (where the image is published) and Container artifacts > Published Docker image (in-tree publication pipeline)."*

## Cross-corpus observations

> Patterns visible only with full role visibility — surface even if not actionable now

**Deployment topology is structurally the destination for substrate-replaces-container migration proposed by the Container artifacts depth pass.** The Container artifacts depth report proposes moving Vercel deployment config, Cloudflare Workers config, and Azure deployment artifacts out of Container artifacts and into Deployment topology. From the Deployment topology side, those moves are absorbable but uneven: Vercel maps cleanly to Hosted SaaS endpoint (already where both Vercel samples file); Workers maps cleanly to Edge / serverless deployment (already where 2 of 3 Workers samples file; cyanheads is the third, currently only filed under Self-hosted HTTP server); Azure maps to Self-hosted HTTP server (mongodb-js is already filed there). So the proposed cross-role move doesn't add new paths to Deployment topology — it consolidates existing in-tree-config facts under their substrate-class equivalents. The reconciler's choice is whether to expand each Deployment topology path's description to absorb the in-tree config facts, or to track in-tree configs under a new "Substrate-deployment config" path under Deployment topology. The first option preserves the current path shape; the second creates a structural sibling to Container artifacts' Dockerfile paths but inside Deployment topology.

**The role's coverage is undercount-by-design.** 15 of ~104 samples (≈14%) write a Deployment topology section explicitly. Most stdio samples don't bother — Local stdio process per session is the implicit default, and the default goes unwritten. This means the adoption table understates Local stdio's prevalence by orders of magnitude. The role's quantification is honest but easy to misread. A note in the role's prose flagging "explicit Deployment topology entries cluster on samples with non-default substrate facts to surface" would help the reader interpret the counts.

**The role's distinction from `Distribution channel > Hosted endpoint (no install)` is real but subtle.** Hosted SaaS endpoint and Hosted endpoint (no install) name the same fact from two angles: Distribution sees "user gets nothing to install"; Deployment sees "maintainer operates the runtime". 11 samples are under Distribution > Hosted endpoint; 6 are under Deployment > Hosted SaaS endpoint. The 5-sample gap means some samples file the fact under Distribution only — slackapi, stripe, upstash, utensils, cloudflare. None of those file a Deployment topology section explicitly; cloudflare files Deployment topology > Edge / serverless instead (substrate-class one level finer than "hosted SaaS"). The cross-role pointer between Distribution > Hosted endpoint and Deployment > Hosted SaaS endpoint should be explicit in both descriptions; today it is not.

**The Lambda story splits across 6+ roles for one sample, the most cross-role-fragmented sample in the corpus.** awslabs/mcp-lambda-handler files: Distribution > Lambda deployment package, Distribution > PyPI via pip, Container artifacts > No container artifacts, Transport > HTTP via API Gateway in front of Lambda, Multi-tenancy > Per-request tenancy with externalized session state, Deployment topology > Serverless (Lambda + API Gateway), Observability > CloudWatch via Lambda. This is structurally correct — the substrate genuinely shapes 6+ roles — but the fragmentation makes the sample's "deployment shape" hard to reconstruct from any single role. The reconciler may want a cross-role-linkage convention (mentioned in pass3-bin3 refinements as "the trio of these three paths together is the diagnostic signature") for this kind of substrate-coherent multi-role fact.

**Per-user local process (artifact = binary) is real but unwritten.** The path's adoption count is 0 because no sample writes "Per-user local process (artifact = binary)" as a Deployment topology entry, but the shape it describes is exhibited by 5+ compiled-binary stdio servers (github, googleapis, rust-mcp-stack, apollographql, geropl). Those samples either filed under Local stdio process per session (github did) or didn't write a Deployment topology section. The path is a categorization slot that maps to a real corpus shape but never gets named. Either delete the path (no evidence), merge into Local stdio process per session (the binary-vs-script distinction isn't a deployment-topology distinction), or accept it as a structural slot the corpus didn't surface in its prose. The merge option seems cleanest — Local stdio process per session is artifact-agnostic, the path is about *where the process runs*, and binary-vs-interpreted-script is a Distribution channel concern (Pre-built binary release vs PyPI), not a Deployment topology one.
