## Proposed new paths

> Format: `<role> > <new-path>` — supporting samples — qualitative description draft

- `Release automation` > `Quad-target tag-driven publish (PyPI + TestPyPI + MCP Registry + GHCR)` — `Vortiago/mcp-outline` — A single `push: tags: ['v*']` triggers four parallel/chained workflows: `publish-pypi.yml` (build → PyPI via OIDC trusted publishing → conditional TestPyPI on `-rc` → MCP Registry via `mcp-publisher login github-oidc`), `release.yml` (raw `gh release create --generate-notes --notes-start-tag $(git describe --tags --abbrev=0 ${ref}^)`), and `docker-build.yml` (multi-arch amd64+arm64 via QEMU + buildx with `docker/metadata-action` six-tag ladder). Distinct from existing single-target tag-trigger paths because the publish surface spans four independent registries (PyPI, TestPyPI, MCP Registry, GHCR) with no stored secrets — every credential is OIDC-trusted-publishing or GitHub OIDC. Rc-suffix routes only the PyPI-publish job to TestPyPI; release.yml and docker-build.yml have no rc filter, so prerelease tags also cut a GitHub Release and tag a `latest` Docker image (likely-unintended exposure).

- `Release automation` > `Tag-driven CHANGELOG-less notes via `--notes-start-tag` predecessor lookup` — `Vortiago/mcp-outline` — `gh release create` invoked with `--generate-notes --notes-start-tag $(git describe --tags --abbrev=0 ${ref}^)` so GitHub auto-generates the changelog between the previous tag and the current one without any committed CHANGELOG.md. Distinct from existing `--generate-notes` paths because the predecessor tag is computed live in CI rather than relying on GitHub's default "between tags" calculation; useful when tag history is non-linear or when the author wants explicit predecessor selection.

- `Marketplace manifest layout` > `Self-referential single-plugin marketplace at repo root with companion MCP-registry manifest` — `Vortiago/mcp-outline` — Same as the existing `Self-referential single-plugin marketplace at repo root` path but with a sibling `server.json` (modelcontextprotocol/registry schema) at repo root carrying its own `$schema`, `isSecret`/`isRequired`/`registryType: "pypi"` field set, and version field maintained in lockstep. Plus `glama.json` for glama.ai's MCP directory. The plugin advertises to three discovery surfaces (Claude Code marketplace, MCP Registry, glama.ai) from one repo — distinct from "marketplace alone" because the per-registry schema dialect differs and the bump tooling must understand all of them. Could be a description sharpening on the existing path rather than a new path.

- `Tool-use enforcement` > `Read-only enforcement via prose only` — `Vortiago/mcp-outline` — The agent's prompt body declares "read-only" behavior in prose ("don't call destructive tools") rather than via tool filtering or env-var enforcement at the MCP server. The structural enforcement option (`OUTLINE_READ_ONLY=true` at server level) is available but not used; the agent relies on the model obeying its own prompt. Distinct from existing "no enforcement" paths because the prose enforcement IS the enforcement mechanism — there's no claim of structural safety to break. Could subsume into `No enforcement (observational only)` with sharpening.

- `Plugin-component registration` > `Dual `.mcp.json` for production vs developer mode` — `Vortiago/mcp-outline` — Repo ships `.mcp.json` (production: `uvx mcp-outline==<exact-ver>` against PyPI wheel) and `.mcp.dev.json` (developer: `uv run mcp-outline` against in-repo source plus extra env vars like `OUTLINE_DYNAMIC_TOOL_LIST`). Neither is wired into plugin config; developers manually choose which file Claude Code reads in their install. Distinct from existing inline-mcp-config paths because the dual-file convention is the deliberate dev/prod split rather than coexisting alternatives — only one is the plugin's authoritative MCP config at install time, and the choice is left to the consumer.

- `Channel distribution` > `Pre-release suffix routes one job in a multi-job tag pipeline` — `Vortiago/mcp-outline` — Within a pipeline that fires N jobs on `push: tags: ['v*']`, only ONE job (e.g., `publish-to-testpypi`) is gated on `if: contains(github.ref, '-rc')`; the others (PyPI, GitHub Release, Docker) run unconditionally. Effective result: an `-rc` tag publishes to TestPyPI INSTEAD OF (via job conditionals on the production target) AND ALSO cuts a real GitHub Release / Docker `latest` image. Differs from existing rc-suffix paths because the partial-filter creates a leak: the rc tag is a "prerelease" in TestPyPI but a "release" in every other channel. Worth elevating as a distinct anti-pattern since the path looks deliberate from one workflow file but isn't from the cross-workflow whole.

- `Marketplace manifest layout` > `Repo-root `.mcp.json` with hardcoded local dev paths committed` — `ZhuBit/cowork-semantic-search` — Committed `.mcp.json` at repo root contains absolute paths keyed to the author's local machine (e.g., `/Users/<author>/Projects/.../...`). The file is non-functional as a plugin-distribution artifact — it can only run on the author's checkout — yet ships in the public repo. The README's actual install instructions tell users to paste a templated `.mcp.json` into their own project root with their own absolute paths. The committed file is leaked dev config. Distinct from documented `.mcp.json` patterns because the file's *intended audience is no one* — it doesn't function for users and isn't read by the plugin install flow. Worth elevating as an anti-pattern rather than subsuming.

- `Plugin-component registration` > `Skill-as-loose-md-file (non-canonical placement)` — `ZhuBit/cowork-semantic-search`, `a3lem/my-claude-plugins` — A file at `skills/<name>.md` (loose markdown at the skills/ directory root) carrying command-style frontmatter (`name`, `description`, `argument-hint`) rather than the canonical `skills/<name>/SKILL.md` directory structure. Two interpretations: misunderstanding of skills-vs-commands distinction, or leftover scaffolding from a command file mis-placed in `skills/`. Distinct from canonical `skills/<name>/SKILL.md` because Claude Code's skill-discovery looks for the directory form; loose `.md` files are likely silently ignored. Could fit as a new path under Skill authoring conventions OR Plugin-component registration. The consolidated already mentions "loose `skills/<name>.md` files at the skills/ root" inside `Component composition > Skills (universal)`, but a dedicated path with its own description would surface this anti-pattern more clearly.

- `Bin entry mechanism` > `Marketplace-root bin with absolute-path-symlink target (broken at install)` — `a3lem/my-claude-plugins` — Same shape as the existing `Marketplace-root bin with per-plugin symlink` path, but the per-plugin symlinks (`plugins/<name>/hooks/<wrapper>`) are git-tracked with mode 120000 and ABSOLUTE target paths keyed to the author's home directory (e.g., `/Users/<name>/Code/.../bin/<wrapper>`). Once installed via marketplace `git clone`, the symlink resolves to a non-existent path on every other machine; the SessionStart hook fails with "file not found." The author's documented intent is correct (shared utility, one source of truth, ship-with-install) but the committed symlink shape breaks the strategy. Could be a description sharpening on the existing path rather than a new path; the existing description already mentions "Observed in lower-discipline form, where the documented intent is correct but the committed symlink targets are absolute" — but a3lem/my-claude-plugins is the canonical example and could be cited explicitly via the cross-key.

- `Per-plugin discoverability metadata` > `Stale plugin name in non-marketplace metadata after rebrand` — `Vortiago/mcp-outline` (partially) — Several non-marketplace files carry the plugin's identity (`server.json` for MCP Registry, `glama.json` for glama.ai). When the plugin renames, these files must all bump in lockstep with `marketplace.json` and `plugin.json` or external registries get out-of-sync names. Could merge into existing version-coordination paths.

- `Tool-use enforcement` > `Inline `.mcp.json` configuration as the plugin's enforcement boundary` — `Vortiago/mcp-outline` — When the plugin is purely an MCP-server bridge with no Claude Code hooks at all, the `.mcp.json` env block (`OUTLINE_READ_ONLY`, `OUTLINE_DISABLE_DELETE`, `OUTLINE_DISABLE_AI_TOOLS`, `OUTLINE_VERIFY_SSL`) IS the enforcement surface — set at MCP-server registration time, before Claude Code ever sees the tools. Distinct from existing "no enforcement (observational only)" because the policy IS structural, just at the MCP layer not the Claude Code hook layer. Could fit as a description sharpening on `No enforcement (observational only)` to clarify that "no Claude Code hooks" doesn't mean "no enforcement anywhere."

- `Novel and cross-cutting concerns` > `App-level sha256 mirroring the infra-level sha256` — `ZhuBit/cowork-semantic-search` — The plugin uses SHA-256 at two scopes for two purposes: the SessionStart install hashes `requirements.txt` for idempotency (`Dependency installation > SessionStart-driven Python venv with hash gating`), and the runtime application uses `hashlib.sha256` to fingerprint document content for incremental indexing (`server/indexer.py::compute_file_hash`, reading in 8192-byte chunks). Two independent hash checks at different scopes, same algorithm — "hashing is the idempotency primitive" pattern used at both infra and app layer in one repo. Distinct as a cross-layer-coincidence pattern; not a single-role observation but a cross-cutting one. Could fit under `Novel and cross-cutting concerns` since it bridges Dependency installation and the plugin's own product surface.

- `Novel and cross-cutting concerns` > `Gherkin/EARS notation choice for specs` — `a3lem/my-claude-plugins` — The `spec-driven-dev` plugin's spec language explicitly mixes SHALL statements (EARS — Easy Approach to Requirements Syntax), Given/When/Then scenarios (Gherkin), and plain prose. Distinctive choice in the corpus: nowhere else in the surveyed landscape does a plugin commit to EARS/Gherkin as the spec notation. Worth elevating as a cross-cutting concern around how plugins authoring methodology commit to a specific spec-language vocabulary. Note: this path appears in the chain-key inventory at count 1 under the legacy `Sample > 17. Novel axes >` form, suggesting an earlier bin already proposed it; the reconciler may have already integrated.

- `Novel and cross-cutting concerns` > `Inline symlink as plugin-distribution escape hatch` (companion to existing `Bin entry mechanism > Marketplace-root bin with per-plugin symlink`) — `a3lem/my-claude-plugins` — The marketplace-root-bin pattern (described under Bin entry mechanism) is also a deliberate methodology choice surfaced explicitly in the project's `CLAUDE.md`: shared utilities live in `bin/` at the marketplace root and each consuming plugin ships a symlink (`plugins/<name>/hooks/<wrapper>`) pointing at the shared location. This is a DRY pattern unique to multi-plugin marketplaces. Could be a description sharpening on `Bin entry mechanism > Marketplace-root bin with per-plugin symlink` (the existing path mostly addresses the *mechanic* — symlinks, target paths, install model) rather than a new path in `Novel and cross-cutting concerns` (which would address the *pattern justification*). Defer to reconciler.

## Proposed description sharpenings

> Format: `<role> > <existing-path>` — what the existing description misses; supporting samples; sharpening suggestion

- `Version coordination > Multi-site sprawl (5+ locations)` — current description mentions 5+ sites and rebase-driven drift. `Vortiago/mcp-outline` adds the version-bump-script-as-atomic-tool variant: `scripts/bump_version.py` rewrites `server.json` (two version fields), `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, plus a regex rewrite of the pinned `==<ver>` literal in `.mcp.json`'s args array. Validates semver-bump legality (patch/minor/major) before writing. Sharpening: name "atomic-bump-script across N files" as a deliberate single-source-of-truth pattern; specific evidence is regex rewriting inside an inline arg array rather than just JSON field assignment.

- `Tag and release lifecycle > Tag-on-main with active cadence (semver discipline)` — current description names "18 tags over ~13 months" — that observation is from `Vortiago/mcp-outline` specifically. Sharpening: nothing structural is missed; the tag-on-main with rapid burst cadence (most v1.x in a 5-month burst) and `setuptools-scm` deriving `X.Y.Z.devN` for inter-tag dev builds is captured. Could add: when `setuptools-scm` drives versioning from tags, the static JSON manifests (plugin.json, marketplace.json, server.json) hold the LAST released semver and the bump script is the only thing that updates them.

- `Marketplace validation > No validation` — `Vortiago/mcp-outline` and `ZhuBit/cowork-semantic-search` both exhibit "no validation despite having other CI." Sharpening: distinguish "no CI at all" (cowork-semantic-search) from "extensive CI but zero manifest validation" (mcp-outline). The latter is a more interesting failure mode — the project has the infrastructure to validate but doesn't apply it to plugin manifests. The existing description says "manifest regressions surface only at install time on a real Claude Code session" — this applies equally in both cases, but the diagnostic value of pointing it out differs.

- `Documentation surface > Comprehensive single README + ad-hoc CLAUDE.md` — `Vortiago/mcp-outline` matches this path almost exactly. The existing description correctly identifies that CLAUDE.md mixes architecture with operational procedure and that this is acceptable for solo projects but blurs three-doc-separation. Sharpening: add the specific failure mode — the CLAUDE.md "release runbook" embedded inline (uv run poe bump-version → commit → PR → merge → tag → push) is operational procedure that conflicts with the architecture-reference content in the same file. A reader looking for either purpose has to skim past the other.

- `Dependency installation > SessionStart-driven Python venv with hash gating` — `ZhuBit/cowork-semantic-search` matches this path. The existing description mentions the `shasum` (BSD) vs `sha256sum` (Linux) fragility. Sharpening: cowork-semantic-search uses ONLY `shasum -a 256 | cut -d ' ' -f 1` with no fallback, so on Linux distributions where `shasum` is absent (e.g., minimal Alpine or some Debian variants without Perl), the hook aborts via `set -e` with "command not found" before the hash comparison runs. Worth naming as the failure mode rather than just listing the fragility surface.

- `Skill authoring conventions > Standard frontmatter` — current description mentions per-skill `metadata.{author, version}` adding version-sync sites. `a3lem/my-claude-plugins` exhibits the failure mode: `spec-driven-dev` plugin has CHANGELOG `2.1.0`, `plugin.json` `1.0.0`, SKILL.md frontmatter `version: 3.2.0` — three-way disagreement. Sharpening: name "SKILL.md frontmatter version drift across N-way version-source disagreement" as the concrete failure mode, citing the value of having no per-skill version field at all (or an explicit pointer back to plugin.json).

- `Per-plugin discoverability metadata > Bare-minimum (name, version, description only)` — `a3lem/my-claude-plugins` exhibits a sub-variant: not every plugin in a multi-plugin marketplace carries the bare minimum — `auto-memory` has `"version": "1.1"` (non-semver shorthand), `better-comments` and `session-setup` omit `version` entirely. Sharpening: distinguish "bare-minimum but well-formed" from "bare-minimum-with-defective-fields" (missing required fields, non-semver versions). The latter survives only because Claude Code's manifest validation is currently lenient; a stricter validator would reject these.

- `Plugin-to-plugin coordination > `dependencies` field absent` — `a3lem/my-claude-plugins` adds the failure-mode evidence: three plugins (`spec-driven-dev`, `project-notes`, `project-knowledge`) form a "knowledge ecosystem" coupled by convention — the `project-knowledge` README explicitly says "This plugin doesn't manage any store directly — it routes to spec-driven-dev … and project-notes." A user installing only `project-knowledge` gets broken routing with no install-time error because there's no `dependencies` field to enforce the coupling. Sharpening: name "documented coordination without machine-enforcement" as a concrete failure case for the `dependencies-absent` path.

- `Documentation surface > Shipped planning corpus visible in public repo` — `ZhuBit/cowork-semantic-search` matches: `IMPLEMENTATION_PLAN.md` (~44 KB), `memory/project_cowork_rag_plugin.md`, `memory/MEMORY.md`. Sharpening: add the specific risk that `memory/` exposes the author's *Claude Code memory directory* — author's project-memory file shipped as first-class repo content. Different from "planning notes" because it's the author's own assistant context, not a deliberately-published design doc.

- `Bin entry mechanism > Marketplace-root bin with per-plugin symlink` — current description already mentions absolute-vs-relative target failure modes. `a3lem/my-claude-plugins` is the canonical observation; the bin wrapper itself (`bin/inject-rules`) does substantive work beyond concatenation — resolves plugin name from `plugin.json`, walks up for marketplace.json, decorates output with provenance metadata. Could sharpen by naming the "wrapper-as-context-enrichment-formatter" sub-pattern within the marketplace-root-bin path. (The consolidated already has `Provenance-decorated stdout` under Session context loading, so this is captured at the output-shape level; the bin-mechanism path could cross-reference it.)

## Structural concerns

- **Per-sample identification metadata (URL, stars, last commit date, default branch, license, sample origin) doesn't fit the role tree.** Following bin-1's pattern, I moved entity-identifying content into a one-line preamble after the level-1 heading — URL, one-line description, license, default branch, last commit date, sample origin. - **License declaration scope ambiguity.** `Vortiago/mcp-outline` carries MIT (LICENSE file + SPDX in plugin.json + README); `ZhuBit/cowork-semantic-search` carries AGPL-3.0-or-later (LICENSE file + plugin.json declaration); `a3lem/my-claude-plugins` has no LICENSE at all. For a3lem there's `License declaration > [absent — no path covers this exactly]`. Looking at the consolidated, `License declaration > Single repo-level license` and similar paths assume LICENSE is present. The "no LICENSE" case is observable in `a3lem/my-claude-plugins`. Defer to reconciler whether to add a `No license declaration` path or treat as documentation-surface gap.
