Behavior is closer to a rewrite engine than a gate. Distinct from `PreToolUse Bash matcher as ask-first guardrail` (binary allow/deny) and `Soft-then-escalating PreToolUse hook` (multi-tier severity) — this one teaches as it blocks.

- `Hook handler runtime` > `Prompt-type hook (LLM evaluates prose rule list)` — `skullninja/coco-workflow` — At least one hook is `type: prompt` rather than `type: command`; the body is a multi-hundred-word prose rule list; Claude evaluates the proposed tool input against the rules and returns BLOCK or ALLOW. No script process is spawned. Distinct from existing handler-runtime paths (Bash scripts, Node `.mjs`, Python, single-Go-binary), which all shell out to a separate executable. Trade-off: natural-language flexibility, non-deterministic, per-call latency.

- `Plugin-component registration` > `Hook type pivot (prompt → command for non-blocking)` — `skullninja/coco-workflow` — Release history v0.2.1→v0.2.3 shows a deliberate migration of every non-blocking hook (`PostToolUse`, `PreCompact`, `SessionStart`) from `type: prompt` to `type: command` after prompt-type non-blocking handlers caused "stopped continuation" errors; the blocking hook (`PreToolUse/Bash`) stayed prompt-type. Codifies a rule: blocking hooks stay prompt, non-blocking hooks become command. Distinct from existing registration paths because the dimension being recorded is the `type` field's correct mapping to the blocking/non-blocking nature of the event, not the path or matcher convention.

- `Bin entry mechanism` > `Script-relative wrapper avoiding `${CLAUDE_PLUGIN_ROOT}`` — `skullninja/coco-workflow` — A ~6-line bash wrapper resolves the target script via `cd "$(dirname "${BASH_SOURCE[0]}")" && pwd` and `exec`s it, with a comment explicitly framing the choice ("Resolves tracker.sh relative to itself so callers don't need `CLAUDE_PLUGIN_ROOT`"). Distinct from `Script-relative shell wrapper` if that path is generic — this is the variant that *deliberately rejects* the env-var route because `${CLAUDE_PLUGIN_ROOT}` is only exported to hook subprocesses, so command/skill markdown invocations can't rely on it. The decision is paired with a PreToolUse hook that hard-blocks regression to the env-var form.

- `Tool-use enforcement` > `Hook hard-block on bin-invocation regressions` — `skullninja/coco-workflow` — A PreToolUse `Bash` hook hard-blocks any non-`coco-tracker` invocation of the underlying script: `bash "${CLAUDE_PLUGIN_ROOT}/lib/tracker.sh"` (env-var path), absolute paths, variable assignment of the tracker path, `source` of the tracker. Distinct from generic command-shape gates because the gate's specific job is to prevent the bin-resolution pattern from regressing — the wrapper + the hook form a complete enforcement unit for a specific pattern decision.

- `Dependency installation` > `Self-installing pip from plugin root with `--force-reinstall`` — `robertnowell/marketing-pipeline` — SessionStart bootstrap creates a venv under `${CLAUDE_PLUGIN_DATA}/venv` then runs `"$VENV_DIR/bin/pip" install --force-reinstall "$PLUGIN_ROOT"` — the plugin treats itself as an installable Python package (pyproject.toml hatchling build) and reinstalls itself on every change-detection trigger. ## Proposed description sharpenings

> Format: `<role> > <existing-path>` — what the existing description misses; supporting samples; sharpening suggestion

- `Bin entry mechanism > Bash trampoline resolving python3 → python → py` — current path likely names the trampoline aspect. `robertnowell/marketing-pipeline` `bin/marketing` exhibits a bash-wrapper variant that does NOT resolve `python3 → python → py` but DOES `source "$VENV_DIR/bin/activate"` then `exec python -m pipeline.cli`. The `source activate` form is functionally correct (it mutates `$PATH`, then `exec python` resolves the venv's python) but strictly weaker than `exec "$VENV_DIR/bin/python" -m pipeline.cli`. Sharpening candidate: split the trampoline path or add an adjacent path covering the `source activate` + `exec python` anti-pattern explicitly.

- `Bin entry mechanism > existing wrapper paths` — `robertnowell/marketing-pipeline` `bin/marketing` exhibits a `cd "$STATE_DIR"`-before-`exec` pattern with partial argument rewriting (`--file path` resolved against `$ORIG_CWD` before `cd`, but `--file=path` and other relative-path flags are passed through unresolved against the new cwd). This argument-rewriting layer in a bin wrapper is a concrete technique; current paths cover wrappers but not wrappers that mutate cwd plus selectively resolve specific flags. Sharpening or new path: "Bin wrapper with cwd mutation and partial argument rewriting".

- `User configuration and authentication > existing `userConfig` paths` — `robertnowell/marketing-pipeline` declares an 11-field `userConfig` with `sensitive: true` applied cleanly to actual secrets and `false` to identifiers, but reveals two specific sub-failures: (a) one declared field (`ANTHROPIC_API_KEY`) is documented in prose as "only needed for GitHub Actions cron, not for plugin use" — a structural inversion where the declared `userConfig` field is for an out-of-band consumer, and (b) two declared fields (`PINTEREST_ACCESS_TOKEN`, `PINTEREST_BOARD_ID`) are not bridged in the SessionStart hook that exports the others, so the plugin code path doesn't see them. Sharpening: existing `userConfig declared but not wired through manifest substitution` could absorb these two sub-cases as concrete failure modes — declared-but-unused (intended for out-of-band consumer) and declared-but-partially-wired (bridge omits a subset).

- `Marketplace validation > existing absence paths` — `skullninja/coco-workflow` is a case where v0.2.1's release notes document the author *discovering* manifest-structure issues by failing install against Claude Code's own validator at install time. The end-user's `/plugin install` is the validation flow; pre-publish validation is absent. Sharpening for the "no validation" or "external validator" path: explicitly name install-time validation by the consumer's runtime as the *de facto* validator when no pre-publish gate exists.

- `Tool-use enforcement > existing `Stop`-event paths` — `smcady/Cairn` `Stop` hook runs `hook_ingest.py` async: parses recent transcript, ingests into reasoning graph in background. Distinct from session-end aggregation (data leaves the plugin) — here the Stop hook *writes* to plugin-local persistent state (the reasoning graph). Sharpening for `Stop-event handlers for session-end aggregation`: distinguish "aggregation for export" from "ingestion for plugin-local state update."

- `Install failure posture > existing implicit-retry paths` — `smcady/Cairn` exhibits "implicit retry via late-write cache marker": the cached `pyproject.toml` and the cached `.plugin_root` file are written *only after* `pip install` succeeds; on failure they're not written, so the next session's `diff -q pyproject.toml ${DATA_DIR}/pyproject.toml` fails again and re-enters the install branch. No `rm` on failure — implicit retry by virtue of late-cache-write ordering. Sharpening: existing `Implicit retry via late-write cache marker` describes this exactly — Cairn is a clean supporting example.

- `Live monitoring > `monitors.json` absent` — both `robertnowell/marketing-pipeline` and `skullninja/coco-workflow` lack `monitors.json` but offer durable-state surfaces in different ways: marketing-pipeline via GitHub Actions cron (out-of-band scheduler), coco-workflow via slash commands (`/coco:dashboard`, `/coco:status`, `/coco:standup`) the user invokes interactively. Sharpening: enumerate the alternatives that fill the monitor gap (cron, agent-invoked status commands, sidecar daemon) so the absence-as-pattern is more useful than just "absent."
