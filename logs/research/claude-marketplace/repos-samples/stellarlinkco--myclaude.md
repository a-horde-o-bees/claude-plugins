# Sample

Mirrors of `https://github.com/stellarlinkco/myclaude`. Multi-agent development workflow distribution (BMAD / requirements / dev-kit / OmO / SPARV) shipped as both a Claude Code marketplace and an `npx`-driven self-installer that stitches the marketplace layout onto a parallel "modules + skills" installer config. Default branch `master`, 2606 stars, last commit 2026-04-09 (master `c4a1567129`); sample origin: bin-wrapper (primary focus); also a multi-plugin marketplace and dep-management case (Go binary download via `install.sh`).

## Marketplace manifest layout

### Multi-plugin owned-aggregator marketplace

Single `.claude-plugin/marketplace.json` at repo root listing 5 plugins (`omo`, `requirements`, `bmad`, `dev-kit`, `sparv`), each authored by the marketplace owner and sourced via relative path. Top-level fields: `name`, `version` (5.6.1, decoupled from individual plugin versions and drifting against `package.json` 6.7.0), `description`, `owner`, `plugins[]`. No `metadata.{...}` wrapper. None of the plugin names collide with reserved names.

### Parallel non-marketplace inventory

Same repo carries `marketplace.json` AND a separate `config.json` enumerating 8+ modules (adds `course`, `harness`, `claudekit`, `do`) plus a separate "skills" axis (`browser`, `codeagent`, `codex`, `dev`, `gemini`, `product-requirements`, `prototype-prompt-generator`, `skill-install`, `test-cases`) for the `bin/cli.js` npx self-installer. The two inventories are intentionally disjoint: slash-command install via `/plugin marketplace add` gets the 5-plugin subset; npx install gets the richer module/skill menu with its own operations DSL (`copy_file`, `copy_dir`, `merge_dir`, `run_command`).

### `$schema` declaration on marketplace.json

`$schema: "https://anthropic.com/claude-code/marketplace.schema.json"` is present on `marketplace.json`. No CI step validates against the schema — editor-assistance only.

## Plugin source binding

### Relative source pointing to subdirectory

Every plugin's `source` is a relative path like `./skills/omo` or `./agents/bmad`. Naming inconsistency: `dev-kit` (marketplace name) maps to `./agents/development-essentials/`, whose own `plugin.json` declares `"name": "essentials"` — the two names disagree.

### `strict` field default

`strict` is absent on every entry — implicit `true`. No `skills` override on any marketplace entry.

## Per-plugin discoverability metadata

### Category-only

Marketplace entries carry `category` only — `development` on four plugins, `productivity` on `dev-kit`. No `tags` and no `keywords` on entries; no `category` on individual `plugin.json` files. Every `plugin.json` is minimal: `name`, `description`, `version`, `author`.

### `$schema` absence on per-plugin manifests

`$schema` is absent on every `plugin.json`.

## Version coordination

### Three-way version split (marketplace vs npm vs git tags)

Three independent version spaces drift: marketplace+plugin.json (5.6.1, with sparv at 1.1.0 in both), `package.json` consumed by the npx installer (6.7.0), and git tags on master (v6.8.2 most recent of 78 tags). The npx installer asks GitHub's Releases API for `tag_name` at runtime to resolve the download — installed artifacts match the tag while a consumer reading the checked-in files sees stale version fields. A `/plugin marketplace add` consumer gets 5.6.1 artifacts; an `npx github:stellarlinkco/myclaude` consumer gets master at the latest tag (v6.8.2 as of snapshot).

## Channel distribution

### Single channel — tag-on-main with git-ref pinning

Tags on master are the single release channel. Users always pin via `@ref` (or default to the latest release tag via the npx installer). The `--tag <tag>` CLI flag on `bin/cli.js` is the sole channel-pinning mechanism. An `rc/*` branch pattern is declared in CI triggers but no release artifact ties to it.

### Multi-channel via parallel distribution paths

Two install surfaces share the same source — `/plugin marketplace add` for the slash-command path (5 plugins, marketplace metadata at 5.6.1) and `npx github:stellarlinkco/myclaude` for the richer npx path (8+ modules + skills axis, package.json 6.7.0, runtime-resolved to the latest GitHub Release tag). README's "Quick Start" leads with the npx form; `/plugin marketplace add` is documented as the secondary form.

## Tag and release lifecycle

### Tag-on-main, single branch

78 tags (v3.1 … v6.8.2) all sit on master's linear history. No `release/*` branches owning tags; `rc/*` branches exist for pre-merge validation in CI only, with no tags observed on them. CHANGELOG generated by `git-cliff` (cliff.toml present) and run manually via `make changelog`. No pre-commit hook bumps versions. Tag-sanity gates absent — `package.json`'s `6.7.0` lags tags `v6.8.x` indefinitely.

## Plugin-component registration

### Default convention discovery

Every `plugin.json` is minimal — `name`, `description`, `version`, `author`. Components are found by directory convention (`agents/`, `commands/`, `hooks/`, etc. under each plugin root).

### Three-channel parallel registration

Components are registered three ways in the same repo: (a) marketplace.json plugin entries for the slash-command flow (relies on directory conventions), (b) `config.json` modules for the npx flow (enumerates per-module operations: `copy_file`, `copy_dir`, `merge_dir`, `run_command`), (c) legacy Makefile targets like `deploy-bmad`. The npx path also merges per-module agent presets into `~/.codeagent/models.json` and tags every merged hook entry with `__module__: <name>` for surgical unmerge on uninstall.

## Component composition

### Skills (universal)

`./skills/omo/`, `./skills/sparv/` are whole-skill plugins; `./skills/do/`, `./skills/dev/`, etc. ship as npx-selectable skills.

### Commands

`./agents/bmad/commands/`, `./agents/requirements/commands/`, `./agents/development-essentials/commands/`.

### Agents

`./agents/bmad/agents/` with 7 role agents (e.g., `bmad-architect.md`); similar for requirements.

### Hooks

Two locations: repo-root `hooks/hooks.json` serving the `claudekit` npx module, and `./skills/sparv/hooks/hooks.json` for the SPARV skill.

### bin

Repo-root `./bin/cli.js` — the npx installer itself, not a plugin-level bin.

### output-styles, monitors

Output-styles referenced in Makefile as `$(OUTPUT_STYLES_DIR)/bmad.md` but the directory is not checked in (Makefile is a legacy path). No `monitors.json`.

### Composition shapes

Cross-plugin composition mixes skill-only payloads (`omo`, `sparv`), agents-and-commands plugins (`bmad`, `requirements`, `development-essentials`/`dev-kit`), and the npx-only modules (`course`, `harness`, `claudekit`, `do`).

## Plugin-component placement

### Outside plugin directory at repo root

`bin/cli.js` lives at repo root and serves the marketplace as a whole — it is the npx installer, not a plugin-owned tool. `/plugin install`-flow consumers don't reach it; only `npx github:...` consumers do.

## Agent declaration conventions

### Minimal frontmatter (name, description)

Observed on `bmad-architect.md`: `name` and `description` only. No `model`, `tools`, `skills`, `memory`, `background`, `isolation`.

## Bin entry mechanism

### Zero-dependency Node self-installer at `bin/cli.js`

Single-file `bin/cli.js` (~1,285 lines) using only Node stdlib (`https`, `zlib`, `fs`, `crypto`, `child_process`, `readline`, `os`, `path`). Hand-rolled implementations of: GitHub API client (`api.github.com/repos/.../releases/latest`, `/contents/*`), `https` downloader to `codeload.github.com/.../tar.gz/refs/tags/<tag>`, in-memory `extractTarGz` with TAR parsing from scratch (pad-block handling, type-53 directory detection, `safePosixPath` rejecting `/`-rooted, `..`-containing, and `/../` paths), interactive `readline`-raw-mode multiselect for module picking, hook-config merger that tags every merged hook entry with `__module__: <name>` for surgical unmerge on uninstall, agent-preset merger into `~/.codeagent/models.json`. Shebang `#!/usr/bin/env node`; `package.json.bin` = `{"myclaude": "bin/cli.js"}` so npm/npx exposes it. Invoked as `npx github:stellarlinkco/myclaude` (no npm registry publish). Cross-platform via `process.platform === "win32"` checks throughout (`cmd.exe /c install.bat` vs `bash install.sh`; `where` vs `which`). `repoRootFromHere()` resolves via `path.resolve(__dirname, "..")`; with `--tag` set or fetched from latest-release, the CLI downloads a fresh tarball to `os.tmpdir()` and uses the extracted dir as repoRoot, overriding the local reference. No `${CLAUDE_PLUGIN_ROOT}` — pre-plugin-era bin shape. Zero npm runtime dependencies (supply-chain surface is zero) at the cost of TAR-parsing maintenance and unauthenticated GitHub API rate limit (60 req/h per IP) as the ceiling.

## Dependency installation

### Pre-plugin-era installer outside plugin tree

`install.sh` at repo root downloads the prebuilt `codeagent-wrapper` Go binary into `${INSTALL_DIR}/bin/codeagent-wrapper` where `INSTALL_DIR` defaults to `~/.claude` — not under `${CLAUDE_PLUGIN_DATA}` or `${CLAUDE_PLUGIN_ROOT}`. The installer writes directly into the user's claude config directory; the Go binary outlives plugin uninstall.

### External CLI auto-install via vendor scripts

The Go `codeagent-wrapper` binary ships as a per-OS/arch prebuilt artifact. `install.sh` detects OS and arch (`uname -s`, `uname -m`) and composes the GitHub Releases download URL (covers linux/amd64, linux/arm64, darwin/amd64, darwin/arm64, windows/amd64, windows/arm64). `install.sh` uses `set -e`; download failure prints `ERROR: failed to download binary` to stderr and exits 1. Manifest formats: `codeagent-wrapper/go.mod` for the bundled Go binary source; `package.json` for the npx CLI's own (nil) runtime deps; `config.json` for the declarative module/operation registry consumed by the installer. Caller-side failure: `runInstallSh` in `cli.js` rejects the promise with `install script failed (exit ${code})`; top-level `.catch` writes `ERROR: <msg>` to stderr and `process.exit(1)`.

### Zero-dep system-tool stance (bash + jq only)

The Node CLI itself ships zero npm runtime deps (only Node stdlib). Cross-script orchestration relies on `bash`/`cmd.exe` plus `python3` for some hook scripts (`pre-bash.py`, `inject-spec.py`, `log-prompt.py`).

### Coexisting redundant install paths

Three install scripts in tree, only one is actually invoked by the blessed path: `install.sh` is a POSIX wrapper (legacy entry; prints a 5-second warning banner directing users to the npx path), `install.bat` is its Windows companion, and `install.py` is a legacy 1,533-line Python installer that uses `jsonschema` to validate `config.json`. The new blessed path is `bin/cli.js` (1,285 lines), which uses `JSON.parse` without schema validation. A reader has to trace the README's npx instructions to know `cli.js` is the live one.

## Install change detection

### Existence-only check

The npx installer compares nothing beyond existence — `copyFile` refuses overwrite unless `--force`; `copyDirRecursive` skips if destination exists. No hash, sha, mtime, or version-stamp comparison. `--update` re-runs with `force: true` implicitly via re-copy after fetching the new tag. `installed_modules.json` records what was installed but is metadata-only (tracks `installed_at` timestamp, not hashes). Version-mismatch handling: `printPostInstallInfo` runs `codeagent-wrapper --version` and prints the version but doesn't gate or warn on compatibility.

## Install trigger and lifecycle

### User-invoked one-shot installer

Install is a user-invoked CLI (`npx github:stellarlinkco/myclaude`), not a hook. The installer handles tarball download, interactive multiselect, copy operations (`copy_file`, `copy_dir`, `merge_dir`, `run_command`), and merging into `~/.claude/settings.json`. `/plugin marketplace add` is the secondary channel that gets a smaller subset.

## Install failure posture

### Set -e bash with stderr exit-1

`install.sh` uses `set -e` (halt on first error); download failure prints `ERROR: failed to download binary` to stderr and exits 1. Caller (`runInstallSh` in cli.js) rejects its install promise with `install script failed (exit ${code})`. Top-level `.catch` writes `ERROR: <msg>` to stderr and `process.exit(1)` — user-facing CLI output, not hook JSON.

## Custom installer alternative

### Operations DSL with restricted run_command

The npx installer's `config.json` defines modules as a sequence of typed operations (`copy_file`, `copy_dir`, `merge_dir`, `run_command`). `run_command` is restricted at the installer level to exactly `"bash install.sh"` — no arbitrary commands. Minimum-capability safeguard on a powerful primitive: the operation type is general but the registry only permits one specific invocation.

### Hook-config stitching with module-tagged surgical unmerge

When the installer merges a module's `hooks/hooks.json` into `~/.claude/settings.json`, it tags every hook entry with `__module__: <name>`. Uninstall scans settings.json and removes only entries with the matching tag, leaving user-added hooks untouched.

### Installed-modules status file

`~/.claude/installed_modules.json` tracks what was installed with `installed_at` timestamps and per-operation results. Used by `--update` to detect which modules to re-install and by `uninstall` to know what to remove. Durable state file separate from Claude Code's own settings, acting as the installer's source of truth for what it has done to the user's machine.

### Post-install detection report

`printPostInstallInfo` in `cli.js` runs `which codex`, `which claude`, `which gemini`, `which opencode` and reports status with `✓`/`✗` markers, plus detects whether `~/.claude/bin` is in `$PATH`. User-friendly telemetry without phone-home — diagnostic on the user's machine only.

### Dual installer (legacy + current)

`install.py` (Python, 1,533 lines, uses `jsonschema`) and `bin/cli.js` (Node, 1,285 lines, the new blessed path) coexist. The shell wrapper prints a 5-second warning banner directing users to the npx path. Migration-in-progress visible in the repo structure.

## Native artifact distribution

### Bundled go.mod for prebuilt binary

`codeagent-wrapper/go.mod` describes a Go binary bundled in the plugin source tree, rebuilt by CI for six target OS/arch combinations and attached to GitHub Releases as prebuilt artifacts. The plugin's runtime install fetches the prebuilt binary by uname-derived URL rather than rebuilding from source on the user's machine.

## User configuration and authentication

### No user-supplied config

No `userConfig` in any `plugin.json`. The installer reads its own config via `~/.codeagent/models.json` (API keys, agent presets per backend) but that is not a `userConfig` in the Claude Code sense — it's a separate runtime config file for the `codeagent-wrapper` Go binary.

### Custom env-var substitution in hooks.json

`${CLAUDE_PLUGIN_ROOT}` is used in the repo-root `hooks/hooks.json` commands (e.g., `python3 ${CLAUDE_PLUGIN_ROOT}/pre-bash.py ...`) and the Node.js installer re-implements substitution via `replaceHookVariables` when merging module hook configs. `${SKILL_PATH}` is used in `skills/sparv/hooks/hooks.json` — a SPARV-internal convention, not a Claude Code built-in variable. If Claude Code's hook-runtime env doesn't populate `${SKILL_PATH}`, the hook command dereferences an empty string and the `[ -f .sparv/state.yaml ] && ${SKILL_PATH}/scripts/...` guard silently no-ops (absent file path) — fail-open but hides missing-env misconfiguration.

## Tool-use enforcement

### PreToolUse Bash dangerous-command blocker

Repo-root `hooks/hooks.json` (claudekit module) registers a `Bash` matcher running `pre-bash.py "$CLAUDE_TOOL_INPUT"` plus `inject-spec.py` (dangerous command blocking + spec injection). `pre-bash.py` is 536 bytes — minimal; not verified from source whether it is a real safety blocker or a stub. `inject-spec.py` placement on `PreToolUse:Bash` is unusual for context injection — more likely it rewrites the bash command than emits additional context.

### PreToolUse Edit/Write risk advisor

`skills/sparv/hooks/hooks.json` declares an `Edit|Write` matcher running `check-ehrb.sh --diff --dry-run` (risk detection for modifications), gated on `[ -f .sparv/state.yaml ]` existence and suffixed with `|| true` — non-zero exits swallowed, advisor never blocks.

### PostToolUse for index/state maintenance

`skills/sparv/hooks/hooks.json` registers a `PostToolUse` on `Edit|Write|Bash|Read|Glob|Grep` running `save-progress.sh` (journal entry on every relevant tool use), gated on `.sparv/state.yaml`. With sparv active, the journal grows unboundedly fast — the documented "2-action save" protocol scales linearly with work.

## Hook output contract

### Stderr for human display + stdout JSON for harness

Scripts invoked directly via `bash`/`python3`; commands wrapped in `[ -f .sparv/state.yaml ] && ... || true`. Output convention is stderr-human (no stdout JSON), since the sparv scripts' outputs read like human messages.

## Hook failure posture

### Fail-open with always-exit-0

The sparv hook commands wrap in `[ -f .sparv/state.yaml ] && ... || true` — a non-zero exit is swallowed (fail-open). The repo-root `pre-bash.py` (dangerous-command blocker) has no such guard, so its non-zero exit would block Bash as intended.

## Session context loading

### UserPromptSubmit prompt logger

Repo-root `hooks/hooks.json` registers a `UserPromptSubmit` matcher running `log-prompt.py` — name implies prompt logging, not context injection. `log-prompt.py` contents not fetched.

## Live monitoring

### `monitors.json` absent

## Plugin-to-plugin coordination

### `dependencies` field absent

No `plugin.json` declares the schema-level `dependencies` field. Tags are flat repo-wide `vX.Y.Z` (no `{plugin-name}--v{version}` form); the marketplace is multi-plugin but single-version (every plugin shares 5.6.1, with `sparv` at 1.1.0).

### Implicit dependencies coded in installer

The npx installer encodes inter-module wrapper dependencies in source (`WRAPPER_REQUIRED_MODULES = new Set(["do", "omo"])`, `WRAPPER_REQUIRED_SKILLS = new Set(["dev"])` in `cli.js`) so selecting `do` or `omo` triggers `bash install.sh` for the `codeagent-wrapper` binary. Not declarative; not visible to the marketplace consumer.

## Testing

### Go test

The `codeagent-wrapper` Go binary is exercised via `go test -v -cover -coverprofile=coverage.out ./...` inside `codeagent-wrapper/`, with `go tool cover -func=coverage.out | grep total | awk '{print $3}'` to print coverage and a codecov upload (`continue-on-error`). Tests live inside `codeagent-wrapper/` (co-located with Go source).

### No tests

The Node.js installer (`bin/cli.js`, 1,285 lines) has no tests — `test_install_path.bat` is a 1,946-byte Windows-only smoke script, not a real test suite. The Python hooks (`pre-bash.py`, `inject-spec.py`, `log-prompt.py`) and the 1,533-line `install.py` have no tests in CI. Coverage enforcement is absent — the awk pipeline prints coverage but doesn't fail the build below a threshold.

## CI workflow shape

### Multi-OS Go test matrix plus daily cross-version run

`.github/workflows/ci.yml` (861 bytes) runs `go test ...` inside `codeagent-wrapper/` on `os: [ubuntu-latest, windows-latest, macos-latest]` with Go 1.21 fixed. Triggers: `push` on `master` and `rc/*`; `pull_request` on the same. `release.yml` (3,906 bytes) triggers on tag push.

### Action-pinning conventions

`actions/checkout@v4`, `actions/setup-go@v5`, `codecov/codecov-action@v4` — tag-pinned, not SHA-pinned. Built-in `setup-go` cache (implicit default).

## Release automation

### Tag-triggered prebuilt-binary matrix

`release.yml` triggers on `push: tags: ['v*']`. Matrix builds `codeagent-wrapper` for 6 targets (linux/amd64, linux/arm64, darwin/amd64, darwin/arm64, windows/amd64, windows/arm64) with `CGO_ENABLED=0` and version stamped via `-ldflags="-s -w -X codeagent-wrapper/internal/app.version=${VERSION}"`. Uploads all artifacts plus `install.sh` / `install.bat` via `softprops/action-gh-release@v2`. Release notes generated inline via `git log ${PREVIOUS_TAG}..${TAG} --pretty=format:"- %s (%h)" --no-merges` — bypasses CHANGELOG.md entirely. No tag-sanity gates: no verify-tag-on-master, no verify-tag-matches-package-version, no tag-format regex. `draft: false`, `prerelease: false`.

### Auto-generated release notes from commits

Two sources of truth coexist for release notes — `CHANGELOG.md` (Keep-a-Changelog-style, git-cliff-generated, manually run) and the release-workflow-generated `release_notes.md` (raw `git log`). They diverge immediately: CHANGELOG groups by feat/fix/docs; the workflow emits a flat `- <subject> (<hash>)` list.

## PATH augmentation and host-project setup

### Auto-shell-rc modification

`install.sh` detects user shell and writes PATH-append lines to shell rc files with idempotency guards. Crosses the line from "install under `~/.claude`" to "modify user dotfiles" — most plugin-era patterns avoid this because plugin uninstall cannot reliably reverse the shell-rc edits.
