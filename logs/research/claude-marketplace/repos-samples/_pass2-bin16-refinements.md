## Proposed new paths

> Format: `<role> > <new-path>` — supporting samples — qualitative description draft

- `Plugin-component registration` > `Custom `capabilities.json` sidecar` — `marioGusmao/mg-plugins` — Each plugin ships `.claude-plugin/capabilities.json` alongside `plugin.json` with a non-standard schema declaring `{plugin, version, schema_version: "1.0.0", capabilities: [{id, name, type: "skill"|"agent"|"mcp_tool"|"hook", applicable_phases: [...], guidance, anti_patterns: [...], priority: 1-10}]}`. Not in the official Claude Code plugin spec; intended for a router/selector layer (likely the sibling `router-plugin`) that picks which capability to invoke based on `applicable_phases` + `priority`. The sidecar's `capabilities.version` drifts independently from `plugin.json.version` (e.g., codegraph plugin.json `1.1.22`, capabilities.json `1.1.18`). Distinct from `Custom sidecar manifest` only in that this one is documented as feeding a runtime selector, not just a metadata listing.

- `Install change detection` > `Native-module ABI marker driving rebuild-only` — `marioGusmao/mg-plugins` — A `.node-abi` marker file under `${CLAUDE_PLUGIN_DATA}` stores `process.versions.modules` (Node's `NODE_MODULE_VERSION` integer) and is compared on every SessionStart. ABI mismatch triggers `npm rebuild <list>` of explicitly-enumerated native modules only (e.g., `better-sqlite3 tree-sitter`), distinct from a full reinstall driven by `package.json` diff. Two orthogonal change detectors with two distinct recovery actions: full reinstall vs native-only rebuild. Faster than full reinstall on Node major bumps. Sibling to `ABI marker for native modules` (existing path) — this proposal sharpens the recovery distinction (native-only rebuild, not full reinstall).

- `Install change detection` > `Runtime-probe fallback on import error pattern` — `marioGusmao/mg-plugins` — The session-start hook runs `execFileSync('node', ['-e', 'require("better-sqlite3")'])` and pattern-matches `/NODE_MODULE_VERSION|was compiled against a different/` on the error to trigger an inline `npm rebuild` recovery. Belt-and-suspenders alongside marker-file detection: marker catches the common case cheaply, runtime probe catches stale markers or corrupted installs. Sibling to `Runtime-probe fallback` — this proposal pins the specific pattern-match-on-error mechanism.

- `Dependency installation` > `Symlink-out-of-data-dir for ESM resolution` — `marioGusmao/mg-plugins` — Plugin installs Node deps into `${CLAUDE_PLUGIN_DATA}/node_modules` then runs `ln -sfn $PLUGIN_DATA/node_modules $PLUGIN_ROOT/node_modules` so ESM `import` from the plugin's own source resolves without `NODE_PATH` hacks. Inverse of "install into plugin root" patterns; plugin root stays read-only-suitable while resolution still works. Distinct from `Plugin data dir with symlink-out` (existing) only in that this is specifically Node-ESM-resolution-driven and uses `--ignore-scripts` to avoid prepare/build scripts that need source in plugin root.

- `Tool-use enforcement` > `PostToolUse Bash auto-reindex on working-tree-changing commands` — `marioGusmao/mg-plugins` — PreToolUse and PostToolUse on `Bash` matcher with a shared regex set `/\bgit\s+(pull|merge|rebase|checkout|switch|cherry-pick|reset|restore)\b/` plus `/\b(npm|pnpm|yarn)\s+install\b/` to invalidate or refresh a code index on commands that mutate the working tree. Gated on `existsSync(dbPath)` so first pulls don't spuriously create indexes. Distinct from `PostToolUse for index/state maintenance` (existing) in that it specifically uses Bash-command pattern detection rather than file-write detection.

- `User configuration and authentication` > `Project-root YAML config (e.g., `.kdoc.yaml`)` — `marioGusmao/mg-plugins` — Plugin reads a project-rooted YAML config file (e.g., `.kdoc.yaml`) from the user's project working directory in its session-start hook rather than exposing settings via plugin-manifest `userConfig`. Config lives with the project it configures, not with the user; supports per-project customization without Claude Code's user-config UI. Distinct from `Markdown block in consumer's CLAUDE.md` (which is markdown-embedded) and from `External config file owned by plugin` (which is plugin-owned, not project-owned). Folded into `External config file owned by plugin` in the rewritten sample as the closest existing path; the project-rooted-YAML distinction is still worth a dedicated path.

- `Plugin-to-plugin coordination` > `Filesystem-spool convention coupling` — `marioGusmao/mg-plugins` — Two plugins coordinate via a shared filesystem spool (`~/.ai-sessions/spool/events.jsonl`): one writes via a hook (`capture-event.sh`), another reads in its session-start hook to surface drift warnings. No declared dependency; the reader silently degrades when the writer isn't installed. Distinct from `Implicit via filesystem convention` only in that this names the JSONL-spool shape specifically.

- `Tool-use enforcement` > `Pre-push reminder via Bash matcher with command parsing` — `marioGusmao/mg-plugins` — PreToolUse on `Bash` matcher parses the command string for `git push` patterns and reports staleness of a governance file. Always exit 0 — reminder, not block. Uses the Bash-tool hook as a proxy for a git pre-push hook, with explicit documentation that terminal pushes (outside Claude Code's tool channel) aren't covered. Sibling to `PreToolUse Bash matcher as ask-first guardrail` but specifically observation-only with documented gap coverage. Folded into `PreToolUse Bash matcher as ask-first guardrail` in the rewritten sample as the closest existing path; the "reminder, not block" + "Bash hook as git-hook proxy" distinction is worth a dedicated path.

- `Marketplace manifest layout` > `Top-level `bundles` array (non-standard grouping)` — `mdproctor/cc-praxis` — A non-schema top-level `bundles` array in `marketplace.json` groups plugins into named collections with display metadata (`name`, `displayName`, `description`, `skills`). Consumed only by the repo's custom installers (`web_installer.py` for UI grouping, `scripts/claude-skill` for `install-all` subsetting). Claude Code's built-in `/plugin install` does not surface bundles; users installing through the official path see only individual plugins. Distinct from `Custom non-schema fields on marketplace entries` because this is a top-level array rather than a per-entry field, and it functions as a grouping primitive the schema lacks.

- `Channel distribution` > `Maven-style `-SNAPSHOT` suffix as dev-track` — `mdproctor/cc-praxis` — Plugins use `1.0.0-SNAPSHOT` during development, stripped at release; not a SemVer pre-release identifier (`-rc`, `-beta`). Custom version comparator in repo's installer (`_version_tuple`) treats SNAPSHOT as strictly older than the release counterpart. Convention borrowed from Maven (Java/Quarkus ecosystem). Mixing release and SNAPSHOT versions across many plugins creates ordering ambiguity for naive string-based comparators. Distinct from `Pre-release tag suffixes on a single channel` (which uses semver-recognized suffixes) and from `Pre-release suffix as channel marker (Maven-style)` only insofar as that existing path may already cover this — verify during reconciliation.

- `User configuration and authentication` > `Project-type registry in CLAUDE.md as cross-skill router` — `mdproctor/cc-praxis` — Project-level `CLAUDE.md` declares a `## Project Type` field (`java | skills | blog | custom | generic`) that multiple skills read at runtime to dispatch to language-specific sub-skills (e.g., `git-commit` → `java-git-commit` / `blog-git-commit`). User-config-in-CLAUDE.md pattern at project scope, not user scope. Distinct from `Markdown block in consumer's CLAUDE.md` because this is a single typed field consumed by many skills as a routing key, not a freeform config block.

- `Marketplace validation` > `Tiered validator driver` — `mdproctor/cc-praxis` — A single Python driver script (`scripts/validate_all.py`) invoked with `--tier {commit,push,ci}` runs different validator sets at different rigor levels. CI runs all three tiers sequentially. Same runner, escalating flag — distinct from "one workflow per validator type" (`Multi-validator composition`) and from per-stage matrices. Note: the existing `Tiered validator driver` path already exists, this proposal sharpens via a concrete additional sample.

- `Session context loading` > `User-settings session-start hook installed by a plugin skill` — `mdproctor/cc-praxis` — A plugin skill (`install-skills` SKILL.md) instructs Claude to write `~/.claude/hooks/check_project_setup.sh` and modify `~/.claude/settings.json` to register it as a user-level session-start hook. The hook does not register via any plugin's `hooks.json`. Effects: behavior persists after plugin uninstall unless an `uninstall-skills` plugin explicitly unwinds; the hook runs globally on every session regardless of whether the plugin is installed in that project. Note: existing path of same name already covers this pattern; this proposal flags whether to merge or sharpen.

- `Cross-ecosystem distribution` > `Multi-runtime installer with interactive runtime selection` — `raphaelchristi/harness-evolver` — `bin/install.js` detects and installs into any subset of four agent runtimes (`~/.claude`, `~/.cursor`, `~/.codex`, `~/.windsurf`) via interactive prompt letting the user target one, several, or all. Same repo supports two distribution models with two filesystem layouts (plugin-mode under `${CLAUDE_PLUGIN_DATA}`, npx-mode under `~/.evolver`); skills handle the split with runtime fallback (`$EVOLVER_TOOLS`/`$EVOLVER_PY` env vars resolved to `$HOME/.evolver` if plugin envs absent). Distinct from `Multi-runtime install via npm bootstrap` because the selection is interactive and per-runtime, not all-or-nothing.

- `User configuration and authentication` > `External vendor-CLI credential file as secret store` — `raphaelchristi/harness-evolver` — `LANGSMITH_API_KEY` is stored in `langsmith-cli`'s credentials file (`~/.config/langsmith-cli/credentials` or `~/Library/Application Support/langsmith-cli/credentials`), not `userConfig`, not `.env`, not a plugin-specific config. SessionStart hook reads that file and exports the key into `$CLAUDE_ENV_FILE`. Delegates credential lifecycle to a third-party CLI tool — avoids duplicating secret management, creates a hard dependency on the vendor CLI's file-format stability. Sibling to existing `Vendor-CLI credential file` and `Delegated to external CLI`; this proposal pins the specific shape (CLI auth file, hook re-export to `$CLAUDE_ENV_FILE`).

- `Plugin-to-plugin coordination` > `Opportunistic external-MCP install during install-time prompt` — `raphaelchristi/harness-evolver` — npm installer (`bin/install.js`) prompts the user at first-run whether to install Context7 and LangChain Docs MCP servers via `claude mcp add`. MCP registration as a side-effect of plugin install rather than as a declared `dependencies` field entry. The plugin functions without these MCPs; they're an offered augmentation. Sibling to existing `External-MCP install during bootstrap` — this proposal pins the interactive-prompt-during-npm-install shape specifically.

- `Project-convention sidecar files` > `.worktreeinclude` (already exists) — `raphaelchristi/harness-evolver` — confirms the existing path with another instance: `.worktreeinclude` at repo root lists files the plugin should copy into its evolution worktrees (`.evolver.json`, `.env`, `evolution_archive/`). Plugin reads this file when setting up proposer worktrees. Existing path; this is a corroboration, not a new path.

- `Tool-use enforcement` > `acceptEdits permissionMode + git-worktree isolation as safety model` — `raphaelchristi/harness-evolver` — A proposer agent runs with `permissionMode: acceptEdits` (pre-granted edit authority) inside a git worktree the skill creates for it. Safety comes from worktree boundary plus human review at a deploy step, not from tool-use hooks or permission gates. Existing `permissionMode: acceptEdits + worktree isolation` under Agent declaration conventions covers the agent-frontmatter side; this proposal flags whether the same pattern should appear under Tool-use enforcement as the "no enforcement, sandbox the writes" stance, since the plugin has zero PreToolUse/PostToolUse hooks.

## Proposed description sharpenings

> Format: `<role> > <existing-path>` — what the existing description misses; supporting samples; sharpening suggestion

- `Plugin-component registration > Custom sidecar manifest` — `marioGusmao/mg-plugins` exhibits a sidecar with documented runtime-selector intent (`capabilities.json` consumed by a router-plugin to pick which capability to invoke based on `applicable_phases` + `priority`). The existing description likely covers metadata-only sidecars. Sharpening: add a sub-bullet distinguishing "sidecar with consumer documented in same marketplace" (router-plugin reads sibling capabilities) from "sidecar with no observable consumer" (vestigial / aspirational).

- `Version coordination > Marketplace-side pin via source ref` — `raphaelchristi/harness-evolver` exhibits the failure mode: marketplace entry `version: 6.1.0` while `plugin.json: 6.4.2` while HEAD has unreleased work past v6.4.2. The existing description should make explicit that the marketplace-entry version is an authored field that drifts when release tooling forgets to update it; for relative sources Claude Code uses `plugin.json` as authoritative, which means the marketplace-entry value is purely informational and silently stale.

- `Bin entry mechanism > Script-relative shell wrapper` — `mdproctor/cc-praxis` exhibits a strict variant: `PLUGIN_ROOT="$(cd "$(dirname "$0")/.." && pwd)"` with no env-var preference, no fallback cascade. Comment in the file claims "Works both from the plugin cache (${CLAUDE_PLUGIN_ROOT}) and from a local clone" but the mechanism is identical in both — pure script-relative resolution. The existing description should distinguish "script-relative as fallback after env-var" from "script-relative as sole mechanism" — the latter depends on the cache preserving the repo's internal layout.

- `Bin entry mechanism > Stale hardcoded paths after rebrand` — `marioGusmao/mg-plugins` exhibits a related-but-different failure mode: `router-plugin/package.json` declares `"bin": {"router-plugin": "./src/cli.js"}` but `src/` does not exist anywhere in the plugin tree. The bin reference is dead because the file was never committed (or was dropped during sync). Sharpening: rename or split — "stale after rebrand" implies a rename event; "dead bin reference (file never existed in tree)" is a different failure cause with the same symptom.

- `Documentation surface > Layered repo / plugin / skill READMEs (uneven)` — `marioGusmao/mg-plugins` exhibits a five-plugin marketplace where four plugins have READMEs and one (`claude-utils`) does not, where one plugin uses `docs/ARCHITECTURE.md`, another embeds architecture in README via "Why X" headings, a third uses `docs/superpowers/specs/` and `docs/superpowers/plans/`, and a fourth uses `docs/PROTOCOL.md`/`ADOPTION.md`/`CERTIFY.md`/`SCAFFOLD.md` — four different doc structures in one marketplace. Sharpening: add the "convention drift across plugins of the same marketplace" failure mode explicitly so the path captures both unevenness and structural divergence.

- `Install failure posture > `set -euo pipefail` + `trap 'exit 0' ERR` — non-blocking with cleanup` — `marioGusmao/mg-plugins` adds a specific shape: `set -euo pipefail` halts on unexpected errors, but every explicit failure branch writes human-readable stderr prefixed `[CodeGraph]` and still calls `exit 0` after `rm -f` of the marker files (so the next session retries). The existing description should make explicit that the cleanup step and the human-readable advisory before `exit 0` are part of the contract — not just `trap 'exit 0' ERR` but a structured cleanup-then-advisory pattern.

- `Dependency installation > Existence-only check` — `raphaelchristi/harness-evolver` exhibits the upgrade-blind failure mode explicitly: `[ ! -f "$VENV_PY" ]` only triggers on missing venv; `import langsmith` only checks importability, not version. No declared floor anywhere — no `requirements.txt`, no `pyproject.toml`, no version string in the script. If a future feature requires `langsmith>=0.3.5`, the hook never notices a 0.2.0 install is below the floor; `--upgrade langsmith` only fires on explicit npx re-run, never on the SessionStart path. Sharpening: name this "existence + importability check, no version floor" so the upgrade-blind property is explicit.

- `Tag and release lifecycle > Tag-on-main, single branch` — `raphaelchristi/harness-evolver` exhibits a specific drift: HEAD has 14 commits past the latest tag (`v6.4.2`, 2026-04-04) including a substantive feature merge (`feat/autogenesis-rspl`). Marketplace consumers see 6.4.2-labeled work that includes untagged feature commits. Existing description should flag that "tag-on-main, single branch" without a release-cadence discipline produces silent post-tag drift visible to consumers.

- `User configuration and authentication > No userConfig, env-var only` — `mdproctor/cc-praxis` exhibits an env-var-only pattern with a relocate-for-tests escape: `web_installer.py` reads `CLAUDE_SKILLS_DIR` to relocate the install root for tests. Sharpening: name the "test-only env-var override" sub-pattern — env vars used not by users but by the test harness to redirect filesystem writes.

- `Bin entry mechanism > Stale hardcoded paths after rebrand` — should split into:

    - `Dead bin reference (file never in tree)` — bin reference points at a path that does not and never did exist in the committed tree (e.g., `router-plugin/package.json` declares `bin: ./src/cli.js` but `src/` is not present anywhere); the npm `bin` field is therefore vestigial. `marioGusmao/mg-plugins` exhibits this. Different cause, same symptom; readers diagnosing one should not conclude the other. - `Marketplace manifest layout > Custom non-schema fields on marketplace entries` — should split into:
    - `Custom non-schema fields on marketplace entries` (existing) — per-entry custom fields not in the schema

Distinct from per-entry custom fields because this is a top-level grouping primitive that downstream installers can act on. Folded into the existing path in the rewritten sample.

## Structural concerns

> Anything that's hard to fit cleanly under any role/path; questions for the reconciler

- **Per-sample identification metadata (URL, stars, last-commit date, default branch, license, sample origin) doesn't fit cleanly into any role.** Following the convention established by other bins, I moved entity-identification into a one-line preamble after the level-1 heading and omitted numeric metadata (stars, last-commit date). License declaration moved into the `License declaration` role. URL is captured in the preamble.

- **`marioGusmao/mg-plugins` plugin-vs-package.json version drift.** `router-plugin/package.json` declares `"version": "0.1.0"` while plugin.json and marketplace entry both say `1.0.8`. I placed under `Multi-site sprawl (5+ locations)` because three sites diverge, but this is really a "package.json never bumped" sub-pattern — `package.json` was created and forgotten. Defer to reconciler whether this needs a dedicated path or sharpening.

- **`mdproctor/cc-praxis` parallel manual installer**: the repo ships `scripts/claude-skill` (CLI) and `scripts/web_installer.py` (localhost HTTP UI at :8765) as alternatives to `/plugin install`. I placed under existing `Custom installer alternative` paths (`Localhost web UI installer`, `CLI installer with sparse-checkout`) which already exist — but this raises a meta-question: when a sample exhibits multiple sub-paths under one role (web UI installer + CLI installer + sparse-checkout), should the rewritten sample list each as a sibling `###` or consolidate? I listed them as siblings per the "one path per role, but multi-path is a real observation" rule.

- **`raphaelchristi/harness-evolver` zero-CI active project.** I placed under existing `CI workflow shape > No CI`. The sample's commentary is that 41 commits in two weeks plus 10+ tagged releases makes this a notable instance of zero-CI on an active project — but that interpretation is corpus-level, not per-sample. Stripped the cross-corpus framing per the operating principles; left the bare fact (no `.github/workflows/`, only `ISSUE_TEMPLATE/`).

- **`raphaelchristi/harness-evolver` `acceptEdits` + worktree isolation**: this bridges Agent declaration conventions (`permissionMode: acceptEdits + worktree isolation` exists as a path) and Tool-use enforcement (the plugin has zero PreToolUse/PostToolUse hooks; safety is delegated entirely to worktree boundary + human review). I included under Agent declaration conventions; flagged a proposed new path under Tool-use enforcement to capture the "no hooks, sandbox-the-writes" stance.

- **`mdproctor/cc-praxis` `bin/cc-praxis` placement at repo root, not in any plugin.** Since 48 plugin entries are all `./<subdir>` paths and `bin/` is at repo root, the wrapper is not auto-registered with any plugin's bin discovery. Effectively reachable only from a local-clone PATH addition. I placed under existing `Bin entry mechanism > Script-relative shell wrapper` since the resolution mechanism is script-relative, but the `bin/` placement issue itself fits under `Plugin-component placement > Outside plugin directory at repo root`. I included both because they are different observations about the same artifact (its resolution mechanism vs its placement choice).
