## Structural concerns

> Anything that's hard to fit cleanly under any role/path; questions for the reconciler

- The brunoborges/ghx sample captures the install mechanism (lazy GitHub-release download via `bin/` shims, not via SessionStart hook) at two roles: `Bin entry mechanism > Lazy-install bin shim with fallback chain` (the shim mechanism) and `Dependency installation > Pre-built binary download (lazy, per-hook)` (the download/install mechanism). These are distinct concerns (bin invocation vs install) but the sample's facts span both. Verified that placing the install/download details under `Dependency installation` and the shim/exec/fallback details under `Bin entry mechanism` is consistent with how other samples in the corpus separate the two.

- The "dual-CLI marketplace manifest publishing" pattern (one JSON object served from `.claude-plugin/marketplace.json` and `.github/plugin/marketplace.json` for Claude Code + GitHub Copilot CLI) sits at the intersection of `Marketplace manifest layout > Duplicated marketplace manifest at root and nested` (the duplication mechanism) and `Cross-ecosystem distribution > Dual-harness (Claude Code + Gemini CLI)` (the distribution intent). For brunoborges/ghx the mirror is in a separate aggregator repo (`brunoborges/agent-plugins`) and doesn't quite match the existing path's "root and nested" framing — the duplication is across repo paths, not nesting depth. Flagged as a potential bucket-split or sharpening for the reconciler to weigh.

- `anthropics--knowledge-work-plugins.md` exhibits a "nested marketplace.json inside a plugin directory" (`partner-built/brand-voice/.claude-plugin/marketplace.json`) where the nested manifest is not byte-identical to the root entry — the root advertises one in-tree path while the nested manifest advertises a self-contained partner mirror with `metadata.pluginRoot: "."`. Distinct from `Duplicated marketplace manifest at root and nested` (which implies duplication). Mapped to existing `Nested mini-marketplace inside a plugin directory`; flagging the distinction in case the reconciler wants to sharpen description boundaries between the two paths.

- `anthropics--life-sciences.md` has scattered "drift" findings: `metadata.version` (1.0.0) decoupled from release tags (v1.1.1); plugin.json `version: "1.0.0"` permanent across release cuts; `scientific-problem-selection/` exists on disk and ships in release zips but is NOT listed as a plugin in marketplace.json. These three drifts each fit different roles (`Version coordination > Stale fallback constants in code` for the plugin.json drift; `Marketplace validation > No validation` for the unlisted skill drift; potentially a new sharpening for `metadata.version` drift). Routed individually to the appropriate role rather than into a single combined bucket.

- The brunoborges aggregator (`brunoborges/agent-plugins`) is a separate sibling repo from the plugin source repo (`brunoborges/ghx`). The sample is framed around the plugin source repo at `agent-plugin/` subpath but documents both the plugin source and the aggregator's manifest behavior. Where the aggregator-specific facts belong (e.g., `marketplace.json` has 1.0.0 wrapper; aggregator's `.github/workflows/` was not fully traversed) is ambiguous — they're "about" the marketplace surface but the aggregator is technically a separate entity. Filed under `Marketplace manifest layout` and `Marketplace validation` since the sample's framing treats the aggregator as the marketplace surface for this plugin.
