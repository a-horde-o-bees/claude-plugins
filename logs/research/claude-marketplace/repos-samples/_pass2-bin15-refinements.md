## Proposed new paths

> Format: `<role> > <new-path>` — supporting samples — qualitative description draft

- `Bin entry mechanism` > `Bun-shebang TS launcher with three-tier env-var root resolution` — `jmylchreest/aide` — `bin/aide-wrapper.ts` is a TypeScript launcher invoked via `#!/usr/bin/env bun`. Resolves plugin root through precedence `AIDE_PLUGIN_ROOT` > `CLAUDE_PLUGIN_ROOT` > `realpathSync(SCRIPT_DIR/..)` so the same wrapper ships to OpenCode/Codex CLI consumers who don't set `CLAUDE_PLUGIN_ROOT`. Self-heals `node_modules` by running `bun install --frozen-lockfile` inline if missing, then version-checks and downloads a Go binary on demand. Distinct from `Node CLI launcher with env node shebang` (Bun-specific, hard prerequisite — no graceful degradation if Bun is missing) and from `POSIX shell wrapper with ${CLAUDE_PLUGIN_ROOT} fallback` (TypeScript runtime, three-tier env-var precedence).

- `Bin entry mechanism` > `User-PATH-first three-tier shim (user install > plugin cache > download)` — `lukasmalkmus/moneymoney` — `bin/mm` is a 3.4KB bash shim that resolves the underlying binary in three tiers: (1) cleans `self_dir` from `PATH` via `grep -vFx` to prevent self-re-exec, then `command -v mm` searches the cleaned path — if found, `exec "$real_mm" "$@"`; (2) checks `${CLAUDE_PLUGIN_DATA}/bin/mm` and compares its recorded version against `plugin.json`; (3) lazy-downloads a release tarball, `chmod +x`, strips `com.apple.quarantine`, and execs. Inverts the more common "plugin-managed only" pattern: a user with `cargo install` or `brew install` runs their own binary; the plugin never competes. Distinct from `Lazy-install bin shim with fallback chain` (which doesn't prefer the user's pre-existing install) and from `POSIX shell wrapper with ${CLAUDE_PLUGIN_ROOT} fallback` (env-var-driven, not user-PATH-driven).

- `Dependency installation` > `MD5-over-source-concatenation with cross-platform hash fallback` — `jxw1102/flipper-claude-buddy` — `on-session-start.sh` concatenates `pyproject.toml` + `bridge/*.py` and pipes through `md5 -q` (BSD `md5(1)` on macOS) with fallback to `md5sum | cut -d' ' -f1` (GNU coreutils on Linux) and a final `|| echo "none"` trapdoor. Hash stored in `$VENV_DIR/.installed-hash` and compared on every SessionStart; mismatch triggers venv recreate + `pip install --force-reinstall`. Distinct from `Diff-based byte comparison of manifest` (concatenates and hashes content, not diffs files; doesn't depend on a reference tree) and from `Plugin-version stamp file` (content-based rather than version-based). The `"none"` fallback is a trapdoor: on a minimal system without either md5 tool, every session re-installs (or, if `"none"` is stored verbatim, pins forever).

- `Dependency installation` > `Refcount-gated daemon with venv + IPC over Unix socket` — `jxw1102/flipper-claude-buddy` — Beyond venv install, the SessionStart hook spawns a long-running Python daemon (`"$VENV_DIR/bin/python" -m bridge` via `nohup ... &`). Multi-session coordination uses `/tmp/claude-flipper-bridge.refcount`: SessionStart increments, SessionEnd decrements, daemon dies only at zero. PID, socket, log, and skip-stop flag also live in `/tmp/`. Distinct from `Self-healing inline install at MCP launch` (one-shot install, no daemon) and from `SessionStart-driven Python venv with hash gating` (which manages venv lifecycle but no IPC/daemon shape).

- `Bin entry mechanism` > `Self-healing TS wrapper with native-binary download` — `jmylchreest/aide` — Wrapper acts as both launcher and lazy installer for an out-of-tree native artifact. `ensureDependencies()` detects missing `node_modules` (post-`autoUpdate` scenario) and runs `bun install --frozen-lockfile` inline, with `cross-spawn` lazy-required so the install can complete before the require resolves. Then `ensureBinary()` checks `bin/aide[.exe]` existence + parses `aide version` output through SemVer regex, downloads from `releases/download/v<plugin-version>/<binary>` with fallback to `releases/latest/download/<binary>` (race-condition mitigation). `mkdir`-based lock at `bin/.aide-download.lock/pid` with 60s timeout serializes concurrent invocations.

- `Channel distribution` > `Force-recreated floating snapshot tag` — `jmylchreest/aide` — In addition to versioned tags `v0.0.61`, the release workflow maintains a `snapshot` tag that is force-deleted (`git push origin :refs/tags/snapshot`) and recreated on every push to main, then attached to a `prerelease: true` GitHub release. The Go binary's wrapper distinguishes dev builds (`0.0.X-dev.N+sha`) from release builds (`0.0.X`) with different version-compare logic. Consumers caching by tag SHA against `snapshot` see silent moves. Distinct from `SHA pinning per external entry` (stable per entry) and from `Linear 0.0.z dev counter` (single linear sequence, no parallel snapshot artifact).

- `Marketplace manifest layout` > `Self-referential git-subdir source` — `jxw1102/flipper-claude-buddy` — Marketplace at repo root with `source: "git-subdir"` pointing at `path: plugin` of the same GitHub URL — re-clones the repo from origin even though the marketplace and plugin co-locate in one tree. A `relative` source would also work for in-repo co-location; the author chose `git-subdir` so a marketplace-add from GitHub resolves the plugin without requiring users to clone separately. Distinct from `git-subdir into upstream` (which points at a different repo) and from `Relative source pointing to subdirectory` (no network round-trip).

- `Plugin-component registration` > `Hooks.json registering non-canonical events` — `jxw1102/flipper-claude-buddy` — `hooks/hooks.json` registers 15 event types including `StopFailure`, `PostToolUseFailure`, `TaskCompleted`, `SubagentStart`, `SubagentStop`, `Elicitation` — events not listed in the canonical `docs-hooks.md` surface. All matchers are empty string (fire on everything). Whether these events are emitted by current Claude Code is unverified; the plugin treats hook-event variety as a way to discriminate notification sounds at fine granularity. Distinct from `Hooks-json with broad event coverage` (canonical events) by registering events outside the documented surface.

- `Tool-use enforcement` > `Hardware-routed PermissionRequest with timeout fallback` — `jxw1102/flipper-claude-buddy` — `on-permission-request.py` delegates the allow/deny decision to a physical Flipper Zero device via Unix-socket round-trip with a 60-second timeout. Emits `hookSpecificOutput.decision` with `behavior: "allow"|"deny"|"ask"`. Falls back to Claude's native dialog on timeout, error, or no-device (`exit 1`). Generalizes to any "remote approval" surface routed through hook-level PermissionRequest. Distinct from `PermissionRequest with if: allowlist` (no external decision authority).

- `Session context loading` > `Side-effect SessionStart for daemon lifecycle (no context)` — `jxw1102/flipper-claude-buddy` — SessionStart hook does no context emission whatsoever; it manages a long-running Python daemon's lifecycle (install, start, refcount-register the session). Goes beyond `Dependency install only (no context emission)` by also coordinating cross-session daemon state via `/tmp/` files (`claude-flipper-bridge.sock`, `.pid`, `.refcount`, `.log`).

- `Bin entry mechanism` > `Background-disowned SessionStart warmup` — `lukasmalkmus/moneymoney` — `hooks/ensure-binary.sh` forks `("$plugin_root/bin/mm" --version) & disown` and exits 0 immediately, never blocking session startup on network. Composes with the shim's lazy-download path: download logic lives in one place (`bin/mm`); the hook merely triggers it early. Distinct from `SessionStart direct invocation` (which blocks until install completes) by deliberately decoupling the warmup from session readiness.

- `Tool-use enforcement` > `Word-boundary-regex skill nudge with one-shot per-session marker` — `lukasmalkmus/moneymoney` — PostToolUse hook on `Bash` matcher uses `(^|[^a-zA-Z0-9-])mm($|[[:space:]])` to match `mm` only as a whole token (avoids substrings like `mmdd`, `commit`, `common`). Emits a `<system-reminder>` pointing agents at `/moneymoney` skill via `hookSpecificOutput.additionalContext`. Marker file at `${TMPDIR}/.moneymoney-skill-nudge-${session_id}` (with `$PPID` fallback) ensures one-shot per session. Distinct from `PostToolUse local workflow reminders` (typically fires every time, no one-shot semantics) and from `PreToolUse advisory injection (no blocking)` (different hook event).

- `Documentation surface` > `Duplicated CLAUDE.md and AGENTS.md with high drift risk` — `lukasmalkmus/moneymoney` — Both `CLAUDE.md` and `AGENTS.md` exist at repo root with near-identical content (CLI shape, output formats, exit codes, build, commit format, dependencies, skills). No symlink, no generator — manual lockstep maintenance. Distinct from `AGENTS.md as ecosystem-neutral alternative to CLAUDE.md` (which uses one or the other as the canonical source) and from `AGENTS.md as cross-runtime governance unification` (which de-duplicates content rather than parallel-maintaining it).

- `Cross-platform discipline` > `macOS-only with explicit non-Darwin runtime rejection` — `lukasmalkmus/moneymoney` — Plugin installs cleanly on any OS but `bin/mm` exits 127 with a specific "MoneyMoney is macOS-only" message + install hints (`cargo install moneymoney --locked` or `brew install lukasmalkmus/tap/mm`) on non-Darwin platforms. The capability filter is runtime, not install-time — `MoneyMoney` (the upstream macOS GUI app) is the AppleScript integration target, so the binary itself is macOS-bound but the plugin surface is OS-agnostic. Distinct from `POSIX-only with no Windows story` (which doesn't loudly reject — silently degrades) and from `POSIX with documented platform rejection` (which rejects at install).

- `Release automation` > `Cross-build with UPX compression and CDN-fetched zig` — `jmylchreest/aide` — `release.yml` does CGO + zig cross-compile across linux/amd64, linux/arm64, darwin/amd64, darwin/arm64, windows/amd64, windows/arm64, then runs `svenstaro/upx-action@v2 --best --lzma` on Linux and Windows-amd64 (skipping darwin and windows-arm64 where UPX doesn't work reliably). Zig is downloaded from `ziglang.org/builds/...` with `curl` inside each cross-compile step — external dependency on the Zig CDN at build time. Distinct from `Tag-triggered cross-compile + asset upload` by adding compression as a release-pipeline stage and by relying on a zig CDN.

- `Release automation` > `Multi-trigger workflow with snapshot vs release path forking` — `jmylchreest/aide` — Single 28KB workflow handles PR CI, main-branch snapshots, and tag releases by gating jobs on `needs.prepare.outputs.is_release` and `github.event_name == 'push'`. `prepare` job detects "commit already has release tag" via `git tag --points-at HEAD | grep -E '^v[0-9]+\.[0-9]+\.[0-9]+$'` to skip the snapshot path on a release commit. Snapshot path force-deletes and recreates the `snapshot` tag on every main push; release path attaches binaries via `softprops/action-gh-release@v2` with `generate_release_notes: true`. Distinct from `Multi-trigger workflow with single-snapshot path` by additionally branching internal job execution on detected release-tag presence.

- `Source layout` > `Multi-target adapter tree with shared TS core` — `jmylchreest/aide` — Same TypeScript core under `src/core/` is packaged as (a) Claude Code marketplace plugin (this repo), (b) OpenCode npm package via `packages/opencode-plugin/`, (c) Codex CLI install target via `bunx @jmylchreest/aide-plugin install --platform codex`. `src/opencode/` adapts core; `src/cli/` drives the npm install flow. A single plugin root directory serving three different AI-coding-assistant ecosystems. Distinct from `Adapter directory per host CLI` by sharing TS core across adapters rather than duplicating manifest formats; distinct from `Generated manifests from upstream config` by being source-shared rather than generated.

- `Cross-ecosystem distribution` > `Bun runtime as hard prerequisite for cross-ecosystem plugin` — `jmylchreest/aide` — Plugin ships to Claude Code, OpenCode, and Codex CLI but the wrapper's `#!/usr/bin/env bun` shebang and `Bun.sleepSync` lock-poll make Bun a hard prerequisite across all three ecosystems. README states "**Prerequisite:** Bun — the only runtime dependency. The Go binary downloads automatically." Distinct from `Triple-ecosystem (Claude + Codex + Cursor)` by requiring a non-default runtime (Bun) on every host rather than degrading to Node.

- `Component composition` > `src/agents/ as internal-skill-consumed agents (not plugin-registered)` — `jmylchreest/aide` — Agents at `src/agents/*.md` (architect, designer, executor, explore, planner, qa-tester, researcher, reviewer, writer) carry standard Claude Code agent frontmatter (`name`, `description`, `defaultModel`, `readOnly`, `tools`) but live outside `.claude-plugin/agents/` and have no `agents` field in `plugin.json`. They are consumed internally by the swarm skill's orchestration logic — not registered as plugin sub-agents. A reader scanning directories for agent definitions could mistake them for plugin-registered agents. Distinct from `Agents` under Component composition (which presupposes plugin-registration).

## Proposed description sharpenings

> Format: `<role> > <existing-path>` — what the existing description misses; supporting samples; sharpening suggestion

- `Live monitoring > monitors.json absent` — current description states the absence. `jmylchreest/aide` and `jxw1102/flipper-claude-buddy` exhibit two different "absent monitors.json with live notification work elsewhere" patterns. Aide implements live HUD updates via PostToolUse hook writing to `.aide/state/hud.txt` plus a separately-installed `~/.claude/bin/aide-hud.ts` status-line script. Flipper uses sound/vibration/display notifications routed through hook events. Sharpening: name "absent monitors.json may coexist with substantial live-notification machinery implemented at a different layer (hook-driven file writes, hardware peripheral, status-line wrapper)" — currently the description risks reading as "no live behavior at all" when in fact the plugin can have substantial live behavior outside `monitors.json`.

- `Channel distribution > Linear 0.0.z dev counter` — `jmylchreest/aide` carries `0.0.61` and uses `0.0.z` as a release counter, but synthesizes a separate `0.0.X-dev.N+sha` form computed via `git describe --tags --match 'v*' --always --long` for the Go binary's embedded version string only. The plugin.json's `0.0.z` does NOT dev-bump; it tracks released semver. Sharpening: distinguish "0.0.z as release counter where each commit auto-bumps z" (the existing pattern) from "0.0.z as released counter where dev builds carry a separate `-dev.N+sha` suffix not applied as a tag" (the aide variant — different counter semantics).

- `Source-pin maintenance > Registration-list drift guard` — current description names registration-list drift detection. `jmylchreest/aide`'s `bin/aide-wrapper.ts` reads version from `.claude-plugin/plugin.json` first then `package.json`; `src/lib/aide-downloader.ts` reads from `package.json` first. Two version sources accessed in different orders by different callers — same kind of drift surface but at the read path, not the registration list. Sharpening: extend or split to cover "version-source-precedence drift" — different callers reading the same version metadata in different orders create silent drift even when both sources are kept in sync, because a future divergence is consumed inconsistently.

- `Tool-use enforcement > PostToolUse local workflow reminders` — current description names PostToolUse-driven workflow nudges. `lukasmalkmus/moneymoney`'s nudge has two distinguishing properties not captured: (1) word-boundary regex to avoid substring false positives (`mm` matches in `mmdd`/`commit`/`common`); (2) one-shot per-session marker via `${TMPDIR}/.moneymoney-skill-nudge-${session_id}`. Sharpening: name the discrimination strategies (regex-boundary matching, session-scoped marker) so future implementations can adopt them rather than re-deriving.

- `Channel distribution > Pre-release tag suffixes on a single channel` — `jmylchreest/aide` exhibits a hybrid: bare semver tags (`v0.0.61`) plus a permanently-floating `snapshot` tag force-recreated on every main push. The pre-release suffix lives in the `snapshot` artifact's binary version (`-dev.N+sha`) rather than in the tag itself. Sharpening: name the variant where pre-release semantics are carried by a separate floating tag rather than by the tag suffix on the release tag — distinct from `0.4.0-rc1`-style suffixes on a single tagged release.

- `User configuration and authentication > CLAUDE_PLUGIN_OPTION_<KEY> env-var consumption` — `jxw1102/flipper-claude-buddy` exhibits a re-export pattern: SessionStart hook reads `CLAUDE_PLUGIN_OPTION_serial_port`, `CLAUDE_PLUGIN_OPTION_transport`, `CLAUDE_PLUGIN_OPTION_bluetoothName`, then re-exports them as `FLIPPER_*` env vars consumed by the Python daemon. Decouples plugin-manifest naming from the daemon's env-var contract. Sharpening: name the "key rename / re-export" sub-pattern — distinct from direct consumption where the plugin code reads `CLAUDE_PLUGIN_OPTION_*` directly.

## Structural concerns

> Anything that's hard to fit cleanly under any role/path; questions for the reconciler

- **Per-sample identification metadata.** Each original sample opens with an Identification section listing URL, stars, last-commit date, default branch, license, sample origin, and one-line purpose. Per the operating instructions I moved entity-identifying content into a one-line preamble. Numeric metadata (stars, last-commit date) is omitted; default branch and SPDX license are mentioned only when load-bearing for a path's evidence (e.g., MIT under License declaration). Question for reconciler: should there be a structured preamble convention so per-entity facts (stars, last commit, branch name) are retrievable without polluting the role tree?

- **Skill activation mechanisms outside Claude's `description`-based activation.** `jmylchreest/aide` skills declare a `triggers: [...]` array (~10 short phrases each) consumed by a fuzzy-matched `UserPromptSubmit` injection. This is a parallel skill-activation mechanism to Claude's built-in `description`-based dispatch. I placed it under `Session context loading > UserPromptSubmit fuzzy-matched skill injection` (which exists). But the *trigger-array as skill-frontmatter declaration* (a skill-authoring pattern, not just a session-context pattern) doesn't fit cleanly under `Skill authoring conventions` — there's no path for "non-standard frontmatter fields beyond Claude's documented set." Could be a description sharpening on `Skill authoring conventions > Standard frontmatter` to acknowledge that some plugins layer their own activation fields (`triggers:`, `platforms:`, `compatibility:`) on top.

- **Out-of-band hook installation as a side effect of SessionStart.** `jmylchreest/aide`'s SessionStart hook installs `~/.claude/bin/aide-hud.ts` (Bun-shebang script that discovers the newest installed plugin version and delegates) on first run. A side-effect on the user's home directory not declared in `plugin.json` or marketplace metadata. Doesn't fit `Out-of-band hook registration` (which is about registering hooks outside the manifest, not about installing files outside the plugin tree). Could be a new path under `Plugin/state separation` or under `PATH augmentation and host-project setup` — leaning toward the latter ("HUD wrapper installed into ~/.claude/bin at SessionStart for cross-version forwarding").

- **Three-version-string state machine.** `jmylchreest/aide` distinguishes release (`0.0.61`), dev-build-from-main (`0.0.62-dev.5+a1b2c3d`), and unknown — the wrapper handles all three with different version-compare logic (dev: `base >= plugin`; release: `>=` exact; unknown: use-what-we-have). Sits between `Channel distribution` (which is about channels) and `Version coordination` (which is about cross-site coordination of one version). I placed it under `Channel distribution` near the snapshot-tag entry. Reconciler may decide whether the version-state-machine deserves its own path.

- **`.claude-plugin/settings.json` as empty placeholder `{}`.** `lukasmalkmus/moneymoney` has `.claude-plugin/settings.json` as literally `{}` — kept as a placeholder rather than omitted. Doesn't fit any existing path under `Permission and contributor governance` (which addresses content) or under `Plugin-component registration` (which addresses what's registered). Could be a description sharpening on `Permission and contributor governance > Plugin-root settings.json — agent pointer only` to acknowledge the "intentional empty placeholder" sub-case where the file is present but carries no settings — flag as benign-but-unused.

- **Hardware-as-UI as a category beyond software-only plugins.** `jxw1102/flipper-claude-buddy` ships a daemon talking to a Flipper Zero device with C firmware in the same repo. The full system is a tri-repo pattern (FAP firmware + Python daemon + plugin scripts). Hard to fit cleanly into any single role. Distinct facts went into Tool-use enforcement (PermissionRequest hardware routing), Dependency installation (refcount-gated daemon), Documentation surface (firmware-scoped CHANGELOG, three coordinated version strings). Reconciler may want to consider whether "hardware-coupled plugin" warrants any cross-cutting acknowledgment.
