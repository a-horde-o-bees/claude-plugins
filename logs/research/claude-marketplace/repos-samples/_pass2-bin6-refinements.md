## Proposed new paths

> Format: `<role> > <new-path>` — supporting samples — qualitative description draft

- `Per-plugin discoverability metadata > Keywords drift between marketplace entry and plugin.json` — JordanCoin/pdf-to-text — Marketplace-entry `keywords` array and plugin.json `keywords` array each declare semantically related but unequal lists (e.g. 5 vs 6 entries). No tooling reconciles. Variant of cross-file drift specific to two `keywords` arrays rather than a `category`/`tags` mix.
- `Plugin source binding > `repository` field points to non-existent repo` — JordanCoin/pdf-to-text — `plugin.json.repository` URL points to a sibling repo that returns 404 (e.g., engine-binary repo not yet created). Manifest declares a vapor URL; consumers following the link land on a missing page.
- `Version coordination > Five-way version sprawl with no sync mechanism` — JordanCoin/pdf-to-text — `plugin.json`, marketplace entry, top-level `VERSION` file, sub-package `package.json`, AND a hardcoded constant in source code (e.g., `version: "0.1.0"` in `mcp-server/src/index.ts`) all carry the same version with zero sync mechanism — no script, no CI gate, no pre-commit hook. Distinct from "Multi-site sprawl (5+ locations)" which describes the existence of many version sites; this captures the absence of any sync at all.
- `Channel distribution > Cross-repo update poller pointing at non-existent repo` — JordanCoin/pdf-to-text — A bin-script update poller (`bin/update-check`) curls `api.github.com/repos/<other-owner>/<other-repo>/releases/latest` for an engine-binary repo that does not yet exist. The poller's silent-on-network-error branch fires, so no update notice ever surfaces. The "channel" is wired to a vapor endpoint.
- `Bin entry mechanism > Half-implemented snooze read-path with missing write-path` — JordanCoin/pdf-to-text — `bin/<plugin>-update-check` parses a `$SNOOZE_FILE` carrying a 3-field record (`version level epoch`) and uses a `case` on level to pick escalating durations (24h → 48h → 7d), but no script in the repo writes the file. Read path exists; write path absent. Captures partial-feature pattern where design intent is visible in code but functionality is incomplete.
- `Documentation surface > MCP build prerequisite undocumented` — JordanCoin/pdf-to-text — `.mcp.json` invokes `node ${CLAUDE_PLUGIN_ROOT}/<subdir>/dist/index.js` but `dist/` is gitignored and no hook builds it. README does not document the `npm install && npm run build` step required before the MCP server loads. Fresh installs silently fail at MCP startup. Pairs with "Documentation drift signals" but is more specific — a build precondition exists but is documented nowhere.
- `Install change detection > No sha verification on downloaded payload` — JordanCoin/pdf-to-text, K-dash/typemux-cc — Install scripts fetching binaries or WASM payloads from GitHub Releases skip sha256/signature verification. Trust is implicit in HTTPS plus GitHub Releases. A compromised mirror or MITM delivers arbitrary content. Already implicit in some existing paths; could be surfaced as its own concern under change detection or as a note on existing native-binary paths.
- `Source layout > Repo-local developer skills shipped to end users` — K-dash/typemux-cc — `.claude/skills/<dev-skill>` directories at repo root (e.g., `plugin-test-cycle`, `publish`) are auto-discovered by Claude Code on any install. End users see triggers meaningful only to the plugin author. (Note: this is already covered as `Distribution exclusion and dogfood layout > Repo-local developer skills exposed as plugin skills` — proposing to verify that path's coverage matches.)
- `Plugin-component registration > Inline `lspServers` plus duplicate root `.lsp.json`` — K-dash/typemux-cc — Plugin declares the same LSP server entry twice — once inline in `plugin.json.lspServers` and once in a sibling `.lsp.json` at repo root. Claude Code consumes the `plugin.json` form; the standalone file is either a vestige or a standalone-mode fallback. Duplicate-source-of-truth defect specific to LSP config.
- `Plugin-to-plugin coordination > Required-disable conflict declared in README prose only` — K-dash/typemux-cc — README instructs users to `/plugin disable <other-plugin>@<other-marketplace>` before installing because two plugins would register conflicting LSP servers. Plugin metadata has no mechanism to declare exclusivity. Already partially covered by `Implicit prose-only dependency`; this is the conflict-mode variant ("require disabling another plugin" rather than "require installing another plugin"). May warrant a sub-path.
- `Bin entry mechanism > Orphan wrapper sourcing user config that the binary already reads natively` — K-dash/typemux-cc — Refines the existing `Orphaned wrapper alongside downloaded binary` path. The wrapper sources `~/.config/<plugin>/config` then `exec`s the binary; the Rust binary loads the same config natively at startup. Wrapper is committed and `chmod +x`ed; install.sh copies it next to the binary; nothing references it. Specific signal: half-completed refactor from wrapper-based config loading to in-binary config loading.
- `User configuration and authentication > Wrapper config-loading semantics diverge from binary parser` — K-dash/typemux-cc — A committed wrapper sources a `KEY=VALUE` config via shell `source`, supporting `$(...)`, backticks, `$VAR` expansion. The Rust binary parser (`src/config.rs`) explicitly rejects shell expansion. A user upgrading from wrapper-era config to binary-era config could carry a syntactically valid shell file the binary refuses to parse. Compatibility-drift defect across two parsers for the same file format.
- `Documentation surface > AGENTS.md as canonical, CLAUDE.md as pointer` — K-dash/typemux-cc — `CLAUDE.md` is two lines that delegate (e.g. `@AGENTS.md` include) to a substantive `AGENTS.md` carrying the full agent rule set. Inverts the convention where `CLAUDE.md` carries primary content. Different from "AGENTS.md as ecosystem-neutral alternative" — here both files exist and CLAUDE.md is intentionally a pointer.
- `Marketplace manifest layout > `metadata.{description, version}` lagging plugin.json version` — Kanevry/session-orchestrator — Marketplace `metadata.version` carries one version (`2.0.0`) while `plugin.json.version` is at a later pre-release (`3.0.0-dev`). Treated by the author as marketplace-bundle version, separate from plugin version. Already covered by `Top-level metadata wrapper variants` paragraph noting "drift goes unnoticed" — proposing the specific case where the marketplace metadata version lags by a major number.
- `Version coordination > Banner version embedded in hooks.json` — Kanevry/session-orchestrator — `hooks.json` SessionStart hook carries an inline `echo '...v2.0.0...'` banner whose hardcoded version string drifts independently from `plugin.json.version`. Adds a fifth (or sixth) version-bearing site in hook payload itself. Variant of "Multi-site sprawl" where the version is in shell-quoted hook string output rather than a manifest field.
- `User configuration and authentication > JSON-Schema validator for parsed CLAUDE.md block with bypass env var` — Kanevry/session-orchestrator — Refines `Markdown block in consumer's CLAUDE.md`. The plugin ships `scripts/lib/config-schema.mjs` (full JSON-Schema) plus `scripts/validate-config.mjs` and a bypass env var (`SO_SKIP_CONFIG_VALIDATION=1`). Validation runs at session start; failures emit corrective error context. Already partially captured; proposing the schema-versioning + bypass-env-var sharpening.
- `Tool-use enforcement > Hook output via centralized emitAllow/emitDeny/emitWarn helpers with non-empty-reason invariant` — Kanevry/session-orchestrator — Refines `Fail-closed scope and command guards (belt-and-suspenders)`. Adds the structural invariant that `emitDeny` throws a `TypeError` if reason is empty — making "silent deny" structurally unrepresentable. Plus 1 MB stdin cap and 5s `AbortController` timeout in `readStdin()` that bubble to the top-level catch. The non-empty-reason enforcement is a specific discipline worth flagging beyond what the existing path text mentions.
- `Hook handler runtime > Stop and SubagentStop in one file via event-name discrimination` — Kanevry/session-orchestrator — `on-stop.mjs` handles both `Stop` and `SubagentStop` events by discriminating via `hook_event_name` (with `agent_name` fallback). Single file, two hook events, exploiting common payload shape. Specific consolidation pattern within hook handlers.
- `Telemetry and self-evaluation > Cross-IDE platform branching via shared mjs library` — Kanevry/session-orchestrator — `platform.mjs` exposes constants (`SO_PLATFORM`, `SO_IS_WINDOWS`, `SO_IS_WSL`) so shared library code can branch by host. Used alongside `JSONL append plus optional remote POST` to gate behavior per IDE. Could be a new path or a sharpening of an existing cross-platform discipline path.
- `Testing > vitest with skill-local nested package.json and CI nested-install step` — Kanevry/session-orchestrator — Refines `vitest with multi-suite layout`. Glob includes both `tests/**/*.test.mjs` and `skills/*/tests/**/*.test.mjs`. CI workflow runs `(cd skills/<skill> && npm install …)` in a separate step before the main `npm test` to bootstrap a skill that has its own `package.json` with runtime deps. Captures the "nested package.json inside a skill" pattern and its CI ergonomics.

## Proposed description sharpenings

> Format: `<role> > <existing-path>` — what the existing description misses; supporting samples; sharpening suggestion

- `Bin entry mechanism > Skill-invoked update poller` — JordanCoin/pdf-to-text — Existing description covers the polling mechanism and `UPGRADE_AVAILABLE`/`JUST_UPGRADED`/nothing emission contract. Could sharpen by adding: the snooze sub-feature can be partial (read path implemented, write path absent), turning the documented escalation into design intent without runtime functionality. Also: state coordination split between hook (writes `${INSTALL_DIR}/.version` + `just-upgraded-from`) and skill bin (reads both, writes `last-update-check` + `update-snoozed`) — explicit shared-sentinel-file convention.
- `Plugin-runtime root resolution > Three-tier with hardcoded data-dir terminal fallback` — JordanCoin/pdf-to-text — Confirms the existing description: terminal fallback is `$HOME/.config/<plugin>` (the data dir, not a plugin code dir). Sharpening: explicit note that this is semantically wrong for code that needs to read SKILL.md siblings — works only because the skill preamble's downstream invocations (`$_PLUGIN_DIR/bin/*` and `$_PLUGIN_DIR/hooks/*`) are wrapped in `2>/dev/null || true`, which swallows the resulting path errors.

Sharpening: cross-repo dependency (plugin repo + separate engine-binary repo with the WASM artifacts on its Releases). Plugin's `VERSION` file pins the engine version to download. - `Bin entry mechanism > Pre-built binary download (lazy, per-hook)` — K-dash/typemux-cc — Existing description covers Go-flavored cross-platform download. Also: unauthenticated GitHub API call (`/releases/latest`) hits 60/hr rate limit per IP, surfacing as cryptic "Failed to find binary for ..." errors when the limit hits.

Sharpening: when paired with `source: "./"` self-referential marketplace, the plugin filesystem boundary swallows non-plugin content (CI configs, lockfiles, contributor docs, `node_modules/` after install) unless filtered by `.claude-plugin/ignore` or similar. ## Structural concerns

> Anything that's hard to fit cleanly under any role/path; questions for the reconciler

- The existing path `Documentation surface > AGENTS.md as ecosystem-neutral alternative to CLAUDE.md` and the proposed sharpening `AGENTS.md as canonical, CLAUDE.md as pointer` are subtly different states. The existing path describes "AGENTS.md present alongside CLAUDE.md as cross-runtime governance unification." The K-dash/typemux-cc case is "CLAUDE.md is a 2-line `@AGENTS.md` include." Recommendation: treat as a sub-variant or new sibling path.
- The `Plugin-component registration > Inline mcpServers definition in plugin.json` paths group by what's inline. K-dash/typemux-cc declares an inline `lspServers` block plus a duplicate `.lsp.json` at repo root. Reconciler should decide whether `lspServers`-specific paths belong under the existing `Inline …` family or get their own sibling describing LSP-specific duplication.
- Kanevry's `.mcp.json` invokes `bash -c "exec bash ..."` against a shell script (`scripts/mcp-server.sh`). This is functionally a hook-side wrapper but lives under `.mcp.json`'s `command`, so it doesn't fit `Bin entry mechanism` cleanly. Considered placing under `Server runtime (MCP)` but no existing path matches "MCP server is a bash script with cascading env-var fallback." Surfaced as Open Question.
- Kanevry's "Session Config" parsing (markdown block in consumer CLAUDE.md, schema-validated, env-var bypass) is captured by `User configuration and authentication > Markdown block in consumer's CLAUDE.md`. The plugin also implements a JSON-Schema-driven config schema (`config-schema.mjs`), a runtime validator (`validate-config.mjs`), and a homegrown agent-frontmatter linter (`agent-frontmatter.mjs` + tests). These extra layers cross between User configuration, Marketplace validation, and Tool-use enforcement. Surfaced as a sharpening candidate but might warrant cross-references in the consolidated.
- JordanCoin's `bin/update-check` references a `SNOOZE_FILE` and parses a 3-field record but never writes it. Half-implemented features — design visible in source, runtime incomplete — recur across samples (Kanevry's documentation-asserted-but-unwired hooks, JordanCoin's snooze write path, `glyph-api` repo not yet existing). Consider whether this warrants a cross-cutting "incomplete-implementation surface" annotation in the consolidated rather than a per-role new path.
